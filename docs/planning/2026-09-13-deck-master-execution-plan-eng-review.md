## 1. 主要发现

### F1｜[P1] (confidence: 9/10) 成稿接入仍未定义完整的数据交接

位置：[执行方案:97](2026-09-13-deck-master-execution-plan.md#L97)、[执行方案:292](2026-09-13-deck-master-execution-plan.md#L292)。

方案提出“Agent 叙事被生产主链接受”，又把叙事建议接口是否支持“增删、顺序和后续引用”留到实施时确认。这是 WP3 的主要接入边界，不能仅靠已有接口名称视为可用。

当前代码给出了更确定的限制：

- [narrative.py:399](../../scripts/advisory/narrative.py#L399)：`if beat_id not in beat_map:`，下一行执行 `continue`，新页面被跳过。
- [narrative.py:410](../../scripts/advisory/narrative.py#L410)：`planning["decision_intent"] = action`；该段写回的主要是规划字段，不能等同于接收完整标题、正文、图示关系及页面顺序。
- [deck_master.py:537](../../scripts/deck_master.py#L537)：`narrative_plan = plan_narrative(`；后续还会从规划构造 page_tasks。新接入必须明确何时沿用已有成稿、何时允许重新规划。

定向实验向现有接口提供一个新的公司介绍页面：校验返回 `valid: true`，但差异中的 `page_task_changes` 是空数组。此实验只证明该接口的局限，不声称新方案已经实施后仍会丢页。

**影响：**主编即使写好了内容，实施仍可能只接入部分规划字段；再次生产时，页面集合、正文或顺序未进入实际消费链。接入成功的状态也可能掩盖新页面被忽略。

**建议补入 WP3：**明确沿用哪些现有产物承载页面集合和顺序、对外正文、图示及来源引用。优先复用 narrative_plan/page_tasks 与 Page Package；明确整稿接收、页面增删/重排、正文更新、下游重建各自读写哪些产物。已接收的成稿继续生产时保留正文与顺序；只有任务发生相应变化时才重新规划。无需新增一套内容对象或独立服务。

**验收动作：**用一份包含公司介绍、明确顺序和完整正文的稿件接入正常入口；增加一页、删除一页、调整顺序，再继续生产和恢复，核对实际 PPT 的页面集合、正文、图示关系及引用。未知页面不能静默跳过；旧页面 ID 和未受影响内容得到保留。

**处理节点：**在 WP3 的接入实现开始前补齐该小段设计。WP1/WP2 的试做可以先行。

### F2｜[P2] (confidence: 9/10) 冻结后的验证没有覆盖核心“方案评审”类型

位置：[执行方案:16](2026-09-13-deck-master-execution-plan.md#L16)、[执行方案:142](2026-09-13-deck-master-execution-plan.md#L142)、[执行方案:147](2026-09-13-deck-master-execution-plan.md#L147)。

方案优先承诺“能力/产品说明与方案/设计论证”，但冻结后的两个任务是“H1 陌生企业能力/产品说明、H2 新材料研究简报”。同时明确“P1 在使用后同样成为开发材料”。

**影响：**方案评审只有 D2 和早期 P1 的开发证据；冻结版即使 H1/H2 成功，也没有检验其面对未调试过的方案论证任务时能否成立。研究简报占用了一个验证位置，却是首轮是否公开仍待判断的能力。

**建议：**保持轻量规模，优先让 H1/H2 分别覆盖陌生企业能力说明和陌生客户方案评审；研究简报作为额外探路任务，若拟纳入公开承诺，再安排相应未见材料。另一种可接受处理是明确收窄首轮公开范围，不能把研究简报结果当成方案论证的迁移证据。

**验收动作：**冻结后使用没有进入方法调试的来源包和方案评审任务，检查推荐方案、业务机制、取舍和成立条件；仍按第一次完整交付评阅，不改成关键词断言。

**处理节点：**WP4 开始前确定任务对应关系，不增加固定运行配额。

### F3｜[P2] (confidence: 8/10) 无库验收尚未绑定开源用户实际安装的产物

位置：[执行方案:103](2026-09-13-deck-master-execution-plan.md#L103)、[执行方案:154](2026-09-13-deck-master-execution-plan.md#L154)。

方案已经要求无安装、无配置、无缓存环境，也要求开源使用说明和公开样例；但未明确从新生成的安装产物启动验收。源码目录中的正常入口与实际安装后的 Skill/CLI 仍可能使用不同的方法文件或能力清单。

当前实现确有独立的发布路径：

- [installer.py:1834](../../scripts/skills/installer.py#L1834)：`_copytree_replace(source, release_root / "skills" / name)`。
- [installer.py:1885](../../scripts/skills/installer.py#L1885)：发布文档采用显式清单，不会自动包含全部仓库文档。
- [installer.py:1909](../../scripts/skills/installer.py#L1909)：`json.dumps(product_capability_manifest(), ensure_ascii=False, indent=2)`，发布清单由函数重新生成。
- [installer.py:2391](../../scripts/skills/installer.py#L2391)：`"delivery": "ready" if full_suite_ready else "blocked"`。所选路线与全套能力的依赖判定需要在实际安装结果中保持一致。

**影响：**本地已改的方法和无库路线可能试做成功，用户安装后仍拿到旧指令、未包含的方法文件，或全套依赖判定。当前证据说明此处需要验收，并未证明候选安装包已经发生了这些故障。

**建议：**将现有无库端到端验收至少一次安排在新建 release tree 的已安装入口上。复用 release-build/release-smoke；选定一个本轮支持的宿主与生产路径，从公开样例启动，验证方法可达、正确版本被使用、无关 Library 不被要求、实际文件可交付。只核验所声明的环境，不新建安装平台或扩大宿主矩阵。

**验收动作：**用安装后的 Skill/CLI 完成同一份公开样例，过程中不借开发 checkout 的文件路径补方法或补脚本；显式请求 Library 的任务仍返回其真实依赖信息。

**处理节点：**WP5 的开源交付收口前。已有安装/发布机制足够作为基础。
