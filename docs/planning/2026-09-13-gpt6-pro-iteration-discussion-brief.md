## 1. 本轮要你参与什么

本轮重点是内容专业性、内容结构、产品差异和迭代方式。先提出有依据的判断与可比较的方案，不直接编写大规模工程 Spec，不开始实现，不把问题转化为一串要求用户填写的问卷。

## 2. 项目背景与已有成果

Deck Master 是本地优先、面向 Agent 的 Solution Deck 生产与编排项目。通过 CLI、Skill 和审查界面管理资料、需求、叙事、页面生产、构建、质量检查与交付。

演进大致为：
- 2026-05-21：最早 Office Hour 关注历史 PPT 的页级检索与复用。当时的问题是从约 500 份历史 PPT 中找合适页面。
- 2026-06-10：扩展为 Professional Deck Run OS，最初目标是把“方案思路基本确认到第一版可审查草案”从约 12 小时压到约 2 小时。
- 6月至7月：逐步建设运行状态、恢复、Skill 套件、审查界面、安装、依赖绑定和发布验证。
- 8月：增加高密度页面、图像蓝图、原生 SVG、可编辑 PPTX 与读回检查。
- 9月：出现过度防御治理、独立安装与公共方案内容能力的 SC-1 规划。旧 SC-1 不应自动成为本轮必须全量继承的范围。

应保留的成绩：
- 历史记录包含真实 12 页交付。
- 存在 73 页图像转原生 SVG 的历史脱敏证据，但不能据此声称 73 页全部完成当前版本 PPTX 端到端验收。
- 用户认为此前一个实际客户项目的“图像 → SVG → 最终 PPT”生产相对顺利，是较好的部分；视觉保真仍需要调优。
- 不应把整个系统全部推倒，也不应把已有工程成果等同于已证明专业初稿稳定可用。

## 3. Codex 已核查的具体事实及边界

以下是本次复盘对本地 main@bcb5b37 的读取与小范围探针结果，不是对更晚主线的现状声明，也不是完整生产审计。若项目文件或远端已有更新，请注明差异，不能把已修复问题再次当成当前缺陷。

1. 通用资料入口 scripts/context_intake/local_sources.py 将单份摘要截取至约 260 字，摘录至约 900 字；brief_compiler 以主题和摘要切句构成核心要点。宿主 Agent 可提供更丰富输入，因此不能说所有路径都只有截取能力。
2. scripts/planning/page_budget.py 的默认 GENERIC_BEATS 预置“开场定位、业务痛点、关键挑战、总体方案、实施与服务保障、目标架构、业务场景、数据与运营、流程、案例、价值、CTA/试点推进”，没有公司介绍。
3. draft_gate_v2 的部分叙事检查偏向 opener / 问题框架；生成和检查可能共同强化一种固定结构。
4. 对 _judge_evidence_sufficiency 的函数级探针：一个没有来源、没有 risk_flags 的论点，返回“1/1 个论点有充分证据支撑”、100% 覆盖率和 0.9 置信度。这是该函数的反例，不证明所有下游交付门禁都会放行。
5. Deck Planner、Deck Quality、Deck Review 的公开 Skill 入口大量描述前置条件、命令、产物和停止条件，专业规划与编辑方法相对薄。外部语义审查有入口，不能说完全没有。
6. 客户可见语言检查主要包含词表扫描；语义审阅提示较宽泛，未充分保证实际页面全部成为对外正文。
7. 当前仓库中 ppt-deck-pro-max 是指向 deck-producer 的兼容入口，不能凭不同名称就认定是独立产品能力。
8. 故事线选择曾因无法实际配置的 Host/UI 密钥停滞；封面等曾被正文规则误杀，旧报告曾阻断新产物。相关修复已进入所查主线，故事线选择已改为正常推进。这些是设计教训，不应全部重报为现存缺陷。
9. 本地 2026-07-03 旧 benchmark 汇总曾显示平均估算节省约 14.6 小时，同时 final_ready_count=0。估算来自人工基线减去阶段时间，不能当成用户端到端投入的实测。没有采用反馈也不等于没有价值。
10. 当时生产诊断 blocked 包含本机安装、后端绑定、发布证据和未指定 run 等条件；这不是证明历史交付失败的证据。

## 4. 用户明确提出的要求与纠正

### 4.1 核心价值是达到专业可用门槛，不以耗时为中心

用户指出：
“假设你现在产出的内容低过一定的阈值，我没有去改的想法。”
“产出这种高质量的、能一次可用的内容，才是这一类型的产品最核心的、最关键的价值点。”

这些材料会被专业人士逐页审视，局部事实、业务逻辑、叙事或表达错误会迅速放大，不能被整套平均表现掩盖。

用户认为事后要求自己回来报告“我已完成、花了多少时间”不符合自然工作方式，难以回收。不要把计时、完成登记、重写字数填报设计成必须由用户配合的使用流程。

工作解释：第一次交给用户的完整稿应能进入正常业务审阅，不需要用户重建主线、补写核心论据、清理大批制作语言。系统内部可自行检查和返修；不应承诺绝对无需任何人工调整。

### 4.2 过度防御存在产品价值问题

用户认为很多机制完全无助于实际业务目标，在 Deck Master 和其他项目中都出现过。
不能只把“不必要的硬门禁”改成“可选门禁”来保留所有设计。需要重新判断功能是否值得存在。
保留实际必要的事实、隐私与交付质量保障，但不能以假想风险不断增加流程和用户负担。

### 4.3 PPT Library 的需求与关系需要重新判断

用户不记得真正完成过一次“通过 PPT Library 提取历史页、合并内容、结合新生产页、最终整套交付”的全过程，因此连这条需求是否仍成立都需要讨论。
不能把“从未做过”当作本次已完成全库审计的事实，也不能继续把其成立当作默认前提。
历史 PPT 可以是事实来源、案例、思考方式、业务图、视觉参考或完整页面；RAG 只是获取材料的手段之一。
Deck Master 不必强绑定 PPT Library。

### 4.4 商业叙事严重不合场景

用户经常看到模型：
- 习惯以诊断、痛点开场。
- 默认写 CTA 或呼吁开始 POC。
- 忽略公司介绍与能力说明，即便真实商业交流需要先建立信任。

用户不是要求所有材料必须固定先写公司介绍，而是要求符合真实商业场景。
模型选择可能影响表现，但默认模板和质量标准本身也有责任。

### 4.5 思考过程、内部制作语言进入最终页面

实际页面出现大量内部语言、制作说明和思考过程表达。
用户专门做了 Deck Quality 与 Deck Review，但效果未达预期。
“本页通过三个维度建立客户信任”是给作者看的说明；对外页面应写出三个具体事实。单纯删除若干禁用词不能解决这类问题。

### 4.6 Planner 的差异化不足，问得过多

用户觉得前置规划像“拷问我的 Skill”。
核心问题：相较通用澄清工具或 gstack Office Hour，Deck Planner 到底有什么独有价值？
某些情况下 Office Hour 理解更通透、效果更好。
不能靠多一轮问答、多几份 JSON、多一个 Skill 名称证明差异。已有讨论与决定应被接收，不重新询问。

### 4.7 开源定位要求超越个人样例

如果只有用户自己使用，学习其历史方案可能足够；但开源项目必须服务其他用户，专业性和结构该如何设定？
不能把一个人的习惯推广为公共专业标准，也不能要求所有新用户先建设自己的知识库才能获得可用结果。

### 4.8 类型与场景的差异必须成为规划基础

用户最新补充：不同类型、不同场景的内容，结构存在明显差异。
不能只用“商业方案”一个标签覆盖全部材料，也不能把内容类型与使用场景混为一谈。

## 5. Codex 提出的候选方向：供你批判，不是已批准架构

1. 首轮可考虑聚焦解决方案售前、咨询顾问的客户材料；但具体支持类型与范围尚未确定。
2. 分开通用成稿要求、场景专业方法、企业/行业知识和个人表达偏好。
3. 从内容职责推导结构，再安排章节和页面，不使用唯一通用目录。
4. 类型、场景、受众分开建模：
   - 类型：公司能力介绍、产品介绍、客户方案、技术架构、研究决策、培训、投标应答等。
   - 场景：首次交流、已有合作、专项沟通、正式评审、已明确试点等。
   - 受众：高管、业务负责人、技术团队、执行人员等。
   这些是候选分类，不是首版承诺全支持，也不代表分类已严格成立。
5. 一份 Deck 可以混合公司介绍、业务方案、技术架构、案例和实施计划，需兼顾整套任务、章节职责与页面表达，避免互斥单选和模板组合爆炸。
6. 每个受支持类型可提供内容职责、典型组织方法及选择理由、质量要求、正反例。用陌生材料验证迁移，而非只复现作者范文。
7. 默认无需历史库即可工作；指定文件或本地资料即可增强。PPT Library 作为可选材料能力。
8. 对用户呈现的过程可收束为“理解材料与场景 → 编写完整方案 → 制作、审阅并修订成稿”。内部对象和工具不是每次都要用户操作的步骤。
9. 专业审阅应实际检查页面、提出具体修改并由系统完成可自行解决的返修，避免只产出报告和新门禁。
10. 从迭代定义、真实案例、现有结构取舍走到开发 Spec。已有 SC-1 需要重新对照，不自动整包继承。

## 6. 现在最需要讨论的八个问题

A. 公共专业性如何成立？
哪些属于跨用户可复用的方法，哪些必须依赖领域知识和机构资料？如何形成可信默认质量，而不是“专业、深入”等空泛提示？个人历史方案如何提炼为公共方法而不传播个人偏好？

B. 内容类型、场景、受众与复合 Deck 如何组织？
请提出一套足够小且能解释真实差异的分类与组合方法。说明哪些是主要维度，哪些只是修饰条件，怎样避免分类繁殖、固定模板和大量配置。哪些类型首轮值得支持，为什么？

C. 结构究竟如何生成？
从任务与材料到整体叙事、章节、逐页内容，模型承担什么判断，方法与代码承担什么？如何避免默认诊断、默认 CTA/POC、遗漏公司介绍，又不反向硬编码“所有 Deck 必须公司介绍开场”？

D. 与通用 Office Hour / 直接使用强模型的差异是什么？
哪些能力让 Deck Master 值得独立存在？哪些前置问题可以直接取消或复用已有讨论？哪些现有 Skill 应合并或仅作为内部工具？

E. 正文表达与专业审阅如何真正奏效？
怎样阻止制作语言进入正文，怎样发现“有结构无内容”、无依据结论、架构逻辑不成立、案例不支撑主张？如何让系统真正完成改稿，不再叠加签名、报告、门禁和用户审批负担？

F. 历史 PPT 怎样使用？
事实、知识、叙事、图、样式与整页分别怎样处理？RAG / 文件读取 / 页面提取在哪些条件下有价值？Deck Master 与 PPT Library 应保持怎样的边界？

G. 怎样验证“一次专业可用”而不要求用户做评测员？
公开样例、失败样例、专业审阅、当前产物检查和真实使用各自能说明什么？如何避免只测结构、模型自评自证，以及用用户最终放弃造成的“没有修改”误判成功？如何区分模型能力与产品方法的贡献？

H. 如何规划下一轮迭代？
提出一条能交付完整用户结果的顺序，说明保留、改造、合并、移出主链或删除的判断方法。避免提出一个新平台、行业插件市场或巨量 Spec 来解决此前的过度复杂。
