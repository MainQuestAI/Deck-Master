## 1. 目标与本轮范围

Deck Master 把已有讨论和资料转化为符合具体交流任务的完整、可编辑 Deck。首份完整稿应当允许用户进入正常业务审阅：讨论观点、方案选择和表达，而不是重建主线、补写核心内容或清理大批制作说明。

专业性同时包含事实可靠、观点有价值、机制讲得清、方案理由成立、内容详略适配，以及视觉表达完整。不能靠删除所有有判断力的内容获得“没有错误”的稿件。

优先形成能力/产品说明与方案/设计论证的成稿能力，冻结后的未见任务分别覆盖这两类核心承诺。材料驱动的研究简报保留为额外探路任务；若拟纳入公开承诺，另用冻结后的未见研究材料验证。公开资料核验和必要补充研究按任务需要进行；独立完成深度行业研究不纳入本轮核心承诺。

暂停新增历史整页混编投入。历史 PPT 继续作为事实、案例、业务图和表达参考；无历史库新建是正常路径。第一轮不建设类型配置平台、行业知识包注册机制、独立模型 Provider、新会话系统或新的审查服务。

以上为本次协作提出的执行建议，不把旧 SC-1 整包当成本轮已批准实施范围。

## 2. 实际运行方式

入口接收已有讨论、材料、当前任务与用户明确约束。资料足够时直接工作；只有缺失信息会改变核心方案、事实或商业承诺时，才提出具体问题。用户给了定稿直接制作；只要求局部修改就沿用既有方向。

宿主 Agent 连贯完成主编、编辑与生产职责。它先理解业务机制和本次受众要解决的问题，形成观点与方案判断，写出完整正文并安排图示；审阅后直接修订，再生产、读回和检查实际页面。图示或排版暴露内容问题时，回到对应正文调整，不另起一套用户审批流程。

局部改动按内容影响传播：文字偏好通常影响单页；案例数字、系统边界或方案选择发生变化，要检查引用这些内容的其他页面及整稿结论。未受影响的页面和既有用户决定保留。内部修订不设置机械的统一轮数门槛；有具体改进就继续，无新依据且没有实质改善时说明尚未解决的问题。

制作阶段新加或改写的标题、图表标签、补充分析同样进入语义审阅；不能因位于 scene、蓝图或 enrichment 中而绕过。实质文字修订同步更新受影响的引用、内容锁和下游消费，再读回真实成品。保留适合对外阅读的 business_implication，不把字段名本身当成需要删除的内容。

内容类型、场景、受众与呈现方式用于推导结构，而非要求用户填写分类表。允许典型结构作为参考，但整套 Deck 由一个共同交流任务组织，不能把五种小模板拼起来。

页数优先遵循用户明确要求；未指定时根据任务、内容复杂度、现场讲解/独立阅读等呈现条件安排。历史 12/15 页只能作为可选估算或旧稿解释，不能先填占位再裁剪论证。Agent 形成的结构不能被预算器、下游通用 beats 或 gate 改回固定目录。高密度是呈现选择，不是专业标准，不靠缩字塞满来满足页数。

| 任务示例 | 主线需要完成的内容 | 详略与结尾 |
| --- | --- | --- |
| 首次能力交流 | 企业是谁、擅长哪些任务、能力如何发挥、何种案例能够支持适配判断 | 公司与能力信息要充分；结尾可以总结适用任务，不默认推进 POC |
| 已有客户方案评审 | 当前目标与条件、推荐方案、关键机制、真实取舍、实施依赖 | 不重复已知公司介绍；结尾呈现本次实际需要判断的事项 |
| 材料驱动研究简报 | 核心发现、材料范围、分析理由、对业务的含义及建议 | 不把发现强行变成销售方案；重要限定在相关结论附近呈现 |

## 3. 公共内容方法的最小形态

首先在既有 Skill 的 references/playbooks 中落实以下方法，配套完整材料、成稿与具体返修示例。不是七个新阶段，也不要求每页出现对应字段。来源与简短设计依据服务于编辑和核验，不要求记录模型私有推理过程。

| 方法 | 可执行写法 | 反例 |
| --- | --- | --- |
| 判断交流任务 | 从已有信息确定对方已知什么、需要理解/选择什么、这份材料应提供哪些实质内容 | 所有首次交流都诊断痛点；所有结尾都启动试点 |
| 解释业务机制 | 说明参与者、触发条件、输入、动作、产出，以及哪里发生了有意义的业务变化 | “AI+数据+平台”即解决方案 |
| 形成观点 | 对照事实、目标和约束提出值得讨论的判断；区分事实、分析和建议；必要时补读来源或补充研究 | 复述资料即洞察；没有现成句子就不敢提出设计 |
| 选择方案 | 存在真实取舍时比较可行方案，说明关键选择依据及成立条件；不强制凑三个方案 | 先决定推荐项，再把其他选项写成明显不合理 |
| 组织整稿 | 让后续内容建立在前面已说明的信息上；把证据放在它真正支持的论点附近，按任务决定顺序和密度 | 公司介绍、案例、架构分别生成后拼接；同一案例重复三遍 |
| 写成页面 | 写出可直接呈现的标题、正文、表格与图中关系；选择最能说明问题的视觉表达 | “本页通过三个维度建立信任”；把标题换成“三大优势”就算修复 |
| 实际编辑 | 阅读完整稿、来源及实际页面，修正具体内容并检查影响；比较改前改后是否更好地完成任务 | 提交“建议增加说服力”的报告；扩大禁词表替代改稿 |

从个人优秀方案提炼公共方法时保留“为什么在这次任务中这样做”，并补充不适用条件。公开示例使用允许公开的材料或明确标记的合成材料；不把个人客户内容直接变成开源默认知识。

## 4. 工程减法与保留原则

一个检查或中间步骤只有能够对应具体用户结果，才值得留在生产主链。判断时同时用正确流程和错误情况验证：它保护了什么、误伤哪些正常任务、删除后是否出现真实损失。

保留原始材料定位、当前稿件版本与恢复、页面输入分离、实际文件读回、数字/图示语义保真和可编辑交付。把安装/发布核验放在相关操作中；不要每做一份 Deck 都重新运行发布治理。

固定目录、重复问答、无必要的重新确认、仅为满足状态而写的占位产物，以及只证明“存在某个字段/页型”的专业质量判断，按实际调用链改造或删除。保留既有用户授权和当前版本一致性，不通过伪造报告、复用过期批准或绕过真实阻塞来展示成功。

标准与高密度生产资产均保留。先选一条实际可用生产路径完成首批验证，明确当次路径；通用内容方法不得只存在于高密度分支。首轮是否覆盖另一条交付路径，必须以其真实构建/读回结果说明，不能从共享输入推断已验证。


## 5. 五个工作包与交付顺序

执行主体为维护者与实施 Agent。维护者准备适合使用的材料并安排业务阅稿；Agent 完成材料读取、方法与代码改动、制稿、返修和技术验证。用户只处理不可替代的业务决定，不承担填写评测表或补完创作的默认职责。

本轮提交此方案；以下工作包是后续实施路线，尚未执行。

### WP1｜建立成对任务、基线和兼容边界

- **输入：**同一家企业的能力/案例资料、具体客户任务资料，以及当前代码和候选旧 run。
- **产物：**D1/D2 共用来源包、两份简短任务说明、强模型直接成稿基线；实际可用的生产入口、首轮支持的宿主/生产路径/办公环境，以及代表性旧 run 兼容样本说明。固定旧 run 的已有产物、真实依赖与预期恢复动作，供 WP5 按同一基线复验。
- **完成动作：**材料由维护者整理，已有决策足以启动任务；关键内容能回到原文；明确恢复能力哪些经过运行、哪些只有代码依据。
- **失败去向：**缺材料则选择合适任务或补足必要输入；入口不清先核查实际调用链，不凭规格猜测可用性。

D1 是首次能力交流，D2 是已有客户方案评审。两者共用企业事实；场景确需不同资料时明确记录，不能偷偷给一个任务增加有利事实。

### WP2｜成对形成内容方法与完整稿

- **输入：**D1/D2、基线、已有 Skill 方法与已经可用的制作能力。
- **产物：**从 SC-1 选择性改写的精炼方法、两套完整正文、具体返修前后例，以及早期成品试做。
- **完成动作：**两稿都完成各自交流任务；能力说明提供具体可信内容，方案说明业务机制与真实选择理由；公司介绍、结尾、页数与深度随任务改变。正文已经写完，不能交页纲冒充。
- **失败去向：**观点空泛回到机制分析；结构雷同回到交流任务；来源错误回到材料。方法在宿主中无效时，先修方法，必要时做模型能力对照，不靠增加流程掩盖。

WP2 与 WP3 交错：发现固定目录或库依赖确实阻碍生产时，可先完成对应最小修复再继续试做，不要求两份完整 PPT 先成功才允许修接入。人工精修示范与系统原始输出分开保存。

### WP3｜修正必要接入并提前验证迁移

- **输入：**已经出现的具体失败、成对方法和本文件的实现入口核查。
- **产物：**按失败修复的最小补丁；可通过正常入口交付的 D1/D2；陌生企业方案 P1 的完整结果；旧 run 兼容检查。
- **改动重点：**原文实际使用、Agent 叙事被生产主链接受、无历史库新建、审阅后的改稿进入成品、所有可见文字使用对外表达。按下述成稿接入规则复用单 Run、import-plan、Page Package、既有 Builder 和局部修改能力；按 6.5 统一本地测试入口。
- **完成动作：**正常入口不会把 Agent 成稿覆盖回固定目录，不会因为未使用的历史库阻断；实际页面保留内容与图示语义；修改能进入当前版本；约定旧 run 可按原能力恢复。P1 在接入早期就运行。
- **失败去向：**新企业内容失败回 WP2；入口或文件失败修 WP3；旧 run 回归则缩小/撤回破坏性改动，保留原数据与有效路径。

必须核查完整影响，不能只修改参数或 Markdown：无库路径覆盖新建、sourcing、generation、next-step、所选生产路线所需能力检查与最终交付判定。并非列出的模块都要改，实际未依赖库的模块只需验证。

无库验收使用未安装、未配置历史库且没有历史检索缓存的环境，验证正常入口真实交付。指定少量历史 PPT 作为资料不因此引入 Library 安装前提；显式要求检索历史库时，则保留真实依赖与失败提示，不静默转无库。实际缺少 Builder、转换器等生产依赖仍按原因处理。

每个补丁附一个真实失败或必要兼容依据。方法已经足以解决的部分不增加代码。旧测试若固化了错误叙事或正常用户阻塞，应按用户结果改写，而非继续追求原预期全绿。

#### WP3 成稿接入与修改规则

采用现有 `import-plan --source agent` 的 JSON 导入路径作为结构接入基础，在同一入口扩展完整 Page Package 的接收与后续更新。以下是待实现的行为约定，不代表当前命令已经支持全文导入。`apply-narrative-advice` 继续承担已有页面的建议修改，不作为整稿入口；当前 Markdown 导入只提取标题并推断页型，保留为旧页纲兼容能力。用户提供 Markdown 定稿时，由宿主 Agent 读取完整内容并转换为下面的现有产物，不能经过标题提取器丢掉正文。

| 内容 | 使用的现有产物 | 采用规则 |
| --- | --- | --- |
| 页面集合、顺序及叙事职责 | `narrative_plan.json` 的 `beats` | 接收的 beats 数组确定当前页面集合和顺序；同步派生的 order，不再由通用模板重排 |
| 每页生产任务 | `page_tasks.json` | 从同一叙事生成或校验；与 beats 一一对应，保留 Agent 提供的论点、来源关联和生成要求 |
| 完整对外内容 | `page_packages/<page_id>.json` | 使用既有 Page Package：customer_visible、speaker_notes、visual_spec、asset_bindings、citations 及 claim/evidence 绑定；正文不再从 generation_brief 重新编造 |
| 下游制作输入 | 既有 sourcing/generation、build manifest 和所选路线的内容锁 | 只消费当前活跃页面及其版本；图示与排版可迭代，文字实质变化回写 Page Package 后再生产 |

JSON 整稿输入沿用已有 `narrative_plan`、可选 `page_tasks`，增加 `page_packages` 数组承载完整活跃页面，数组元素直接使用既有 Page Package 契约。没有该数组的旧输入仍按“导入规划”处理，不能报告为完整成稿已接收；新建与继续执行的 playbook 使用全文路径接收已经写完的稿件，不新增用户审批阶段。

导入和修改遵循以下规则：

1. **页面身份稳定。**新增页面建立唯一的 beat_id/page_id 对应，旧页面沿用已有对应；重排不重新编号 ID。整稿中的页面集合、任务和 Page Package 必须一致；缺页、重复 ID 或引用不到的目标返回具体原因，不静默跳过。整稿接收后，target_pages 反映实际页面数，不反向裁剪内容。
2. **一次接收一致内容。**先校验结构、完整正文及现有来源/资源引用，再沿用 `overrides` 备份受影响的规划和页面内容，只写入变化项。导入中断不得把半更新版本当成可继续制作的当前稿；恢复上一份一致输入或完成本次写入后，再继续生产。不新建版本服务或状态平台。
3. **继续生产沿用成稿。**已有完整 Page Package 的页面进入正常制作，不被当作缺正文重新生成。缺失的视觉资源可以继续生产。`next-step`、autoplan、预算器及所选 Builder 沿用已接收的页面和正文；仅用户任务或内容变化要求调整时才重做受影响规划，不按页序轮流重新分配 claim。
4. **增删重排进入实际成品。**新增页面进入任务和制作清单；删除页面退出当前页面、package index 与 build manifest，历史内容保留在备份中。不能扫描目录后把已删除页面重新带回成品。重排同步页面顺序和受影响的跨页表达，保留未变正文与可复用资产。
5. **修改后刷新相关下游。**正文、来源、图示关系或可见补充分析改变时，更新相应 Page Package、引用及所选路线的内容锁，刷新受影响的生成/制作/审阅状态。已修复 SVG 等有效资产按真实内容变化决定保留或重做；新 PPT 重新做文件级检查，旧报告不为新版本背书。

```text
已有讨论或完整定稿
  -> 宿主 Agent：完整正文、页面结构、图示与引用
  -> import-plan JSON：narrative_plan + page_tasks + page_packages
  -> 当前活跃页面 -> 必要资源生产 -> 所选 Builder -> 实际 PPT
                                           |
                 修改对应 Page Package <---+ 成品反馈
                       -> 更新受影响产物 -> 重新读回
```

接入验收在同一份完整稿上增加公司介绍页、删除一页、调整顺序，再正常生产和恢复；检查实际 PPT 的页面集合、正文、备注、图示关系与引用。另验证导入中断可恢复、已有页面不会无故重新生成。检查对象是完整交付物，不能只断言 `imported` 状态。

### WP4｜冻结候选版，验证未见任务

- **输入：**冻结的方法、代码、模型设置、工具权限，以及未用于调试的 H1/H2。
- **产物：**H1 陌生企业能力/产品说明、H2 陌生客户方案/设计评审；公平对照完整稿；原始输出、实际 PPT、成品检查及必要修订记录。
- **完成动作：**按第一次系统完整交付评估，不挑最好一次；来源、模型配置和方法版本可对应；H1 能说明可信能力及适用任务，H2 能说明推荐方案、业务机制、真实取舍和成立条件。至少一份开发或探路任务保留真实任务所需的完整复合长度，不能全部压成三页演示。
- **失败去向：**用于修方法的 H1/H2 转成回归材料；修复后另选未见材料验证，或收窄公开结论。不能原题修好后继续叫未见通过。

P1 在使用后同样成为开发材料。合成任务可以启动验证，但结果只证明在该合成任务上的表现，不能包装成真实客户接受度。

研究简报作为额外探路项，检查材料发现、分析理由和业务含义，不默认导向采购或 POC。拟将该类型纳入公开范围时，使用未参加探路/调试的研究材料单独验证；它不替代 H2，也不列入下述核心五任务的固定起点。

### WP5｜专业阅稿、实际编辑和范围收口

- **输入：**完整对照稿、原始来源、实际成品、已知问题及兼容结果。
- **产物：**轻量阅稿结论、可复现的交付检查、候选安装产物及开源使用说明；允许公开的完整样例、安装入口和已验证范围。
- **完成动作：**拟宣称专业可用的场景，由具有相关交付或使用经验且未参与本次成稿的人类阅稿者检查；在目标办公环境实际编辑关键文字和关键图示关系；更新一个跨页条件并恢复约定旧 run；完成下面的安装后无库真实交付。
- **失败去向：**实质重写回 WP2；文件、编辑或恢复失败回 WP3；没有合格业务阅稿时可完成方法与工程试行，专业业务可用证据仍未完成。

依赖关系：WP1 → WP2 与 WP3 交错 → WP4 → WP5。业务阅稿可尽早介入试稿，并在最终范围收口使用冻结结果；不能直到最后才发现全部稿件需要重写。

安装后验收复用 `release-build` 和 `release-smoke`：从候选代码生成新的 release tree，并在隔离的安装目标使用 WP1 选定宿主的 Skill/CLI。至少一次无库真实交付从此入口完成，采用允许公开的完整样例；所需方法、示例和脚本全部来自该候选产物，不借开发 checkout 的路径补齐。确认生成后的能力清单、Skill 指令和所选路线依赖一致；Library 未安装、未配置且无检索缓存时正常制稿，显式请求 Library 时仍按真实依赖处理。无需扩展到所有宿主或另一条生产路线。

`release-smoke` 通过与上述真实制稿分别记录。安装包能启动不代表正文、图示和编辑效果已通过；实际制作、读回和办公软件编辑仍按 6.4 验收。方法或依赖行为改变后只重做受影响验证，不把整套发布核验塞回每次制稿主链。候选包可以在本地验收，公开发布另按当时明确授权执行。

## 6. 轻量验证方案

### 6.1 五个任务的用途

| 任务 | 用途 | 为什么需要 |
| --- | --- | --- |
| D1 / D2 | 同源材料、不同交流场景的成对开发 | 防止方法只学会首次交流或售前模板 |
| P1 | 陌生企业、不同业务机制，提前试做 | 在最小接入过程中尽早发现过拟合 |
| H1 | 冻结后未见的能力/产品说明 | 检查公共方法能否迁移企业与资料组织方式 |
| H2 | 冻结后未见的客户方案/设计评审 | 检查核心方案能力能否迁移到不同业务机制与约束 |

这是核心五任务的务实起点，不是统计稳定性证明，也不是运行时硬性配额。研究简报按 WP4 的额外探路规则处理。维护者选择允许使用的材料；普通用户不必为产品提供五套材料。

### 6.2 对照分阶段安排

A：同一强模型、同样资料与明确任务，有合理的原文回看、自查和返修机会。\\
B：A 加公共内容方法，不增加完整内部编排。\\
C：同一模型与输入进入候选工作流，包括编辑、生产和成品反馈。

D1/D2 先做 A/B，接入后补 C；P1 先完整 C；H1/H2 先比较 A/C。方法与编排的归因有争议时，再补对应 B。这个起点约 11 份完整输出，但不把数量作为完成门槛，不为凑数重复已经足以回答问题的运行。

D1/D2 只能说明开发样本上的增量；H1/H2 的 A/C 只能比较整体候选，不能单独证明公共方法的泛化收益。复用旧输出仅限该次对照的模型与推理设置、来源版本、任务、适用的方法版本、相关实现版本、工具权限、自查机会及人工介入记录相符；设置变化不能拼接成同一次比较。

各条件使用独立会话，共享同样的业务背景，不继承另一组的答案或点评。WP2 探索稿与冻结候选结果分开；方法/实现变化后，不用旧 B 和新 C 作最终归因，只补跑受影响条件。保持合理可比的自查机会，但不要求 A/B/C 内部编排完全相同。H1/H2 在冻结验证前不进入方法示例或定向调试。

公共方法不可夹带评测任务答案或精修范文。C 内部如果换用更强模型、更多资源或外部人工意见，要明确其贡献，不能全部归因于流程。内容比较使用统一且不改写内容的版式；流程效果另看真实交付物与实际编辑。比较版不能替代 PPTX 验收。

首稿是系统第一次交给用户的整份稿件，允许此前的自主审阅和返修；收到用户/外部阅稿反馈后的修改不能倒算进首稿。

### 6.3 阅稿与结果记录

阅稿者获得任务说明、必要来源和匿名、随机顺序的完整稿。只记录结论、关键页面和实质理由：

| 结论 | 判定 |
| --- | --- |
| 可以进入正常业务审阅 | 主线、实质内容和必要判断成立，后续修改不需要替系统重新创作 |
| 需要实质重写 | 主线、关键机制、方案理由、事实或大量正文需要重做 |
| 未完成本次任务 | 核心内容或必要资料仍缺，无法完成本次理解或判断任务 |

正确但空泛的稿件不能仅因没有事实错误判为可用。说明型材料不强制比较方案，研究型材料不强制销售行动；看本次任务真正需要的信息与判断。

普通表格记录任务、条件、版本、完整输出位置、人工介入、阅稿来源、结论及失败页即可。内部专业意见、外部专业阅稿、客户实际采用、模型审阅、工程检查分别陈述，不合并成一个“通过”。无人反馈记未知。没有合格的人类专业阅稿，不阻止工程试行，但不得声称专业业务价值已经证明。

### 6.4 必须做的行为验证

1. **资料理解：**把会改变方案的条件置于来源后段，检查它是否真正改变相关推荐、流程或图示；必要时用只改变该条件的成对输入核验。正文提到该约束或日志显示读取均不充分。没有 risk_flags 不代表证据充分，存在引用也不自动充分；合理推理与设计建议按机制、条件和理由审阅。
2. **场景与结构：**同源首次交流和已有客户评审形成实质不同的内容；短简报不因默认页数被填充；封面、章节页不承担正文证据与密度要求。
3. **无库生产：**在未安装、未配置、无历史检索缓存的环境，从正常入口完成真实生产；不等待候选页，不调用未使用的库，不生成 Fixture 成绩，也不借“允许降级”绕过实际依赖。另检查显式请求历史库时的真实依赖与失败行为。
4. **正文与可见文字：**检查标题、正文、图内标签、表格、页脚、实际讲者备注和高密度补充文字；内部文字不能仅换成另一种空泛话术。用真实生产页面验证，不能用 fixture 路径代替。
5. **文件与编辑：**读完整成品；在目标 PowerPoint/WPS 等实际环境中编辑关键文字与图示关系，确认语义、对象和排版；库能提取文本不等于编辑体验已通过。
6. **成稿接入、更新与恢复：**按 WP3 接收完整正文，增加公司介绍页、删除一页并重排，核对实际 PPT；未知页面不能被忽略，已删除页面不能从旧目录重新带回。变更一个影响多页的事实/设计条件，检查所有相关内容更新、无关页面保留，旧批准版本可找回；验证导入中断恢复，并按 WP1 基线实际恢复代表性旧 run，不重排叙事、覆盖正文或引入无关安装/发布/检索。真实外部依赖缺失时说明具体缺口。新产物刷新文件级检查，旧报告不能为新版本背书；未运行的另一条生产路线仅声明保留资产或静态核查。
7. **安装后交付：**按 WP5 在候选包的已安装 Skill/CLI 中完成同一公开样例的无库真实生产；核对实际使用的方法版本、依赖判定、PPT 内容与可编辑性，不用源码入口或仅 release-smoke 结果替代。

需要因行为改变编写的测试应覆盖上述真实失败与兼容性；不为文档措辞编写测试，不以检查模板关键词替代语义质量。完成相称检查后收口，只有新失败或未解决疑点才扩大。

若 B 有效而 C 没有额外内容增量，保留方法，将 C 的价值限定到有证据的生产、修改和恢复；若 C 只有更多操作，删去无增量编排。任何关键错误或核心内容缺失都不能被平均分抵消。不同模型与不同生产路线的能力分别说明，不泛化未经验证范围。

## 7. 方法示例：观点必须改变对业务的理解

以下材料完全合成，只用于说明方法，不是客户事实、系统运行结果或独立验证样本。

企业提供资料接入、引用问答、权限与门户集成；一个历史项目完成了手册/工单接入和上线培训，没有效果数字。客户售后判断依赖设备型号与版本，但当前门户不要求填写版本。120 条互斥分类的记录中，36 条信息齐全可按资料处理，54 条需先补问版本或批次，30 条信息齐全仍需专家判断。门户支持加字段和展示查询结果，工单本期只读。

由这些资料可以形成设计建议：优先把设备条件收集前移到服务点提交时，并为专家准备完整问题上下文。不能推断 54 条都会被自动解决，也不能推断效率提升比例。若现场根本无法获得设备条件，应改为设备识别/现场信息采集方案；增加字段不一定有效。

这不是“做知识库”的资料复述，而是一个能够改变建设优先级的建议。下面是连续三页的对外正文示例，实际稿件可采用表格或流程呈现。

**页面一：让产品知识进入一线售后工作流**

我们提供技术资料接入、引用问答与业务系统集成服务，把设备手册和维修记录接入服务人员日常使用的工作入口。统一查询帮助定位资料；引用位置帮助回到原文核对适用条件；企业身份与权限对接让应用沿用现有访问体系。

在设备维修知识应用项目中，我们承担了手册与维修工单接入、权限对接、引用问答界面及上线培训。这些交付经验可以用于资料、权限与服务入口的协同建设。

**页面二：把设备条件收集前移，减少总部接单后的重复补问**

当前服务判断依赖型号、版本或批次。120 条记录中，54 条首次处理需要补问版本或批次；36 条信息齐全可按现有资料处理；另有 30 条仍需专家判断。

仅增加资料搜索入口，会保留提交后再补问的流程。建议在服务点提交问题时提示补齐设备条件，让总部收到包含设备信息、问题现象和候选资料的完整问题包。54 条补问记录支持优先改善这一环节，不代表这些问题都能自动解决。

**页面三：在现有门户中连接条件补齐、引用问答与专家接力**

资料搜索增强可以改善查询，流程改动较少，但设备条件仍按原流程补充。门户内的条件补齐与引用助手，能把补问前移，并按资料适用范围展示引用；相应需要新增设备字段、适用范围映射和补问交互。

建议采用第二种方式：服务点提交设备与问题信息，系统提示补齐缺失条件，检索并展示适用资料；需要进一步判断的问题附完整摘要转交专家。工单接口按本期约定只读，摘要在现有流程中使用。

验证关注首次信息完整度、专家重复补问次数以及引用资料与设备版本的适配性。已有资料与权限集成经验支持接入部分，设备条件映射与转交体验属于本期新增设计。

这三页在首次能力交流中连接能力、客户任务与适配建议。已有客户方案评审应压缩公司介绍，围绕推荐选择、条件映射和实施内容展开；不能只换标题，也不必把边界再单独扩成一页。
