# 开发任务卡｜Deck Master 主流程重建 v1.1

**25 张开发任务卡、126 个卡内实施步骤，覆盖原实施清单的全部 90 条验收行为。**这是一份开发执行输入；全部任务保持待开发，未把环境清理、文档校验或历史测试计为新核心实现完成。

拆分基线：`codex/rebuild-mainline-v1@61d43a111284c8ab9254f85dc8f7191ee4670928`；产品实现取用来源仍为原 Spec 的 B0/K0 固定 SHA。开始开发时核对当前 checkout 的增量，不 reset 到文档 SHA。当前任务只拆卡，不实施代码、不激活安装、不创建外部任务。

## 怎么使用

1. 在下方选择一个任务，先读卡里的依赖、接口、输入和验收。现有 [实施清单](../IMPLEMENTATION_CHECKLIST.md)、[task-list](../inventory/task-list.json)、[正式 Spec](../MASTER_IMPLEMENTATION_SPEC.md)继续定义总范围；任务卡是其操作化拆解。
2. 以整卡为领取单位，卡内步骤不声称可独立派发。提前交接按[阶段交接与验证](handoffs.md)的输入、输出和接线责任执行；整卡完成仍须满足 `depends_on`。
3. 交付代码、相称的测试、真实产物或操作证据，并回填卡末交接。`min` 是开发中的早期切片，不是新增产品模式、运行阶段或独立永久契约。
4. 卡中 `<候选Python>` 替换为实际候选解释器绝对路径。拟建测试在实施后执行；只读文档校验不能代替产品测试。需要实际阅图、模型运行、浏览器或人类操作的项目另外留证。
5. 普通设计取舍已有 Spec 决定，不把每张卡变成用户审批节点。安装/发布沿用会话已有授权；缺对应授权时先交可验证候选，再明确实际需要的最后一步。

文件入口：[任务卡机读索引](tasks.json) · [子任务 CSV](subtasks.csv) · [完整验收矩阵](../inventory/acceptance-matrix.csv)。JSON/CSV 是本次拆分的导出快照；后续增改子任务同步更新卡和索引，产品完成度以实际回填证据为准。

## 验收归属和完成记录

每条 AC 的最终负责人来自原 `acceptance-matrix.task_id`；任务清单中其他卡引用该 AC 是早期或接线验证。例如 T05 先让页列表可见，但 AC-U01 最终由 T14 关闭；T05/T16 先查资源，AC-I06 由 T20 的无源码安装闭环关闭。**90 条 AC 均有且仅有一个最终主责卡**，不能多个任务互相引用就当已验收。

- 工程行为：可重复的正例、真实失败反例与故障注入；说明执行命令与输入版本。
- 内容/视觉行为：实际Host读资料、读图、看SVG/PPT及具体观察；接口正确或marker命中不证明内容专业。
- 独立复核：只有实际不同执行者完成复核才按实况记录；改reviewer名称不是独立证据。
- 人类专业与桌面编辑：保留真实反馈、目标应用与保存重开结果；缺失时标未验证。可以交工程试行，但不能回填专业通过。
- 产品完成说明：对应实际当前版本，保留失败/旧版；首稿和人工/Host精修结果分别保存。

默认每张卡为一个可审查开发单元，可分小提交；几何修复可独立提交。5个WP是最终归组，早期交错切片可以跨WP先提交，不为了凑一个巨型PR推迟真实链路验收。本轮没有创建PR或外部项目管理任务。
