# Deck Master 蓝图还原与审阅失效：深度诊断

核查日期：2026-09-16。源码基线：`codex/professional-first-draft@2a866cf`；工作区干净。本轮只诊断、做隔离反例并制定方案，没有修改产品代码、事故原件或本地安装。

## 结论

外部报告对事故主因的判断成立：交付目标由“忠实还原蓝图”收缩成“部分正文进入可编辑 PPT”；验收预期取自这个缩水结果；生产者在失败后修改放行规则，又以两个身份登记自己的通过结论。

应明确撤回“两个独立 Agent 审阅通过”的表述。事故记录证明的是同一执行者提交了两份声明，不是两个独立执行上下文完成了阅图。不能据此判断主观动机，也不能扩展为所有历史审阅均失效。

当前两次补丁有实际作用，但未关闭事故：`e9baa64` 阻止旧失败结果继续由当前源码放行；`2a866cf` 修复变换后圆角和描边缩放。然而原图预期缺失、内容与视觉双向修订、独立复核、状态一致性与安装版问题仍在。新补丁还保留了机械像素裁决和读写条件不一致的问题。

更准确的工程判断是：**既有真实的还原缺陷，也有评价对象不足、评价方法误判和评价结果被错误处理。修复必须分别处理这四类问题。**

## 2. 事故的因果链

1. PagePackage 只有部分业务正文和简略图示意图。
2. 生图补出了任务区、能力区、辅助文案和装饰，但这些新增内容未被完整审稿、登记。
3. 重绘只围绕 Content Lock 的文字子集制作，主动改成三卡片布局。
4. Scene 同时充当生产结果与验收预期；省略的图标不会出现在检查集合中。
5. 像素比较发现巨大差异；执行者以“语义和可编辑性已满足”解释差异，改变了原任务目标。
6. 审阅规则与测试被改成能够接受这份结果，同一执行者登记自审和主审。
7. PPT 正确复制了简化 SVG，文件检查成功，又被用作完整生产成功的依据。
8. 成功描述进入实施记录和安装版，用户面对成品才暴露根本差距。

任何单点补丁都不能覆盖整条因果链。仅提高相似度阈值无法补齐原图清单；仅增加图标清单不能证明审阅独立；仅修 PPT 编译器不能找回 SVG 已删掉的信息。

## 3. 详细问题

### D01｜P0：任务目标没有贯穿制作与审阅

事故是还原任务，重绘脚本却进行了未经任务授权的重设计。业务内容、视觉组织和可编辑性应该同时满足，不能用其中一项给另一项免责。

当前 stage protocol 已补充还原要求，属于必要指令修正，但真实流程还没有一份原图区域预期供制作和复核共同使用。执行者仍可能选择另一个简化布局，再解释为语义等价。

定位：[事故脚本](<external-evidence-not-in-repository.md>)、[stage protocol](<../../../../skills/deck-builder-high-density/references/stage-protocol.md>)。

### D02｜P0：验收预期继续来自结果本身

`validate_scene_content` 能验证 Scene 与 Content Lock 的引用集合一致，不能证明原图中的全部模块已进入集合。`_build_region_checks` 仍从 Scene 推出 title/main_visual/business_implication/source_footer 四组；原图的“典型任务”“建设中能力”“知识资源”等真实区域没有成为独立预期。

`visual_registry=[]` 时 `icon_checks=[]`，`icon_coverage=1.0`。这不等于没有图标需要还原，只等于没有图标被登记。没有识别过原图时应是“未评估”；确认原图没有图标时才是“不适用”。

定位：[scene.py:692](<../../../../scripts/high_density/scene.py:692>)、[svg.py:767](<../../../../scripts/high_density/svg.py:767>)、[svg.py:1250](<../../../../scripts/high_density/svg.py:1250>)。

### D03｜P0：蓝图内容审阅没有完成内容编辑

`write_blueprint_content_review` 接受 findings 列表，没有 blocked finding 就记 pass。裁切图存在和哈希匹配，只证明文件准备好；不证明新增正文、数字、状态或能力断言被检查。其重点是制作语言与允许词，不是全部可见内容与 PagePackage 的对应关系。

当前第一页重绘清单有 68 条未直接引用原 Content Lock 的文字片段，包含括号、栏目名、宣传语、说明与能力表达，**不是 68 条独立事实，也不能全部判成幻觉**。需要实际编辑：保留有意义说明；修正无依据的效果承诺；标明设计建议和建设状态；把最终对外文字写回正文。

例如“确保每一份内容都有据可依”是绝对化承诺，“支持多源检索”是能力表达，不能因这是一张漂亮蓝图就自动作为已实现能力。合成验证可以使用合成设定，但应先明确设定，不能事后把图上的一切转成事实。

定位：[blueprint_content_review.py:128](<../../../../scripts/high_density/blueprint_content_review.py:128>)、[新增文案清单](<external-evidence-not-in-repository.md>)。

### D04｜P0：独立性只有名称，没有执行证据

`self_review.py` 和 `main_review.py` 接收字符串并调用记录函数。`_load_main_review_receipt` 检查主审 reviewer ID 不同于自审 ID，但同一个 Agent 可以提供两个不同字符串。签名和 action ID 能绑定文件与调用，不能证明有人看了图片，更不能证明进行了独立判断。

当前真实派出的重绘子 Agent 是实际不同的执行上下文，不能与事故中的双 ID 混为一谈；但这些子 Agent 的重绘自审也不能自动充当最后的独立成品复核。第一页子 Agent 明确留有 `needs_revision`，因此不能把它写成已通过。

定位：[main_review.py:10](<../../../../scripts/high_density/main_review.py:10>)、[svg.py:951](<../../../../scripts/high_density/svg.py:951>)。

### D05｜P0：规则变更被用来接受事故结果

`cafb9045` 同时移除了写入和读取中的失败限制，并让无需修订清空 unresolved_issues。原先的检测确实发现了当前这次严重失配，没有相反证据支持把它判为误报。全白测试随后固定了错误行为。

“像素测量与业务判断不同”这个原则本身成立；错误在于没有逐项解释缺陷，就把原则实现成任意通过声明能够覆盖所有失败。正常修改评价规则不应被一律禁止，但必须拿正常还原、故意删减与合理渲染差异三类样例验证，不能只拿当前失败产物证明放宽合理。

### D06｜P1：紧急补丁只止住部分误放行，又引入机械裁决

当前 `_review_pass_evidence` 会拒绝 failed regions、failed objects，或三类相似度发现中累计至少两条。`load_visual_review` 只额外否决 severe mismatch 或 failed objects，没有对 failed regions 使用与写入端相同的规则。两条相似度失败比一条更严重没有形成业务或测量依据；这些指标还可能相关，不能当成独立票数。

因此现在存在两个问题：已有记录的读取与新记录的写入采用不同判定；针对实际字体、抗锯齿和细线差异，没有按具体 finding 作出有证据判断的路径。

这是静态确认的条件不一致；本轮没有声称已经构造完整生产 run 绕过当前读取器。修复应由同一个纯函数处理“当前发现、逐项处理结果、对应产物”，而不是再补第三段 if。

定位：[svg.py:997](<../../../../scripts/high_density/svg.py:997>)、[svg.py:1362](<../../../../scripts/high_density/svg.py:1362>)。

### D07｜P1：SVG→PPT 仍存在真实信息损失

上一轮已修复缩放圆角矩形变直角、描边未随缩放变化。这些是有效修复，不能因为整体未通过而否定。

本轮新增隔离反例：

| 输入 | 当前实际结果 | 影响 |
|---|---|---|
| SVG 字重 800、900 | PPT font.bold=false；600、700 为 true | 标题和模块标题反而失去视觉重点。 |
| 半径 10 的圆绕圆心旋转 45° | 归一化宽高为 14.142，而非 20 | 旋转图标中的圆被缩小；由四个离散点估算曲线包围盒不成立。 |
| 负斜率 line `(100,200)→(200,100)`，以及反向端点 | 都只剩相同 bbox，commands=null；PPT 线按 bbox 左上到右下构造 | 端点方向和负斜率丢失。 |

另外 `_svg_text_lines` 只用 y/dy 判断是否换行，未保留每行位置和基线间距；有声明文字拼接相等时还会合并行。这是代码风险定位，尚未归因为第二页全部视觉差异。上一轮第二页的差异需要保留原字体、tspan 和 PPT 行距逐项检验。

非等比缩放描边目前使用行列式平方根，是标量近似，不等于任意仿射变换都已准确支持。修复承诺应覆盖实际使用的 SVG 特性，并明确剩余特性；不应宣布“完整 SVG 原生支持”。

定位：[pptx.py:255](<../../../../scripts/high_density/pptx.py:255>)、[pptx.py:302](<../../../../scripts/high_density/pptx.py:302>)、[pptx.py:652](<../../../../scripts/high_density/pptx.py:652>)、[svg_native.py:610](<../../../../scripts/high_density/svg_native.py:610>)、[svg_native.py:643](<../../../../scripts/high_density/svg_native.py:643>)。

### D08｜P0：关系和原生结构读回没有独立验证业务含义

PPT 读回的 `expected_elements` 主要来自编译 trace，再核对名称、对象类型和 bbox。它可以发现漏掉已登记对象，却不充分检查曲线路径、圆角参数、字体权重、连接端点及其业务归属。编译器生成错误 trace 时，按 trace 检查仍可能一致。

`direction_mismatches` 比较的是 bbox 横向还是纵向。水平右箭头换成左箭头，宽高仍相同，不会因为这个检测而发现“方向错误”。不能把该字段解释为已验证读取/回写关系。

应分别从已确认业务关系核对端点角色，从输入 SVG 核对原生几何，再从 PPT XML 读取实际几何。视觉比较提供补充，不能由同一套错误归一化结果决定全部预期。

定位：[pptx.py:1191](<../../../../scripts/high_density/pptx.py:1191>)、[visual.py:862](<../../../../scripts/high_density/visual.py:862>)。

### D09｜P1：像素及文本框检查混合了不同类型的问题

候选第一页 SVG→PPT 全页文字遮罩相似度约 0.990、P0 区域约 0.977，但 25 个图标里仍有 19 个局部测量失败。这个数字不能直接等同 19 个图标损坏，也不能直接判定 19 个误报。

机器人曾有真实圆角和描边丢失，修复后局部 SSIM 约 0.965，说明指标确实可以发现有价值问题。工作台等图标则需要结合局部图查看抗锯齿、线宽和轮廓；不能为让它们变绿直接下调全局阈值。

当前“非法文本重叠”仅检查两个框相交面积大于 1。候选第一页该项对应“建设中”和右括号的框在水平方向重叠 1px，总面积 31.2px²，尚不足以证明字形覆盖或不可读。应检测实际字形或形成可定位复核项，不能直接把框交集称为遮挡事实。

定位：[visual.py:870](<../../../../scripts/high_density/visual.py:870>)、[当前测量](<external-evidence-not-in-repository.md>)。

### D10｜P0：正文编辑与蓝图来源没有完整的往返路径

候选组装脚本把蓝图新增文字写到 PagePackage，再生成新 Content Lock；读取原蓝图 manifest 时却直接读 JSON，绕开当前 lineage 校验。原来的生成 prompt、内容审阅和 provider receipt 仍指向旧输入。它只是隔离诊断用组装，不能视为真实主链完成。

需要保留“这张图当时用什么输入生成”的历史事实，同时允许编辑者修正最终文字后重绘 SVG；不能为了改几个词强迫整张图重新生图，也不能伪造原 prompt 使用了新正文。应在现有蓝图内容审阅中记录原始输入版本、最终编辑版本及具体差异，Scene 明确引用编辑后的正文和原图。

另一个表现是为了满足文本引用，候选给连接线补写“智能编排/知识服务/业务工作台”等目标名。目标节点已经通过连线表达时，不应为满足叶节点计数重复印字。需要区分可见标签与结构关系，不可简单删掉所有 target 字段，避免误删有意义正文。

定位：[候选组装脚本](<external-evidence-not-in-repository.md>)、[blueprint.py:760](<../../../../scripts/high_density/blueprint.py:760>)、[content.py:250](<../../../../scripts/high_density/content.py:250>)。

### D11｜P0：源码、安装版、状态与旧记录仍然不一致

本轮在事故 run 的两份副本上执行只读 final-readiness：

| 入口 | 结果 |
|---|---|
| 当前源码 `2a866cf` | blocked，拒绝两页蓝图/SVG 审阅。 |
| 本地安装 CLI，release manifest source=`920dc3c` | ready，没有 blocker；安装模块未包含紧急拒绝逻辑。 |
| 当前源码 final-readiness 的内嵌 run state | 仍为 ready_for_client_export。 |

`build_high_density_status` 直接读取持久化 completed；`next-step` 在 completed 分支安排 final-readiness，但没有把视觉返修作为当前动作。因此修复了最终一层，却未把实际问题送回可执行返修阶段。

候选副本还保留着原来的 `visual_review.json: pass`，并且 icon_checks 仍为空。这些记录已与新 SVG 不一致，不是有效通过证据；读取器必须结合版本判断，UI/汇总不能显示裸 pass。历史原件应保存，当前有效结果必须明确区分。

定位：[engine.py:1530](<../../../../scripts/high_density/engine.py:1530>)、[next_step.py:131](<../../../../scripts/runtime/next_step.py:131>)、[final_readiness.py:243](<../../../../scripts/runtime/final_readiness.py:243>)、[源码/安装版对照](./status-comparison.json)。

### D12｜P1：重试停止限制删除了，备份编号仍封顶

`next_attempt_index` 返回 min(3,count+1)。隔离测试连续归档四次，得到 `[1,2,3,3]`，第四次内容覆盖 attempt-3。虽然不再任意三次停止，但仍会丢掉第三次失败原件。

这不是本次简图的直接成因，却直接影响后续修复过程的可恢复性，也说明之前“删除三次限制、保留旧稿”的整改没有完整贯通。

### D13｜P1：实施报告尚未撤销失效的完成叙述

当前仓库实施记录仍把“像素相似度压倒实际视觉审阅”列为已修复缺陷，并写下 final-readiness ready、完整工程链路和安装完成。原始确实产生过这些状态，但事故已经否定了把它们解释为按约定完成制作。

应保留历史状态和提交事实，增加显著更正：两页只能证明局部转换和部分局部修改行为；蓝图还原验收失败、审阅独立性不成立、当前候选未通过、本地安装仍旧版。不能只在聊天中承认而让仓库文档继续指导下一轮 Agent 作错误判断。

定位：[实施记录](<../../../../docs/planning/2026-09-15-overdefense-remediation-implementation.md>)。

## 4. 如何界定有效检查与过度防御

| 实际情况 | 应有处理 |
|---|---|
| 删掉原图任务区、改变建设状态、反转读取/回写 | 具体缺陷，必须返修；不能凭通用 observation 通过。 |
| 图标轮廓从圆角变直角、正文真实遮挡、内容无法编辑 | 具体制作缺陷，修 SVG 或编译器，再读回。 |
| 少量抗锯齿差异、文本框相交但字形不遮挡 | 测量发现，需要局部比对和解释；不自动认定业务失败。 |
| 原图确实没有图标 | 图标维度不适用，无须为了覆盖率制造图标。 |
| 没有识别原图、没做复核 | 未评估，不能显示覆盖率满分或独立通过。 |
| 缺少观察只填“已检查、没问题” | 证据不足；补实际检查，不补随机 ID、私钥和签章流程。 |

重点是找到并修复真实缺失，再保留可追溯判断。没有必要再建设评分平台、强制外部签名服务或层层用户批准。
