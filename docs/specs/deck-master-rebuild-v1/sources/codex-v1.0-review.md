# Deck Master Rebuild Spec v1.0 审查

来源：用户在本对话转交的 Codex 报告。以下核查归属于该报告，不是本次修订重新运行仓库所得。本轮修订只对已有v1.0包进行文档与合成示例校验。

结论：认可主流程重建与资产提取方向，建议修订为 v1.1 后作为实施基线。文档已经足以确定范围，但不应把每项接口都视为已闭合。此次仅审查，没有实施、删除或安装。

## 核查范围与结果

阅读 ChatGPT 最近的重建判断与完整 Spec 交付说明，审阅 ZIP 的 15 章规格、五类合同及任务表；核对当前 Git HEAD 为 2a866cf138f6359f853db35e0a926ad79391b691，工作区干净。
70 条 FILES.sha256 全部一致；5 份 Draft202012 Schema 与对应示例均通过。旧 scripts 清单 177 项、旧 contracts 清单 58 项与当前跟踪路径完全一致。任务依赖图检查发现 T13 未进入 T25 的祖先集合。
这是文档与映射核验，未运行新产品、编译器、安装或业务验收。未逐函数复核 177 个文件的迁移可用性。

## 认可的主要决策

- 同仓 src/deck_master 建新核心，切换后只有一个默认主流程；不整包合并 PR31。
- Host 负责完整正文与场景判断，规则 Planner 和循环配 claim 退出正式生产。
- SVG 为唯一手写视觉源，IR 派生；原文和原图保留独立预期。
- Document 决定当前页集合；CLI/UI/出口读取同一事实；任务进度、制作完成、检查和人类认可分开。
- PPT Master、Library 不再参与正常新建或安装就绪；公开 Skill 收敛为一个。
- 保留版本和原子写入，但不继承旧九阶段、评分和审批平台。
- 删除顺序为停止调用、停止发行、验证替代后删源码；保留用户材料与事故原件。

## 需要修订的条目

### R1 / P1：未知来源哈希与旧资料导入相冲突

03.2 允许未知为 null 或缺省，12.2 明确没原文就记未知；但 document.v1.schema.json:99、149 把 original_sha256 设为必填的 64 位字符串。本轮将合成来源该值改为 null，验证实际拒绝。

影响：有旧 PPT、正文和图片但原资料已不可达的合法导入会被格式卡住，或诱导实现填写假哈希。

修订：允许未知原文件哈希；区分已保存提取文本/媒体的真实哈希与未核实的原文件哈希。已有媒体查看不依赖原文重新出现，涉及证据复核时才明确缺口。加入缺源导入反例，不以全零哈希或对 URI 求哈希代替。

### R2 / P1：画布、样式与允许资产缺少可恢复的权威入口

05.1 的 prompt 需要 style、语言、画布与允许资产；06.1 的编译需要 canvas、slide_size、字体和资产映射；08.3 要按全局字体/样式变化失效。当前 Document 无对应配置，Page 只有 string 类型 style_ref；它如何解析、版本化、导入、重定位没有确定，Artifact 角色也没有通用素材入口。

这不是要求增加平台，而是需要规定上述真实制作输入放在哪里。否则 Host、编译器、UI 可能再次各用默认值，项目移动后丢字体/图标/Logo，缓存无法判断有效性。

修订：在现有 Document 中定义最小 design_context，或一个明确引用的版本化制作配置文件，固定画布、字体选择、样式及允许资产 ID/ref；Page 可做明确覆盖。详细规定 style_ref 与素材路径解析和依赖计算。只增加实际消费的字段。验收含非 16:9、指定字体/Logo、移动项目、只改样式。

### R3 / P1：任务依赖遗漏和调用额度的执行边界

实际 task-list 图中，T25 依赖所有其他任务，唯独不依赖 T13。T13 负责历史重试和真实外部调用限额，其 AC-S11/S12 可在最终任务依赖全部完成时仍未执行。

修订：让 T25 或合适的安装验收任务明确依赖 T13。同时区分 T01 的“建立退役清单”和 T24 的“退役引用归零”，不要把同一 AC-L05 的最终完成要求提前交给 T01。

此外，08.6 承诺调用前遵循外部额度，Task.usage 目前只有调用后的 host_reported 计数。应明确同一项目并行 Host 的额度如何分配、未知调用结果如何处理、重试如何计数。最小做法是当前项目调度时分配明确调用 allowance，保留未知结果并停止追加外部调用等待核实；本地修正继续。不能声称产品能约束绕过产品的宿主工具调用，不建设账户预算服务。

### R4 / P1：UI 可启动，但默认何时出现仍不够明确

10.4 明确了 view --open；09.5 默认宿主循环只要求完整候选之后提供 URL，没有明确正常 create/首次正文接收是否实际启动并打开服务。仅实现命令仍可能让用户再次一直看不到 UI。

修订：桌面正常任务首次形成页面时，由主 Skill 自动调用 view --open；同一项目复用服务及 URL。之后每次稿件更新提供同一入口。非交互/无浏览器环境明确返回实际可用地址或不可启动原因。验收从自然语言入口开始，不手工额外执行 view，并观察失败稿和修改反馈可达。

这不意味着 UI 自带模型后台；无 Host 时等待状态已有正确边界，应该保留。

### R5 / P2：可编辑形状与原生图表/表格的能力边界应明确

此前实施目标涉及原生图表。新 Spec 以 SVG 作为制作源，主要声明可编辑文字/路径/形状；Page 有 table 数据但没有 chart 数据模型或原生 chart 写入接口。图表画成可编辑矩形，并不支持 PowerPoint 的“编辑数据”。

修订：明确首版交付的表格、图表究竟是原生 Office 对象还是可编辑形状组。建议先承诺高保真的可编辑形状与文字；原生数据图表若继续纳入，须补数据、单位、序列与编译接口，并用目标应用实际改数据验证。不能从“可编辑”推断完整原生图表能力。

### R6 / P2：最早真实闭环不要等完整通用能力

T10 已提前真实生产，是正确安排；但目前它依赖完整 T03 材料支持、T09 全部绘制修复等。75 个目标是台账，不应变成第一份成品之前必须铺齐的文件数量。

建议保留最终范围，允许最小纵向切片交错：已知材料与完整稿接收、事故页所需 SVG 子集、实际 PPT 渲染、只读四视图、一次单页修改先跑通。随后补齐格式、一般化事务和安装。最小闭环必须实际对照原图，不能因 T11 统一审阅尚未开发就省略人工/Host 阅图；也不能把该阶段称全产品完成。

## 其他明确修订

分支建议 rebuild/mainline-v1 改为遵循仓库约定的 codex/rebuild-mainline-v1；是否创建在实施时执行。本轮未切分支。
对 Review fixed 的实际复查关联、稳定 atom ID 的生成规则、结果信封格式，建议在相应任务开工前各补一个完整往返例，不需要扩大成更多永久 schema。跨对象语义已有单独校验要求，不能仅因 JSON Schema 容许空列表就断言产品必然放行。

## 建议实施顺序

先修上述合同和执行缺口，形成 v1.1。第一批验证两条结果：同源 D1/D2 从原材料形成不同正文；事故架构页和含表格/数值页完成原图→SVG→PPT 三方对照，并在同一工作台可见。紧接一次单页修改，检查其他页不重生。成立后扩展完整恢复、独立安装及旧代码退役。H1/H2 保留到冻结后。

这份 Spec 可以作为重建基础，无需再重写一套总体方案；修订的目的在于补实输入、用户入口和完成条件，避免正确原则在实现时被不同模块各自解释。
