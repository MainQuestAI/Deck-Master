# Deck Master 主流程重建与遗产提取方案

依据：[全链路架构审计](./architecture-audit.md)。本文件是后续方案，本轮没有启动实现。

## 建议与实施边界

选择“重建主流程＋提取资产”。保留当前仓库及历史，停止给旧 OS 增加新生产例外。不先删 5 万行，也不把 5 万行全部维护一遍。用一条真实、可审阅的路线决定哪些组件值得进入新核心。

新版可称 Deck Master 2.0；是否新仓库不是当前技术前置。先在现有仓库的隔离实现边界验证替代路径，验证完成后再切换默认入口。旧路径不能永久成为与新路径并列的第二个产品；旧 run 的读取或继续执行要明确使用 legacy 边界。

这比上一轮蓝图修复方案扩大了范围：内容与结构、图片输入、SVG重构、PPT编译、UI、状态、安装独立性必须在同一条正常任务上成立。

## 用户看到的流程

1. 给资料及任务，已有讨论直接沿用；Agent补读原文，写出场景适配的结构与完整正文。
2. 内容与设计要求生成蓝图；对照蓝图重构SVG，编译可编辑PPT并读取实际结果。正文不足回到编辑，视觉缺失回到制作。
3. 首稿与修改后提供真实页面预览及审阅工作台；用户指出具体页面/内容，系统更新受影响页面并保留其他页面。
4. 当前成品及适用检查一致后交付PPT、必要预览与可恢复源文件。没有外部PPT Master绑定、Library安装或团队审批系统前置。

一个主要Skill入口足够；主编、设计、制作、审阅仍是实际职责，但无需让用户逐个调用Planner/Producer/Builder/Quality/Review。宿主Agent负责理解和创作，代码负责确定性的文件处理、图形转换、运行恢复和真实检查。

## 第一批：建立小型完整链路并判定资产

输入：事故两页、已有合成资料，再加一张包含表格/数值和单位的页面。保留原坏稿作为反例。内容不足先改正文，不让生图凭空补能力和效果。

产物：完整正文、实际prompt、PNG、SVG、PPT、两阶段渲染对比及可点击审阅页。初期审阅页可以很小，必须直接使用本次真实产物。

涉及代码：

- [完整稿接收与回滚](../../../../scripts/runtime/orchestration.py:153)：提取稳定页身份、全稿接收、增删重排、失败恢复。
- [PagePackage](../../../../scripts/production/page_package.py:1)：保留对外正文与内部说明边界。
- [Content Lock投影](../../../../scripts/high_density/content.py:250)和[蓝图prompt投影](../../../../scripts/high_density/blueprint.py:385)：完整传递正文、脚注/标签及适用的设计要求。
- `svg_native.py`、`svg_paint.py`、`pptx.py`、`visual.py`：提取实际几何、样式、编译、渲染与测量；修复上一轮已复现缺陷。

通过条件：三页内容成立，图标/状态/关系/数值和视觉层级保留，文本及图形可编辑；删除关键对象或反转关系能被定位；实际UI看得到这些页面。

失败去向：内容不足修改方法和正文；PNG输入遗漏修prompt；SVG缺对象重构对应区域；PPT失真修编译组件。不得改预期清单以接受坏输出，也不得加完整工作区平台来绕开这些问题。

这一批应尽早交出真成品，而不是先完成全部平台设计。

## 第二批：替换默认内容链，避免“好方法只是可选文档”

输入：同一组资料的首次能力交流与已有客户方案评审两种任务。

改动：

- 默认新建任务先进入宿主成稿方法；`autoplan`规则输出不再被当成正式结构。
- 移除生产路径中按关键词铺页、显式页数补通用目录、循环分配论点的逻辑。用户指定页数只约束长度，不授权固定目录。
- 自动摘要用于导航和定位；业务判断必须读取相关原文。保留可定位来源，不要求所有建议都有历史效果数字。
- 正文要能解释当前任务的机制、取舍与选择条件。第二页应说明阶段范围、先后依据和转段条件，不能仅把两个阶段标签放大。

定位：[规则Planner](../../../../scripts/planning/narrative_planner.py:235)、[论点循环配页](../../../../scripts/deck_master.py:578)、[规则Brief](../../../../scripts/conversation/brief_compiler.py:12)、[公共内容方法](../../../../skills/deck-master/references/content-methods.md)。

通过条件：两种任务形成不同且成立的正文与结构；材料末尾只读/不可回写约束真正改变方案和图示；合理短稿不填章节，复合稿不被压成两张概念卡片。人工精修的演示稿与正常首稿分开记录。

## 第三批：统一状态并让UI成为真正的审阅入口

改动：

- 当前页面集合与版本来自同一个产物清单；构建、审阅、CLI和UI都读取它。保留原有可靠格式，移除平行事实，而非再造一个总治理层。
- 将旧run_state、Skill OS、preview与高密度status中的适用事实归并；旧stage不直接决定新任务是否可交付。
- UI页面卡片直接读取真实正文与产物；并列查看蓝图、SVG、PPT以及具体问题。查看失败产物不依赖最终批准。
- 新建/继续/修订输出当前任务审阅链接；提供一个维护简单的启动入口。现场生成和修改后能回到同一工作台。
- 只询问会实质改变当前任务的缺失决定，不再因为九个Skill阶段有未填问卷而重问已确认内容。

定位：[旧预览依赖](../../../../scripts/preview/server.py:1654)、[页面列表来源](../../../../scripts/preview/workspace_api.py:984)、[无preview时的状态映射](../../../../scripts/preview/workspace_api.py:812)、`scripts/runtime/run_state_resolver.py`、`scripts/runtime/next_step.py`、`scripts/workflow/state.py`。

通过条件：事故副本显示真实两页及具体未通过项；不再出现“可交付＋0页＋初始化等回答”。改一页后UI与CLI立即指向同一个新版本，其他页保持不变。不能只截一张新UI效果图作为完成证据。

## 第四批：移除绑定与不必要工作区平台，提取发布能力

改动：

- 新核心不依赖PPT Master外部repo、认证、SHA或安装；Library仅在明确请求历史检索/复用时加载。
- `product-capability-manifest.json`、路由、installer、doctor、README和UI统一调整；不能仅把错误降成warning或再加profile判断。
- 用户现有材料目录直接使用，自动创建必要制作产物目录；新任务不需要先初始化整套客户项目目录和结构模板。
- 公开主要入口收敛到deck-master；维护工具不包装为不同生产专家。
- 从已有发布/回滚中抽取可靠能力；验证实际安装内包含必要代码、方法和Web UI。

定位：[外部后端前置](../../../../scripts/runtime/build.py:137)、[绑定管理](../../../../scripts/runtime/builder_backend.py:26)、[全局就绪绑定](../../../../scripts/skills/installer.py:2395)、`scripts/runtime/workspace_resolver.py`、`scripts/workspace/project_init.py`。

通过条件：未安装/未配置PPT Master和Library的环境，从安装后的正常入口完成制作、显示工作台并修改一页；不调用源码目录补文件。报告安装版本与实际模块来源一致。

## 第五批：迁移与切换默认入口

- 对旧run只承诺经过验证的读取、导入或在legacy环境继续；不把所有旧状态文件强搬进新核心。
- 新的默认入口、文档、安装Skill和UI使用同一条路线。旧模板Planner和旧标准后端不再通过某个默认值悄悄复活。
- 保留事故正反例、单页修改/增删重排/重定位恢复测试，删除只为错误产品行为背书的测试。
- 用陌生企业材料和不同类型Deck检查方法迁移；专业性、视觉效果和编辑体验由真实使用者验收，模型间一致不作为业务通过。

## 不进入新核心的内容

旧的固定九阶段Skill OS、生产前的全套安装齐备要求、全局PPT Master认证、默认Library检索、MBB候选强制二次选择、与新产物重复的旧preview事实、无实际价值的团队审批/商机管理/时间节省评分。

可以保留在旧版本供历史使用，不以“大删代码”作为本轮成果。确有新业务需求时再用实际任务证明必要性，不能因为代码已经写了就强行继承。

## 最终选择标准

保留一个组件，要能指出它减少了哪种真实失败，并能在相应样例中重复观察。需要持续手写例外才能跑通、只检查自己生成的答案、或要求用户维护额外状态才能工作的部分，退出新核心。

若原生转换器在已明确的SVG支持范围内仍不能完成样例，就替换转换器；若默认内容仍然空泛，就重做方法和输入消费。不要再次把内容能力不足转译成更多表单、指标、密钥和审批。
