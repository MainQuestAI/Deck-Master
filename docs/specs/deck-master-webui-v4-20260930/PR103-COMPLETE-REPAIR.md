## 旧 CI 差异调查

`37609015551`（push，失败）和 `37609023947`（pull_request，成功）都以 `3f0a28d` 为 head，都是第 1 次运行，并非失败重跑后变绿。失败日志中合法重选上传已返回成功，但 UI 停在“工作状态尚未确认保存”的后续出口；原实现将 `saveState()` 未处于 saved 当成业务失败。独立受控后写反例在原源码重现同一成功后无出口问题。本轮改为独立保留业务完成事实，并验证上传及其三个同源操作。

## 本轮 CI 揭示的恢复收尾竞态

`cb96e1c` 的 PR 运行 `37621592621` 与 push 运行 `37621582466` 失败后没有原样重跑。日志显示合法重选图片已经返回 200，但继续提示停留在“截图已上传；结果已保留”。本轮新增受控反例：新参考已经挂载，草稿保存实际成功但响应丢失；用户核实后草稿变为 saved，继续记录仍不清除。原组件稳定失败。

原因是原恢复监听只负责跳到不同 revision，忽略“已经在结果版本，草稿稍后才 saved”的收尾。修复增加已完成挂载的记录身份，只有结果已读、选择与已保存草稿一致才清除；晚到 saved 和显式核实走同一收尾。原拒绝后合法上传必须自动退出恢复提示的断言保留，未增加固定等待或跳过条件。最终 CI 重新随修复提交运行。
