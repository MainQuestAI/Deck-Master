# Deck Master UI 重构调研 · 2026-10-24

本轮核查 7 份官方一手文档，研究对象是内容生产工具的工作视图、对象操作、版本比较和可访问交互。结论用于精修已认可的浅色 r2 方向，不构成换品牌、换框架或增加功能的理由。这是文档研究，不是竞品完整体验或用户可用性测试；下文明确分开“官方确认的行为”和“Deck Master 的设计推论”。

## 研究结论

粗糙感的主要来源不能只靠缩小按钮解决。需要同时建立三层秩序：**先确定用户正在处理哪个对象，再确定当前工作视图，最后显示此时可执行的动作。** 一级导航稳定；对象标题、状态和动作各有位置；批量动作在选择后出现；编辑和比较拥有明确边界。尺寸、间距和焦点规则随后统一。

本轮建议保留 r2 的系统字体、浅色中性面、黑色主动作和单页阅读结构。增加的重点是选择状态、版本身份、菜单语义、抽屉性质和异步反馈的细节，而不是再加一套装饰。

## 官方资料与应用边界

### R01 · 对象选择决定可用命令

来源：[Linear · Select issues](https://linear.app/docs/select-issues)；核查日期：2026-10-24。

**已核实：** Linear 区分高亮和选择，初次打开列表默认无选择；支持连续选择、键盘选择和清空选择。选择后可通过命令菜单或上下文菜单执行操作，常用批量动作出现在底部；键盘重排以手动排序等条件为前提。

**Deck Master 推论：** 默认页序列表只显示对象和一个末列操作入口。选中页面后显示选择数量、适用动作和清空入口；“查看单页”和“选中页面”必须是两件事。筛选外已选计数沿用本项目 D1 决策，不把选择静默清除。上移/下移是拖拽的明确替代。

**不能照搬：** 不把鼠标悬停作为唯一发现途径，不要求用户记住快捷键或右键；不将 Linear 的问题字段、快捷键或选择规则直接当作 Deck Master 合同。

### R02 · 不同任务需要不同工作视图

来源：[Microsoft · Choose the right view for the task in PowerPoint](https://support.microsoft.com/en-us/powerpoint/training/choose-the-right-view-for-the-task-in-powerpoint)；核查日期：2026-10-24。

**已核实：** PowerPoint 文档分别介绍编辑、排序、大纲和阅读视图：编辑聚焦当前页，排序便于整理页序，大纲聚焦文本，阅读保留少量翻页控制。不同客户端的可用性存在差异。

**Deck Master 推论：** 内容与页序负责论证结构；整稿画廊负责连续视觉检查；单页负责阅读与制作。这些视图共享同一个页对象，切换时保留页位置、筛选和返回入口。正文视图与页面预览是局部视图切换，不应与全局工作区并列。

**不能照搬：** 不复制 PowerPoint 功能区、母版工具或所有视图数量；Deck Master 还需表达生成任务、候选、采用与交付，这些不是上述视图自动提供的能力。

### R03 · 比较先交代对象与版本，再呈现差异

来源：[Figma · Compare changes in Dev Mode](https://help.figma.com/hc/en-us/articles/15023193382935-Compare-changes-in-Dev-Mode)；核查日期：2026-10-24。

**已核实：** Figma 支持在选定对象的版本历史中比较；可查看并排或叠加视图，也可查看发生变化的图层和属性。比较入口依附于所选对象，比较内容有版本关系。

**Deck Master 推论：** 比较头部持续显示“第几页、哪一层、基准版本、候选版本”；正文用文本差异，图像默认完整等比并排。固定比较引用不随后台新结果漂移，返回列表后仍能恢复原比较。动作明确写“采用此候选”，采用后的状态单独回读。

**不能照搬：** 首轮不引入通用图层检查器、代码差异或透明叠加滑杆；历史对比与候选采用并非同一种业务行为。“锁定比较引用”来自本项目约束，不声称是 Figma 的异步保证。

### R04 · 更多操作必须是可识别、可键盘操作的菜单按钮

来源：[W3C APG · Menu Button Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/menu-button/)；核查日期：2026-10-24。

**已核实：** 菜单按钮需要按钮语义、菜单展开状态和弹出菜单关系；Enter/Space 打开后焦点进入菜单。采用 menu 语义时还需实现对应菜单键盘行为。

**Deck Master 推论：** 行末省略号具有稳定轮廓、可访问名称（如“第 6 页操作”）、悬停与焦点态；菜单项按对象动作分组。菜单位置不能被列表裁切，靠近窗口底部时翻转。普通跳转保留链接语义，操作使用按钮语义。

**不能照搬：** 不能只贴上 role="menu" 就称完成；若使用普通弹出按钮列表，应按其真实语义提供 Tab 路径。r2 的 details/summary 样例需要在工程阶段选定并验证一种完整模式。

### R05 · 抽屉形状不决定模态性质

来源：[W3C APG · Dialog (Modal) Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)；核查日期：2026-10-24。

**已核实：** 模态对话框打开后底层内容不可交互，焦点进入框内并循环；Escape 关闭；关闭后通常回到发起控件。长内容的初始焦点可放在顶部静态标题以保留阅读结构。

**Deck Master 推论：** 短时编辑抽屉作为模态编辑器：明确标题、字段、保存/取消、焦点返回和草稿保护。需要一边看正文一边核对来源时，使用非模态检查区，不能同时宣称背景可操作又把焦点困住。长正文编辑提供展开工作区，避免被窄抽屉强制压缩。

**不能照搬：** 不把所有详情都放进模态抽屉，不层叠多个模态编辑器；APG 不替产品规定草稿持久化、冲突解决或保存成功语义，这些仍由项目合同定义。

### R06 · 合理尺寸取决于命中区域与输入方式

来源：[W3C · Understanding SC 2.5.8 Target Size (Minimum)](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum.html)；核查日期：2026-10-24。

**已核实：** WCAG 2.2 的 AA 最小目标尺寸为 24×24 CSS px，并含间距、等价控件、行内等例外；文档明确最小合规不等于最好用，重要控件可考虑更严格要求。

**Deck Master 推论：** 延续 r2 的桌面 32px 常规 / 36px 主动作、44px 表单输入与触摸目标方案，并将视觉外框和实际命中区域分开记录。菜单行、图标按钮和关闭入口不能只测可见图标。使用一致的控件内边距和组间留白，不通过全页放大按钮制造“可用性”。

**不能照搬：** 32/36 是本项目的密度选择，不是 W3C 推荐值；24 不能当作所有控件的设计目标。触摸命中区域不得相互重叠，也不能凭几项尺寸检查宣称全站 WCAG 合规。

### R07 · 异步变化应可感知，但不抢走当前工作

来源：[W3C · Understanding SC 4.1.3 Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)；核查日期：2026-10-24。

**已核实：** 成功、等待、进度和错误等状态消息需要能被辅助技术识别，通常无须取得焦点；目标是在不无故打断工作的情况下告知重要变化。文档列出 status、log 和错误提示等适用技术。

**Deck Master 推论：** 保存后在当前对象旁显示结果；任务执行中以局部进度和持久任务记录承接；新候选到达只更新入口数量，不切换正在阅读的版本。不对每次轮询重复播报。错误在受影响区域说明原因与恢复动作，结果未知时显示“结果待确认”。

**不能照搬：** toast、ARIA live region 和绿色标签不证明任务完成。保存、提交、返回、采用、检查与交付必须各自读取真实状态；业务状态依据项目合同，不能从此可访问性文档推导。

## 落到本轮精修的设计约束

以下均为 Deck Master 的设计建议，需在完整方案中成为明确组件规则及验收用例。

| 编号 | 约束 | 应看到的改进 | 验收方式 |
| --- | --- | --- | --- |
| RF-01 | 页面头部只承载本工作面的下一主动作；对象操作就近出现 | 不再在页首堆出一排同等强调的动词 | 用正常、选中、编辑三个状态逐一标注主动作与作用对象 |
| RF-02 | 区分导航链接、视图切换、执行按钮、状态标签 | “文字浮着但不知道能不能点”的歧义减少 | 检查语义、轮廓/下划线、焦点态与指针行为；状态不伪装按钮 |
| RF-03 | 常态列表末列一个可命名操作入口；批量工具栏按选择出现 | 减少重复动作，同时保留可发现入口 | 零选、单选、多选、含筛选外对象各截一屏 |
| RF-04 | 页对象身份与返回位置连续 | 从总览到单页、候选再返回不迷失 | 记录页号/层/筛选/滚动位置，往返后核对 |
| RF-05 | 来源检查和正文编辑分属不同交互模式 | 能看清正文，也能知道此刻是否在编辑 | 用键盘验证非模态区可进出、模态区焦点循环与返回 |
| RF-06 | 比较上下文固定、内容完整等比 | 新结果不会悄悄替换正在判断的基准 | 注入异步新候选，验证当前左右版本保持不变 |
| RF-07 | 异步反馈就近且保留记录 | 不靠短暂 toast 才能知道操作是否成功 | 覆盖进行中、成功、失败、未知、取消及迟到结果 |
| RF-08 | 控件尺寸与组间空间共同治理 | 紧凑但不拥挤，触摸不误触 | 1440/1280 桌面、768/390 窄屏，测实际命中框与相邻间距 |
| RF-09 | 长标题、长正文、空列表、错误状态沿用同一布局规则 | 真实内容增加后界面仍有秩序 | 使用长标题与长段落、0/1/30 页样本检查折行和主要动作可达性 |
| RF-10 | 正文保存不替代内容确认，候选采用不替代质量检查 | 状态文案不夸大业务进度 | 对照真实合同逐项核对动作前后状态与按钮文案 |

## 对“完整方案”的影响

完整方案应覆盖项目入口、五个工作面及共享单页链路；三张已认可样页是组件与层级样本，不等于完成全部信息架构。每个工作面至少指定默认主任务、主要对象、主动作、上下文动作、进入/返回路径和异常状态。

视觉实施宜先归一语义 token 与组件，再迁移工作区，最后覆盖真实动态状态。不得通过隐藏所有按钮、压低正文可读性、去掉必要状态或把所有任务塞进抽屉来追求表面干净。研究支持的是动作与任务的关系，不是对某一竞品像素尺寸的照搬。
