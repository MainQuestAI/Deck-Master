# N6｜正常任务中的内容效果与返修效率改进

## 1. 任务定位

| 项目 | 约定 |
|---|---|
| Spec 包版本 | v1.0 |
| 建议目标候选 | 1.0.0rc4；这是下一候选的规划，不表示已完成修改或已经发布 |
| 审查基线 | `main@a08bc68c1cbbbc806205104c2bb01f3f096305f0` |
| 本卡目标 | 围绕实际稿件缺陷改进内容方法，并在本轮一项完整正常任务中实际应用；有布局缺陷时定向降低返修负担 |
| 主要 Owner | 内容方法与真实任务执行 Agent；必要时由设计/渲染开发 Agent 协作 |

| 最小结果 | 本轮实质方法修改、完整来源与稿件、一次完整正常任务的实际应用、具体问题与修订闭环，以及诚实的效果结论 |

**事实边界：** 所有关于当前仓库能力、可访问材料、实际运行、文件路径、测试及安装的判断，在实施开始时均**需要 Codex 核验**。本卡不把历史报告中的 PASS、一次已审确认稿的制作成功或预设样例，当成本轮新方法的实际应用结果。

## 2. 业务目标与完成原则

用户关心的是：材料进入之后，能否得到有业务判断、内容完整、密度合理、可用于讨论的稿件；发现问题后，能否修复真实内容或排版，并保存稳定可交付的结果。

本卡必须完成实际改进，不能只增加台账、流程说明、质量标签或一个未执行的测评方案。最低要求如下：

1. 从已有正常任务/可读稿件中定位一个本轮范围内的实质内容缺陷或可复用的方法缺口。
2. 修改现有 canonical 方法中的具体写作/审稿步骤或完整正反例，使作者知道如何做得更好；不是只重复“增强专业性”“补证据”。
3. 用固定来源和当前方法执行一项范围清楚的完整正常任务，交出其约定成果并审查实际输出。
4. 对发生的问题做真实修订与复核；结论只覆盖实际执行的任务与对象。

不承诺本轮把首稿通过率提高到某个百分比，不设无法从现有数据推导的内容字数、返修次数、生成速度或效果分数阈值。需要记录的是问题性质、具体变化及是否已经解决。

## 3. 输入选择与资料边界

### 3.1 优先顺序

| 优先级 | 可用输入 | 使用规则 |
|---|---|---|
| 1 | 用户已提供、范围已明确的项目材料与正常任务 | 沿用已有用途、页数、风格和授权；只补问会改变本次结果的真实缺口 |
| 2 | 可取得原件、版本及完整稿的既有项目记录 | 作为问题定位和返修输入；历史首稿保持原身份，不改名为当前候选首稿 |
| 3 | 项目中可完整核对的公开/中性材料 | 形成可独立完成的常规工作委托，明确目标受众和交付用途；不只拿孤立两句模板作为完整任务 |
| 4 | 本地材料不足时的公开资料或明确标注的中性合成材料包 | 材料应包含完成任务所需事实、限制、业务对象和可作判断的关系；公开事实保存出处，合成数字保持示例身份 |

**没有新的真实客户项目不构成任务阻断。** 使用公开或中性完整材料，仍须实际调用本轮宿主完成正常内容工作；不得用脚本拼出固定答案冒充模型应用。用户未要求的客户生产、外部发送或发布不在本卡范围。

### 3.2 历史证据的使用

审查时已读到的定位，实施时需要 Codex 核验：

- `docs/reports/rc3/closeout-20261018/README.md`、`summary.json`、`artifact-manifest.json`。
- `docs/reports/rc3/evidence-ledger.json` 及明确标识的历史台账。
- `docs/reports/rc3/native-content-handoff-20261014/` 中可访问的完整原稿、Owner 稿、实际问题和修订记录。

当前 Git 汇总索引指向的部分成品原件位于仓库之外。能取得则按 hash核对；取不到就只把报告当历史报告，不据索引反造图片、原模型执行、原首次稿或完整 PPT。现有报告中已关闭的布局与备注缺陷不能重新列作当前未修问题，但可用于挑选需要减少的返修类型。

### 3.3 最小任务简述

执行前形成一段可审阅的工作委托，复用已有信息，至少说明：受众、本次要理解/判断/完成什么、来源范围、交付形式、既定约束、缺少什么以及可合理推理到哪里。明确任务是完整内容包还是完整 PPT；不因为开展效果改善就自动扩大用户已授权的产物范围。

使用已有确认稿做局部修改时，委托说明保留哪些方向、修改哪些页/字段。需要观察新方法从材料开始的成稿情况时，选择真实的新内容任务；不将精修后的 Page 输入隐藏起来并声称只提供了原材料。

## 4. 本轮问题选择与实质改进

### 4.1 先定位一个能改变成果的具体问题

使用现有内容审查方法读取完整相关材料和稿件。优先检查以下与本次用户目标直接相关的问题；它们是选择范围，不是认定当前所有稿件都存在这些缺陷。

| 问题类型 | 有效定位方式 | 可能的修复 |
|---|---|---|
| 主线没有形成判断 | 指出任务问题、现有结论、缺失的支持/机制/取舍及受影响页 | 改写实际论证和页间推进；更新相关 Narrative/Plan/Page |
| 矩阵、案例、流程只有标签 | 指出没有差别的单元格、案例中断的因果/动作、缺失的责任交接 | 补写能支持选择的具体差异、条件、例外与工作结果 |
| 页面重复导致信息密度虚高 | 比较两页重复部分与各自应有的独特贡献 | 合并/删除重复表达，补上真正下一步问题；保留有用途的教学重复 |
| 边界/未知反复占据主线 | 指出哪些限定只需在特定结论旁出现，哪些重复没有新增理解价值 | 将必要限定准确绑定结论；集中稳定背景，不在每页重写同一组免责声明；不能删掉会改变结论的限制 |
| 主图与侧栏换词复述 | 对齐图中关系与侧栏实际文本，指出缺少的含义或选择依据 | 侧栏补机制、差异、例外、实施代价或决策含义 |
| 依据齐全但正文没有写出来 | 对齐原件、Narrative/Plan 和 Page 的具体遗漏 | 将关键信息写入客户可见正文；制作说明仍放内部字段 |
| 原生排版反复返修 | 指出真实 SVG/PPT 中受影响的表格、文本框、字号、换行或净空 | 修复该页布局或共享可复用计算；检查实际渲染，不能只核对 XML 文本 |

优先选择已经有本地证据的问题。若首次选择的稿件没有该问题，应更换问题判断，不为符合预设主题而刻意判失败，也不需要固定的“失败样本数量”。

### 4.2 方法改动的最低实质要求

本轮至少有一项 canonical 方法改动，满足以下全部条件：

- 指向上一节真实定位的问题，能说明旧方法在实际执行时哪里不够明确或不够可操作。
- 改动明确下一次作者/Reviewer 应读什么、判断什么、具体改什么，或提供一组完整的正反页面/连续页例。
- 改动能保留有效正文、必要限定和正确图形关系；不能以增加证据 ID、填满更多字段、扩大禁止词表或提高字数要求替代。
- 新例子自包含，示例身份明确；如果沿用设备条件/只读案例，应引入本轮缺口的真实方法增量，不仅更换名称或重复已有六组校准。
- 改动后使用新版本方法完成实际正常任务，不能只做字符串断言或方法文件存在性检查。

推荐首先考虑“页职责/独特贡献与关系密度”或“必要限定就近保留、重复背景收敛”的具体执行方法，但最终选择必须由实际缺陷支撑。若实际主要问题是来源事实错误或表格归属错误，则先修该问题，不为了写出上述主题扩大范围。

### 4.3 允许修改的对象与模块

| 对象/模块 | 允许工作 | 边界 |
|---|---|---|
| `skills/deck-master/references/content-methods.md` | 改进材料→论证→完整页稿、删重、关系表达和实际返修步骤 | 只在这一 canonical 源编辑，不复制到其他 Skill |
| `content-examples.md`、`content-calibration.md` | 加强完整正反例和用途判断，覆盖本轮已定位问题 | 保留稀疏正例、诚实未知；不是新增固定类型目录 |
| `source-reading.md`、`review-and-repair.md` | 必要的来源/影响范围/复核说明 | 不扩大默认人工门槛或变成每次必须填表的过程 |
| `physical-units.md`、既有 SVG/原生排版辅助模块 | 实际发现布局问题时补充可复用方法或局部计算 | 必须有真实版面证据；不更改冻结字体、原图或 converter 全局常数来掩盖失败 |
| 当前正常任务的 Narrative/Plan/Page/notes/SVG/PPT | 经现有 Runtime 服务修订实际受影响对象 | 保留原始输入、原图和历史版本；不编辑对象存储或只修改投影 Markdown |
| 现有审查/交接证据导出 | 保存明确的问题、改句、对象与复核结果 | 不建第二份可独立修改的内容真源，不新增默认审批状态 |

这些路径及已有辅助能力在实施时需要 Codex 核验。缺陷若需要修改本卡之外的授权、宿主桥接或大型编译机制，交对应 Owner 修复；在原任务中保留当前稿与具体未完成部分，不以降低检查要求完成本卡。

## 5. 执行流程

### 步骤 1：固定输入与实际身份

保存实际材料原件/提取文件的版本、原始工作委托和已有决定。选定当前候选及方法 SHA。记录真实可观察的宿主身份与工具能力；不可得的 model id、采样参数或后端版本保持 unknown，不从模型名称或提示词推定。

若 N6 修改了方法，在修改前记录旧版本，在修改后记录新版本；新应用按 N3 取得新 Task 的准确 method_manifest。旧 Task 不在恢复时自动消费新 calibration，也不重标历史任务的方法版本。

### 步骤 2：保留首份完整稿与问题位置

“首份完整稿”指宿主在该任务中第一次形成全部约定内容的可读产物；如果合同接纳曾失败，要同时保留真实原始 Host 输出与首次成功接纳稿的区别。正常自主编辑允许发生，按实际步骤记录即可，不发明“零修改首稿”成绩。

如果使用的是历史确认稿，称为“固定输入稿”或“本轮修改前稿”，不叫“当前方法首稿”。如果当前候选产生新稿，区分原始完整稿、实际交用户审阅稿、后续修订稿，不以最终精修覆盖前面的版本。

### 步骤 3：完成问题驱动的方法修改

把每项选定问题写成“位置—实际—为什么影响用途—期望—修复层”。然后完成上一节要求的 canonical 方法改动。保留具体前后差异和选择理由，说明适用与不适用情形。

建议在同一轮完成方法文本和一个完整正反例的最小配套，而非仅补一句抽象要求。方法包正常打包；资源清单/hash变更应通过 N3/N4 的实际读取路径反映出来。

### 步骤 4：在完整正常任务中实际应用

实际宿主读取固定来源、当前准确方法和工作单，完成本次约定成果。可与本轮其他任务的真实应用共用一个已授权项目，避免为验证重复生图。

- 内容改进至少应用到一份完整内容稿及其现有 Narrative/Plan/Page 关系，不能只做单段改写或生成不进入 Runtime 的示意答案。
- 正常任务是 content_only 时，完成该子意图的完整产物与适用检查即可，不强制追加图片或 PPT。
- 正常任务是 full_deck 时，沿现有授权范围完成 Page→图片→SVG→真实 PPT 与适用检查。
- 只有实际改动布局/渲染时，才要求对受影响页重新生成/编译相应产物并查看实际结果；只改 notes 不重复生图，SVG 修改不自动更换原始蓝图。

如宿主缺少必要工具，先按现有 doctor/恢复流程解决已经授权的环境问题，其中安装问题按 N2 处理。有合理可行的公开/中性任务则继续执行，不能以没有真实客户材料为由结束。真正无法执行真实模型应用时，可以交付已完成的代码/方法和当前稿，但 N6 仍标明“实际应用未完成”，不能仅凭测试宣布整卡关闭。

### 步骤 5：实际审稿、修订和复核

按本次有效的内容审查政策执行；需要独立前审时，由实际非作者执行并沿现有受信回执接纳，不把换 Skill 名称当独立。普通交付不额外要求人类审阅。用户已有正常审稿意见则处理，没有安排用户/听众参与时不因此阻塞。

每项实质问题至少保留原句/原结构、改句/改结构、所在页/atom/关系、所用来源、修复层与实际复核结论。回读受影响的摘要、结论、表格、notes 和最终文件，避免局部改好而别处仍保留旧说法。

按照实际缺陷修复，不默认固定只能返修一次，也不为生成更多记录而额外增加轮次。超出当前 Scope 的必要变化先沿正式范围处理；其余已授权工作继续完成。

### 步骤 6：形成可支持的效果判断

最终回答具体问题：哪些缺陷减少或消失，哪些仍然存在，本轮方法在哪种任务上被实际使用，以及哪些结论尚未验证。

可以记录页数、原生对象、实际调用次数、返修对象数、发生过的耗时等可观察事实，帮助下一轮选择重点；计数不自动形成因果提升。没有相同条件的可比数据，就不声称“提升 X%”或“普遍优于旧版”。正常任务的具体改善不需要另建 Frozen A/B 才能用于产品决策。

## 6. 证据与结果记录

优先使用现有不可变对象、Task 结果、Review findings、diff 和导出；增加一份可读结果索引即可。索引只定位原件和固定快照，不复制一份可以另行修改的正文。

| 需要说明的内容 | 最小证据 | 不可替代物 |
|---|---|---|
| 输入是什么 | 原始委托、来源 Ref/hash、已有决定及覆盖范围 | 只有材料文件名或回忆摘要 |
| 方法确实改变 | canonical diff、旧/新文件 SHA、修改理由 | 仅新建台账、换标题、方法存在性测试 |
| 实际应用什么 | 当前 Task/manifest、真实 Host 输出与完成记录、可读完整稿 | 方法读取回包、脚本预填答案或预期输出 |
| 问题如何修复 | 具体 finding、旧/新对象、真实 diff、受影响范围 | “已增强专业性”或补写 observation |
| 当前结果是什么 | 完整当前稿；适用时实际 SVG/PPT/notes 及检查 | 单独一张截图、XML 字符存在或历史文件 |
| 验证有哪些边界 | 实际检查/未执行项、未知参数、公开/合成身份 | 把 Agent 观察写成人类签字或客户成绩 |

建议结果索引列出：`candidate_sha`、`task/project_id`、`source_basis`、`method_before/after`、`draft_refs`、`findings_and_changes`、`current_outputs`、`checks`、`limitations`。这是普通交接记录的建议字段，不新增必须进入产品状态机的业务对象。

## 7. 明确不做的事项

- 不新增内置 LLM Provider，不要求 API Key，不扩大 harness 适配范围。
- 不恢复旧 Frozen A/B、匿名盲评实验、固定听众人数或固定真人试讲计时。
- 不将人类专业审批变成默认交付前置；只有当前任务明确适用的政策继续生效。
- 不给所有页增加字数、证据索引、制作说明、风险声明或统一“三张卡片”。
- 不因没有量化收益而编数字；也不把诚实未知视为必须删除的内容缺陷。
- 不为改善一处效果而重建无关页面、重生全部图片或修改用户已经确认的用途。
- 不把历史已关闭缺陷重新列作当前失败，不以最终精修结果反写旧失败。

## 8. 验收标准

| AC ID | Given | When | Then |
|---|---|---|---|
| AC-N6-01 | 已有可用材料或可取得的公开/中性完整材料 | 选择本轮实际任务并形成委托 | 明确受众、目的、来源、产物及范围；优先复用已有信息；没有新客户项目不导致任务被搁置 |
| AC-N6-02 | 任务输入、原始 Host 输出及后续稿件实际存在 | 固定版本并导出可读稿 | 来源、首份完整稿、首次接纳稿和修订稿按实际身份分开；不隐藏预先提供的确认稿或用精修稿覆盖首稿 |
| AC-N6-03 | 完整稿中有本轮范围内的实质缺陷或方法执行缺口 | 完成问题定位及 canonical 方法修改 | 至少一项改动能对应具体问题并给出可执行步骤/完整例子；不能只新增台账、标签、字数规则或泛化建议 |
| AC-N6-04 | 方法已修改，当前 Task/安装身份可核对 | 宿主在完整正常任务中读取并实际使用 | 新方法 SHA 与派发 manifest 一致；存在真实运行与完整约定产物；读取字节、合成单测或脚本答案不冒充实际应用 |
| AC-N6-05 | 新任务需要论证或完整内容包；另有确认稿/fidelity 的对照情况 | 完成内容工作 | 前者具备实际 Narrative/Plan/Page 的对应主线，后者保留确认稿边界；不能为填字段补造论证、批准或事实 |
| AC-N6-06 | Reviewer 或作者发现影响用途的具体内容问题 | 通过现有 Runtime 修改并复核 | 保留原句/原结构与实际改动，受影响总结、引用和 notes 一并检查；开放的实质问题不以工程 PASS 抵消 |
| AC-N6-07 | 本轮实际改动视觉布局、SVG 或 notes；或仅完成内容任务 | 重新生成受影响输出并检查 | 视觉声明有真实当前渲染支持；notes/局部SVG修复不无故重生整套图；未做视觉时不宣称视觉已改善 |
| AC-N6-08 | 方法版本已变或历史稿被作为问题输入 | 继续旧任务、准备新任务及引用历史结果 | 沿 N3 保留旧方法身份，正式创建适用新方法的任务；历史失败和已关闭问题保持原记录，不重标为当前首稿效果 |
| AC-N6-09 | 当前任务完成了适用检查，但没有用户试用、听众或真人计时 | 判断交付与本卡状态 | 普通交付按当前 Agent/Runtime 政策继续；不新增这些门槛；工程、实际应用、具体效果及未执行观察分别陈述 |
| AC-N6-10 | 方法/代码已完成定向验证，真实任务成果和问题修复可取得 | 提交本卡关闭报告 | 提供实际 diff、完整稿/成果、修复证据与有边界的结论；真实应用未完成则明确未完成，不用“测试全绿”或空台账宣布关闭 |

## 9. 验证计划

### 9.1 工程定向验证

方法文案修改本身不需要写逐句字符串镜像测试。仅在有具体风险时补验证：

- 资源打包：当前实际安装能取得修改后的 canonical 文件，SHA 与清单一致。
- 方法派发：复用 N3 的方法选择和旧任务兼容验证，不为 N6 复制一套同功能测试。
- 读取投影：复用 N4 的全文/紧凑等价检查，确认完整来源、Page 和必要限定仍可读取。
- 若新增了文本测量、表格布局或 notes 处理逻辑，针对发生过的具体问题测试真实转换/渲染；保留不同字号/物理尺寸的合理正例。
- 若修改输入/内容更新路径，仅对被改依赖的正确失效、未受影响对象复用、取消和重放做定向验证。

当前测试命令、环境、实际结果与是否跳过需要 Codex 核验。不要为了增加测试数量跑与本卡无关的整套真实生图任务。

### 9.2 正常任务验证

实际执行至少一项完整约定范围的正常内容工作，材料可为公开/中性且自包含。它是本轮交付验证，不另建成对实验制度；可复用其他任务已经需要的真实工作，避免重复费用。

验证需检查源材料支持、页职责与推进、关系/案例/取舍的实质内容、客户可见正文完整性，以及适用的物理/文件结果。发现局部问题后直接修复受影响对象，并给出修订前后可核对的成果。

如果需要展示方法效果，可以展示真实改句、单元格和连续页变化，并说明它们解决了什么任务问题。没有可比首稿时，结论限定为“本轮当前任务已应用并完成这些修复”，不补造性能比较。

## 10. 交付清单与完成裁决

| 交付 | 内容 |
|---|---|
| 实质方法变更 | canonical diff、实际问题及适用边界，必要的完整正反例 |
| 固定输入与任务简述 | 来源版本、任务事实、已有决定、使用范围及公开/合成身份 |
| 完整稿与适用成品 | 本轮首份完整稿/修改前稿、当前稿；约定范围内的真实文件 |
| 问题关闭证据 | 具体 Page/atom/关系、旧/新文本或几何、实际修订和复核 |
| 工程验证记录 | 准确候选/安装、方法 hash、实际命令/结果及跳过原因 |
| 效果说明 | 本次实质改善、仍有问题、可推广的条件与尚未验证的范围 |

完成裁决必须同时满足“方法确有实质改善”和“真实正常任务已应用并检查”。工程已通过而效果应用尚未完成时，分别报告，不将整卡标为完成。普通客户交付则继续按该客户任务的当前适用检查判断，不因内部希望积累更多质量样本而新增阻断。
