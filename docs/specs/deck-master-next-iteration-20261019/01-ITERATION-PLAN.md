# 01 完整迭代方案

## 1. 本轮目标

将当前 RC3 推进为更可靠、上下文更精简、专业方法能被正确派发和应用的 RC4 候选。保留现有主架构，集中修复已确认的边界缺口；由正常任务与实际成品检查证明效果改进。

本轮结束时应有五种可观察结果：

1. 输入更新在丢失缓存、丢失响应和跨入口重试后，仍能准确判断是否提交过；旧合法请求保持兼容。
2. 安装或回滚被中断后，可以根据持久记录恢复一致状态；用户及其他工具拥有的路径得到保留。
3. argument 提案满足已约定的连通结构；内容 Review 实际获得内容方法与校准依据，旧任务不被静默换方法。
4. 支持新协议的 Host 不再重复获取同份方法正文；历史操作查询避免每次重新解析全链大对象，事实可信度不下降。
5. 实质方法改进已在正常完整稿中应用，具体缺陷经修复与复查；活动文档准确描述当前入口、版本和恢复流程。

## 2. 六项工作与优先级

P1/P2 是本轮排期优先级，不替代原专业内容 F0–F3 或历史 AC/CQ 体系。

| 工作 | 优先级 | 要解决的用户问题 | 必须交付 |
|---|---|---|---|
| N1 输入更新与操作恢复 | P1 | 已执行操作丢回包后无法可靠找回；同一拒绝在不同入口解释不一致 | 共用恢复解析器、原子 receipt、新旧输入适配、HTTP 错误一致性、特定 SDK 快照读修复 |
| N2 安装中断恢复 | P1 | 激活在四 Skill 同步中断后可能留下混合安装 | 安装事务记录、阶段恢复、显式事务 ID、所有权保护与进程级中断验证 |
| N3 内容结构与 Review 派发 | P1 | 结构不完整的 argument 能保存为提案；内容 Review 获得的方法不完整 | 连通校验、按实际 review_units 派发、准确方法清单和旧任务策略 |
| N4 上下文与历史读取 | P2，合同先行 | 重复方法正文、全量源摘录和历史解析增加上下文与 I/O 成本 | N4A 显式 v2 上下文投影；N4B 可信派生索引与增量验证 |
| N5 文档与版本入口 | P2，可提前 | 新读者被旧路线、本机假设、多入口状态带偏 | 活动入口统一、历史标识、轻量文档守卫、候选版本与交付说明 |
| N6 首稿与返修效果 | P1，与工程并行准备 | 方法虽然存在，实际首稿与返修效果仍需落地 | 正常任务缺陷识别、实质方法/布局改进、完整稿与实际产物复查 |

## 3. 范围边界

### 保留

- 单一 CLI、loopback Workbench、现有 Python 服务层。
- 不可变对象、项目 current revision、CAS 和已有操作 receipt 合同。
- 已有协作、任务、候选、决定、采用和审阅事实的权限边界。
- Master/Content/Design/Review 四 Skill，方法唯一可编辑来源继续为 `skills/deck-master/references/`。
- 原始图片不可变，真实 SVG/PPT 导出，内容、图、单位、限定、notes 与页面依赖关系。
- 当前 CI 单元、真实渲染、浏览器、installed-wheel 与离线检查职责。

### 本轮不扩展

不建设第二套编排引擎、内置模型 provider、通用事件总线、云端数据库或新的业务状态中心；不按行数拆完所有大文件；不重新绑定 PPT Master；不重写 Git 历史或清理用户项目；不借 N4 压缩掉正文与原图；不把人类专业审批设为所有任务的默认条件。

必要的小型抽取只围绕已经重复且被本轮修改触及的快照加载、receipt 解析、方法解析与上下文投影。新增模块须有多个真实调用方或清晰的边界责任，不能仅为目录整齐搬家。

## 4. 实施节奏

推荐按“接口冻结 → 边界修复 → 性能与效果 → 候选集成”推进。时间为规划估计，不是已有实测。以一名集成 Owner 加最多三路执行为例，预计约 2–3 周；环境缺失、实际模型/渲染资源、发现新的阻塞会影响日历时间。**需要 Codex 核验**本机环境与实际吞吐后再更新日期。

| 批次 | 主要任务 | 并行安排 | 出口 |
|---|---|---|---|
| B0 基线与接口确认 | SHA/脏工作树/环境核验；固定 N1/N3/N4 接口；复制台账 | 集成 Owner；其他执行者可读代码与准备证据 | 所有执行者对同一接口、旧数据策略和 AC Owner 签收 |
| B1 优先修复 | N1、N2、N3；N5 活动入口草案；N6 选材与初稿问题定位 | 三条工程线，N5/N6 可由相应 Owner 在不冲突文件上准备 | 输入/安装/内容边界均具正反例，不再留隐式协议决定 |
| B2 降低成本并改进效果 | N4A 接 N3；N4B 接 N1；N6 实施改进并重做受影响内容 | N4 内可拆两路；方法正文最终由 N6 Owner 统一提交 | v1/v2 对照成立；索引冷热证据；方法改进进入实际任务 |
| B3 候选收口 | N5 版本更新、installed 包一致性、影响回归、实际文件检查、结论 | 集成 Owner 收口，原 AC Owner 审阅证据 | 准确候选 SHA/tree、完整台账、已知限制和可执行交接包 |

不能把 B3 的“所有工程验证通过”作为允许 N6 开始的前提。N6 可先使用可访问的既有稿或当前普通任务，固定首份完整稿或本轮修改前稿及问题清单；不强制额外重跑 RC3 基线。后续方法变化后必须确认新任务消费了新 hash。

## 5. 开发投入建议

以下是相对投入建议，便于保护效果工作不被工程清理挤掉；不是精确工时承诺。

| 类别 | 建议投入比例 | 分配理由 |
|---|---:|---|
| N1 + N2 稳定性 | 30% | 先消除重试和中断带来的实际操作不确定性 |
| N3 内容合同与派发 | 15% | 使已有方法与结构约束落到正确入口 |
| N4 上下文与查询成本 | 20% | 降低 Agent 阅读负担和重复 I/O |
| N5 文档与交接 | 10% | 清理活动入口，同时保持历史证据可追溯 |
| N6 实际效果 | 25% | 保证至少有一条完整的“缺陷 → 改进 → 实際产物复查”链条 |

若出现排期压力，先缩小 N4A 覆盖的可协商入口或延后确认无引用的历史归档；不能删除 N1/N2 失败恢复用例、N3 旧任务兼容验证或 N6 的实质应用。任何缩减需要在执行台账说明，不能保留原验收措辞再填 PASS。

## 6. 架构和代码冗余的治理方式

现有大模块和依赖网说明职责边界有继续收敛的空间，但本轮不以模块数量或行数作为成功指标。

- N1 把新旧输入更新汇入一个可恢复的提交核心，适配层承担旧 ID/digest/response 的兼容。
- N3 把方法选择与旧任务解析集中为一个权威来源，Skill 路由和 Workbench 不各自拼接清单。
- N4 复用已提交快照与操作解析边界，移除同一响应中的正文重复和双重历史扫描。
- N5 对真正无活动引用的文档/声明做归档，保留 schema 镜像、运行 UI 资源和用户材料。
- N6 仅修改有实际失败或缺口依据的方法和产物，不通过增加大量规则段落假装方法完善。

每次删除或抽取要回答：原消费者是谁、现在依赖谁、什么回归证明行为保留。无需引入全仓循环依赖清零之类新目标。

## 7. 效果衡量

| 维度 | 本轮可承诺验证的目标 | 不能据此声称 |
|---|---|---|
| 恢复 | 已提交请求可准确重放，冲突和不可验证历史诚实拒绝 | 任意外部数据损坏自动恢复成功 |
| 安装 | 支持的中断窗口可恢复到已核验一致状态 | 未测试平台上与系统掉电条件下绝对安全 |
| 内容 | 新 argument 连通；实际 Review 方法清单正确 | 连通自动证明论证有效 |
| 上下文 | v2 方法正文去重，源全文可按固定版本取回 | token/延迟降低比例可直接推广到所有客户 |
| 历史 | 冷启动全链验证，热态避免全量 JSON 解析，新增历史增量处理 | 任意情况下 O(1) 磁盘访问 |
| 文档 | 活动入口无矛盾，版本与安装说明可核验 | 归档总量必须减少某个百分比 |
| 成品 | 发现的问题经过实质改进并在实际稿件/文件中复查 | 未经对照即可声称总体成功率提高 |

## 8. 完成与后续候选

“RC4 开发完成”需满足本包所有适用强制 AC、当前候选必要 CI、安装/协议一致性，以及 N6 的实际改进应用和约定范围内适用产物的检查。具体见 [05-ACCEPTANCE.md](05-ACCEPTANCE.md)。

若模型或渲染资源确实无法获得，可交付已完成的工程候选和仍为 BLOCKED/NOT_RUN 的效果项，继续完成不受影响工作；不能把工程候选称为本轮全部完成。

本轮结束后再根据证据决定下一轮是否需要更深的 service/tasks 解耦、更多生产效果优化或发布准备。当前不预先承诺正式 1.0.0 日期。
