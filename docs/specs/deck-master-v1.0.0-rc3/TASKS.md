## 1. 启动边界

RC3-00 已接收开发基线，当前处于实现后的收口阶段；下面描述接收条件，不表示基线仍为空。RC3-00 接收的是修复结果，不重复实施上游修复。RF01–RF06 缺一项关闭证据、最终 CI 尚未覆盖最终提交，或必要接口不一致时，接收保持未通过并具体列明缺口。

一旦 RC3-00 通过，可开始 RC3-04 的前置切片、RC3-01 的方法补强和 RC3-02 的编译交付。RC3-01 的实际首稿评价需前置方法/审查入口可用。RC3-03 无调用准备可并行，正式试作需固定合格内容。

## 2. 并行与集成

| 可并行 | 必须保留的顺序与责任 |
|---|---|
| RC3-01 内容方法、RC3-02 compiler/native notes | 方法正文归内容线，文件编译归备注线；共享 Page/输出依赖修改先约定接口 |
| RC3-03 无调用投影准备、RC3-01 内容补强 | 真实试作先固定正文；设计不得补写论据或静默缩减 |
| RC3-03 制作保真、RC3-02 交付收尾 | 同一编译/回读路径由集成责任顺序接入并验证，避免各做一份依赖实现 |
| RC3-04 独立适配层准备、RC3-01/02/03 | service/gate/任务绑定的写入由统一集成责任协调；不用 UI 自存另一套认可 |
| RC3-05 检查准备与记录整理、前序实现 | 真正运行证据只在能力可用、输入冻结后产生；不能提前填写 pass |

各实现线使用独立分支/工作树和 checkpoint SHA；不要求机械固定 Agent 数量。前后依赖以卡片输入/输出为准。任何并行任务必须明确输入、输出、共享文件责任和合流测试；具体执行范围由当前用户任务授权；规划文本本身不启动 Agent 或新产品分支。

共同高风险边界只保留一个实现：实际授权绑定、前审资格结论、真实写集合、共享预算根、输入协调例外和派发 gate。后续卡消费同一 service，不再各自实现第二份。

## 3. AC 关闭与卡片交接

原 AC 的唯一能力 Owner 不变。RC3 执行卡负责汇总其指定 AC；其他卡可以贡献证据。完整映射见 [TRACEABILITY.md](TRACEABILITY.md)。

工程出口允许移交已可用接口与真实产物，不自动把 L2–L6 标为通过。比如 RC3-01 可交固定合格页稿给 RC3-03，最终稿件与成品检查由 RC3-05 汇总并回填原 M/U 条目。RC3-04 的前置切片完成只证明必要能力可用，不关闭 H01–H03。

既有不受修改影响的证据，可按精确候选依赖引用复用；新增 CQ、行为变化和最终安装必须补当前证据。每次合流记录输入/输出 hash、准确 SHA、适用 AC、运行环境、失败修复、未运行层与下一责任。

## 4. 提交与版本

卡片可拆独立可审查提交，不固定“一卡等于一个 PR”。当前三 PR 的修复、RC3 规范、方法、notes、设计、入口与验收记录应能独立定位。最终合流必须核对代码树与受测树一致；父分支更新或 squash 后不能沿用旧 PR 绿灯直接宣布通过。

目标标识为 V1.0.0-RC3。当前包版本为 `1.0.0rc3`，PR120 已合并。RC3-04 保持源码、包元数据、方法资源和安装 manifest 一致；RC3-05 核对实际候选与成品，给出当前结论。生产激活、发布和用户项目写入不因卡片文档存在自动发生。
