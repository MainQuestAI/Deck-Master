# 公共内容方法｜从任务与资料写成专业完整稿

这份方法用于判断和实际写作，不是每次必须填满的字段表。正式结果是完整 Page 正文、合理页序和能支撑表达的图示要求；不是另一套 brief、claim map 或 narrative plan。

## 1. 先确定交流任务

从当前工作单和既有讨论明确：受众已有认知、这次需要理解或判断什么、材料因此必须完成哪些职责。首次认识服务商时，身份、能力与经验可能是必要内容；已有合作的技术评审可以直接进入设计、选择和实施条件。

现场讲解与独立阅读会影响解释量和页面表达，但不自动决定开头、结尾和页数。公司能力、研究发现、产品说明和教学内容都可以是完整 Deck 的组成部分，不需互斥选择固定类型。

**好：**“本次只需理解服务范围与相关经验，所以用能力、机制与案例建立适配认知。”

**坏：**所有首次交流先诊断痛点，所有结尾都启动试点；或把现场稿固定成行动号召、阅读稿固定成风险说明。

## 2. 从资料中找出实际业务机制

与方案有关的过程需要讲清参与者、触发条件、必要信息、关键动作及交接结果。然后识别建议会改变哪一个环节。保留能解释业务价值的细节，不把流程画得复杂当成专业。

例如，一线缺少设备版本，总部接单后再补问。仅增加搜索框并不改变这次往返；把设备条件收集前移并按适用资料检索，才是可讨论的改变。仍需专家的复杂问题，应形成包含设备条件与候选资料的接手摘要，而不是虚构所有问题自动解决。

纯数据展示、日程页、产品参数说明不必套完整机制链；应准确说明如何阅读与使用。

**坏：**几个“AI、数据、平台”方块相连就称方案，或所有页面都是三张能力卡片。

## 3. 形成有用判断，而不是只复述

把分散观察与机制连接，提出会改变理解、优先级或选择的判断。区分事实、分析、设计建议和目标；推导写明理由，数字能复算，既有能力与新增开发不混写。

“54 条记录需补问版本”可以支持优先改善信息收集，但不能直接证明这是总成本最大的原因。若版本信息在现场根本无法获得，应该先讨论设备识别或现场采集，而不是继续坚持加字段。

不要求每份 Deck 都有惊人洞察，也不要求所有页面提出方案。准确说明一项陌生机制或澄清几个混淆概念，本身可以是专业增量。

## 4. 有真实选择时，说明推荐理由

比较可行替代的作用、条件与额外工作。给被推荐以外的方案真实优点，不制造陪跑选项。方向已确认时沿用决定，必要时补理由，不重新组织无意义投票。

资料搜索增强的优点可能是流程改动较少；门户内条件补齐与引用助手更贴近补问前移，但需要设备字段、资料适用范围映射和交互设计。推荐后者需要解释这些工作为何值得做，不能只说“更智能”。

无真实选择时不凑方案一二三；缺少成本数据时不填精确成本与 ROI。

## 5. 让页间关系完成同一次交流

每个实质页面承担一个清楚职责：解释、比较、证明、说明结果或教学。后续内容回答前面留下的必要疑问；材料放在它能支持的位置，避免相同案例在各章节重复出现。

公司能力、客户任务和建议路线可以成为一条主线，而不是分别生成三个小 Deck 拼接。复合内容按整体任务组织；说明型页面可以使用描述性标题，不能为了“每页结论”牺牲准确性。

页数上限约束篇幅，不授权补固定目录。内容放不下时调整内容组织、拆分必要表达，不把正文缩成不可读的小字。

## 6. 写完客户实际需要读的内容

“本页通过三个维度建立信任”不是正文。应写成具体、成立的能力与经验，例如：

> 我们提供技术资料接入、引用问答与现有门户集成服务。已完成的设备知识应用项目覆盖手册和维修工单接入、权限配置及上线培训。对于本次任务，这些经验可以支持资料和入口建设；设备条件映射与草稿写入仍属于需要单独设计和开发的部分。

正式要求与建议同页出现时明确区分。备注给讲述者补充必要解释，制作注释放 internal_only。图内标题、标签、脚注也是正文的一部分，不能只审主文字区。

“不接管生产控制”等边界只有影响当前理解或选择时才进入主线；通常可在相关方案处简洁说明，不自动占一页。CTA 同理。

## 7. 审阅后实际改稿

读取来源、完整正文和实际成品，找到具体错误后完成修改。判断是哪一层出了问题：内容不成立、输入投影丢失、原图还原偏离，还是 PPT 转换错误。不要通过降低要求、删除困难内容或重签参考图把失败变成通过。

**坏的返修：**“P03 建议增强专业性。”

**好的返修：**“P03 将草稿写入描述为公司已实现能力，但能力资料仅证明只读集成。将该句改为本期新增设计，补充权限和人工正式提交关系；同时检查实施与总结页是否仍沿用‘完全只读’的旧说法。”

正常首稿可以有内部自主编辑；用户收到后需要替系统重建主线、补写核心论证，不算已经达到业务审阅门槛。工程通过、人类认可和跨任务适用范围分别记录，不互相替代。
