# Deck Master 内容与协作流程规范 v1.2

> 状态：设计规范，待实现与分层验收。本轮只授权整合评审及编写开发文档；本规范不代表产品已实现、真实用户已认可，或已获真实客户项目生产授权。

## 1. 目的、基线与适用范围

本规范解决一个具体问题：用户给出材料后，系统必须先建立适用的内容方向、稿件和设计依据，并在有效委派范围内推进，最终让用户得到可直接使用的作品。文件生成成功、审批记录齐全和内容可用分别验收。

本规范固定产品选择，供开发直接落实。实施人员不应再次以“D01–D06 尚待决定”为由自行选择相互矛盾的产品行为；实现约束确实无法满足时，应以明确的规范变更记录处理。

- 实现审查基线：`af9fd7a6b4d08f753d2f16536a03f386384f49d2`。
- PR106 文档审查基线：`9797f9e25fbc20880752933be6324b879783603b`。
- PR106 在本轮复核时只有文档变更；本规范描述的是拟实现行为。
- 本规范综合 PR106、前轮静态审查及两份上传评审；上传评审的个人环境与作者自述复跑不作为本规范独立运行证据。
- 后续代码、测试、安装和真实 Host 行为需要 Codex 核验；合成案例通过不得标记为真实生产验收通过。

范围包含新建、仅策划、仅写稿、仅口播、设计试作、完整制作、局部修改、只读审查和续作。保留现有 Store、Task、Artifact、CAS、候选采用、输入失效、晚到结果和生产核心。

范围不包含恢复旧 18 Skill Suite、另建编排引擎、企业审批平台、长期自动学习、强制私有资料库，或借本轮规范启动客户项目。

## 2. 固定产品决定

| 编号 | 本轮决定 | 实现必须体现的结果 |
|---|---|---|
| D01 | 公开四个 Skill：`deck-master`、`deck-content`、`deck-design`、`deck-review` | Content 同时公开规划与写作子意图；不把 Writer 职责重新塞回 Master 的隐式 compose |
| D02 | 自动推进是 Master 的委派执行模式 | 自动模式不另设 Skill、状态目录或宽泛的“已批准”开关；每步读取同一 Runtime 资格结果 |
| D03 | `live` 默认 cues，明确要求逐字稿时用 verbatim；`read_alone` 默认 none | 口播用途与正文用途分别建模；未提供用途不能无条件套用 live 默认值 |
| D04 | Narrative、ContentPlan、Page、Design 各自拥有不同事实 | Narrative 管语义；ContentPlan 管映射与预算；Page 管上屏和逐页口播；Design 管视觉规则，禁止正文平行副本 |
| D05 | 内容与设计采用双循环，生产绑定不可变快照 | 设计可行性先介入篇幅，真实样页绑定完整代表页；不在完成全稿后才首次发现放不下 |
| D06 | 新建 Deck 项目统一采用 `workbench.v3` 及本规范协作资格 | CLI、Studio、聊天 Host 不得因默认参数不同而跳过 ContentPlan 或资格校验；旧项目不伪造历史批准 |
| D07 | 新论证全套生产默认采用 `independent_model_or_human` 内容质量 profile | 独立内容审查与最终人类专业复核政策分别满足；降级须有明确依据，不能从普通“继续”推得 |
| D08 | 决定采用、范围授权、文件认可分开 | 采用样页不扩张范围；允许交付不等于已审阅未来文件；已有有效委派必须复用 |

四个 Skill 是本轮范围选择，不是“四个必然优于一个”的经验结论。独立调用、自然语言路由、Master 调度和恢复调用均须通过相同的职责测试。

`workbench.v3` 是新建项目默认值，不是通过省略参数即可关闭协作资格的可选开关。只读外部文件审查不必为了输出报告而创建完整生产项目；旧项目的兼容读取和显式迁移按 [MIGRATION.md](MIGRATION.md) 处理。

## 3. 角色、方法与交接

### 3.1 公共职责表

| Skill | 输入与入口 | 必须使用的方法 | 可审查产物 | 完成本次职责的条件 | 下一责任 |
|---|---|---|---|---|---|
| Master | 新任务、续作、修改、范围不明 | 读取现有事实；识别本次意图；复用决定；分析影响范围；消费 Runtime 允许动作 | 本次任务理解、范围、阻塞原因、待用户决定项、下一动作 | 本次范围已完成，或需要一个具体外部决定/证据 | Content、Design、Review 或内部 Producer |
| Content | 材料、研究报告、确认稿；content_only 下的 plan_only、write_only、speech_only、content_full | 来源分层；受众目标；论证与证据；结构与篇幅；逐页写作；条件性口播；具体返修 | Narrative、ContentPlan、Page 正文/口播及其只读投影 | 请求的内容产物完整；必要未知有处置；审查范围和接受依据清楚 | 用户决定、Design、Review 或返回调用者 |
| Design | 页面职责、代表正文、模板、品牌参考、仅试样页 | 信息关系判断；密度与阅读距离评估；低成本版式可行性；代表样页覆盖；视觉一致性 | Design 方案、recipe、样页候选、覆盖范围、布局理由 | 获得适用的设计依据，或请求的试作产物已返回 | Content 返修、样页决定、Producer |
| Review | 项目产物、外部文件、具体审查范围 | 检查事实与推论；任务适配；论证；口播；页序；视觉；交付证据；定位责任层 | Findings、证据、严重度、返修责任和验证边界 | 已完成约定审查；未完成维度有明确原因；未冒称用户接受 | Content、Design、Master 或交付判定 |

每个 Skill 必须声明 `Use when`、`Do not use when`、允许产物、退出条件与下一责任。入口只转述“运行 continue”而没有方法和独立退出产物，不得发布。

### 3.2 Writer 的保留方式

Writer 是 Content 内部有明确工作单与验收条件的专业职责。本轮不单独发布第五个 Writer Skill，但以下请求必须可直接调用，不能强制先做完整策划或 PPT：

- “按这个确认大纲写完整逐页稿”：`write_only`。
- “把已确认内容整理成适合新员工的阅读稿”：`write_only`，先检查受众变化是否已授权。
- “只给这六页写逐字讲稿，不动屏幕内容”：`speech_only + verbatim`。
- “只改第三页的解释段”：限定页面与字段的写作修改。

写作完成后返回稿件和检查结果；没有整套制作范围时不能自动进入样页或生图。规划和写作可以由同一 Host 执行，但不能被压成无法检查中间论证的一次全稿接纳。

### 3.3 内部职责与运行层

- Sourcing 保留为 Content 方法：核对来源权威、版本、适用范围、材料冲突及证据缺口。来源位置有效不等于主张被证明。
- Producer 为授权范围内的自动生产模式：blueprint、SVG、原生 PPT、回读、预览与修复。
- Builder 为 Producer 内部编译职责；不得自行改变 Page 正文以便编译或排版。
- Repair 由 Master 分配到问题所属层；不另建跨项目修复状态机。
- Runtime 是项目事实、资格、任务、结果、调用和失效的唯一权威，不是第五个 Skill。
- Studio、CLI 和聊天 Host 是适配器：展示同一事实、采集真实指令、提交任务结果；不私存“用户已确认”或自己的自动推进状态。
- 安装、doctor、升级继续作为运维命令；不成为所有内容任务的必经业务阶段。

## 4. 内容产物及唯一事实源

### 4.1 权威边界

| 产物 | 权威内容 | 最小语义内容 | 明确不承担 |
|---|---|---|---|
| 输入与 Brief | 用户实际提供的目标、约束、材料和有效委派 | 受众、用途、目标、硬约束、来源版本；未给出的值标明未知或建议 | 把 Host 推测写成用户已确认 |
| Narrative | 内容论证或讲解的语义模型 | 交流任务；受众起点/目标；稳定节点；证据、限定和逻辑关系；必要未知 | 再存一份可独立修改的逐页全文 |
| ContentPlan | Narrative 到篇章与页面的实现计划 | Narrative 引用；章节/页面职责；节点映射；页数/时间/密度预算；口播政策 | 复制 central claim、argument nodes 或另造论证真值 |
| Page 的 customer_visible | 真正上屏的完整内容 | 标题、正文、图表文字、标签、单位、来源和必要限定；语义映射 | 用备注补救缺失的关键上屏含义 |
| Page 的 speaker_notes | 当前页口播内容 | cues 或 verbatim；与当前 Page 和语义节点对应 | 成为第二份可覆盖上屏内容的稿件 |
| Design 方案与 recipe | 信息表达、跨页视觉规则与适用范围 | 关系、层级、密度、样页、适用/未覆盖页型、当前内容依据 | 复制全文，或自动删改业务结论 |
| 制作说明 | 实现页面所需的内部指令 | 资产、图式、层级、约束、制作方法 | 混入客户可见正文或伪装证据 |

Narrative 的节点可以是事实、主张、解释、规范、步骤、例子或练习，不强制所有任务都拥有销售主张、异议清单或 CTA。节点的必需关系由交流任务决定。

事实、推论、建议、目标、规范性要求必须可区分。规范由适用规则支持，观察由数据支持；观察到的问题不能自动推出某项规则或收益承诺。

### 4.2 投影与修改

“论证稿”是 Narrative 的人类可读投影；“完整逐页稿”是当前页序与 Page 的投影；“完整口播稿”由当前页序与 speaker_notes 生成。Markdown、导出文本和预览都不能成为第二份独立事实源。

用户对投影提出的修改必须解析为所归属对象的 change candidate，展示具体差异，再按现有接纳机制更新。不能只改导出的 Markdown 而保持项目对象不变。

ContentPlan 可以在 Page 尚未生成时表达拟议页序。Page 建立后，当前文档页序为实际顺序权威；计划与实际顺序的改变必须在同一次接纳中同步或明确标记计划已失效，不允许两个可独立编辑的“当前页序”。

Page 拆分、合并、重排须保留或迁移语义节点映射。口播同步按 page ID 处理；不能按旧页码把上一页的讲稿误配给新页面。

### 4.3 已有确认稿的替代路径

满足以下条件时，用户确认稿可代替重新生成完整 Narrative 的前置要求：

1. 有实际稿件版本及其来源，且用户已明确说明采用该稿件。
2. 受众、用途和本次范围与确认依据兼容。
3. 没有新材料使关键结论失效，没有未处置的正式要求冲突。
4. 本次动作没有超出“照稿制作”或其他已有授权。

系统仍应生成必要的页面/语义映射索引，标明 `imported` 或 `derived`。索引只是对已给稿件的组织，不得回写成“用户曾确认这份新建 Narrative”。没有证据的历史决定保留为 unknown。

只做格式转换、局部改字或只读审查时，不得为了补齐新字段而强制用户重建论证。若本次修改改变中心目标或证据关系，则仅对受影响语义重新进入内容流程。

## 5. 输入路由与范围

### 5.1 路由表

Runtime 的 canonical `request.intent` 只有 `full_deck`、`content_only`、`design_trial`、`review_only`、`edit`。`content_intent` 只有 `plan_only`、`write_only`、`speech_only`、`content_full`，在非 content_only 请求中为 null。`resume` 是对当前请求的操作，不是新 intent。

| 用户实际意图 | Runtime 映射 | 初始可做的工作 | 正常退出产物 | 不能隐式扩张到 |
|---|---|---|---|---|
| 模糊材料启动 | 按用户所求产物归入 full_deck 或 content_only；阶段为 framing | 读材料、整理冲突、形成任务理解和候选方向 | 理解摘要、关键问题、建议路径 | 方向无依据时直接写全稿 Page 或整套外部生产 |
| 只做策划 | content_only + plan_only | 受众目标、论证、证据和篇幅方案 | Narrative、ContentPlan、可决定的取舍 | 完整写稿或制作 |
| 只写逐页稿 | content_only + write_only | 消费确认方向或确认稿，写请求的页面内容 | 完整逐页稿及内容审查 | 口播、设计或全套制作，除非范围包括它们 |
| 只写口播 | content_only + speech_only | 读取当前稿件，写 cues 或 verbatim | 逐页口播及整稿投影、时间估计 | 修改上屏正文或重建全稿 |
| 完整内容生产 | content_only + content_full | 在内容范围内完成理解、论证、逐页稿和约定口播 | 完整内容包及审查 | 视觉生产、PPTX 或外部发布 |
| 仅设计方案/仅试样页 | design_trial；由 scope 区分纯方案与外部试作 | 设计可行性、限定试样 | 方案或指定样页、覆盖说明 | 采用候选或扩大页集合 |
| 完整制作 | full_deck | 依有效方向、内容和视觉依据执行全流程 | 范围内完整作品与分层证据 | 未授权的第二用途版本、外部发布或额外范围 |
| 局部修改 | edit | 分析影响，修改允许页面/字段 | 差异、受影响产物与必要复核 | 无关页重做、未经授权的主线重写 |
| 只读审查 | review_only | 读取指定产物并审查 | 具体 Findings 与验证边界 | 自动修复、生产、采用候选 |
| 续作 | 对现有 request 执行 resume 操作 | 读取当前任务、决定、撤回和已完成范围 | 有效的下一动作或已完成结果 | 复活撤销授权，或重新执行已完成成本动作 |

`design_only`、`trial_only`、`local_revision` 等可以作为用户语义描述或路由别名，但必须映射到上表，不能持久化为另一套并行枚举。生产任务的 `executor`、是否需要决定、阶段、范围和采用策略是不同维度，不能压成一个“human / review / production”枚举。字段及 service 行为以 [CONTRACTS.md](CONTRACTS.md) 为准。

用户要求严格只读时，review_only 必须使用不修改项目状态的报告路径；不在项目中新增 Review、Task 或控制记录。报告可返回会话或用户指定的项目外位置，不能为了保存审查结果而违反只读范围。

### 5.2 未指定、默认与委派

未指定受众不必然触发固定问卷。先判断其是否改变论证或表达：如果材料和任务已经足够明确，可以提出可见假设并在有效委派内推进；如果存在培训、立项、对外介绍等互不兼容路径，应停止依赖该选择的工作。

关键问题每轮优先不超过三个，但不是硬凑三个。每个问题必须解释会改变的产物或取舍；已知问题不重复问。能由已有材料核实的事实先自行核实。

“做一套 PPT”表达了作品意图，不自动提供所有缺失的业务决定。“按你判断先做一稿”可以授予有边界的探索范围；它不等于用户认可该稿内容或允许任意额外调用。

## 6. 专业内容方法与退出条件

### 6.1 从材料到任务理解

Content 先区分正式要求、可验证事实、历史参考、能力说明、用户设想和模型建议。每项关键材料保存来源版本与适用范围；冲突不能由“较新文件一定正确”静默解决。

任务理解必须回答：谁在什么场景使用，受众已知什么，使用后希望理解/判断/执行什么，本次要交付什么。材料不能回答时，产出明确的问题或可委派假设。

退出产物是可审查的理解摘要和分歧，不是空字段列表。没有足够依据的方向保持 proposed；来源整理可以继续，依赖方向的全稿写作不能继续。

### 6.2 从任务理解到 Narrative

根据任务选择方法，不统一套用销售叙事：

- 培训：目标行为、概念/步骤、边界情况、例子和练习反馈。
- 分析汇报：问题、方法、观察、解释、限制及结论。
- 决策建议：真实选项、判断标准、证据、代价与推荐条件。
- 独立阅读或参考：检索结构、定义、完整解释、前提与可定位来源。

每个核心结论必须说明支持它的事实或适用规则；没有数据的收益只能作为假设或验证目标。来源 locator 检查仅证明可定位，不能代替论证审查。

退出条件：目标与内容结构相容；关键推论没有无依据跃迁；限制进入对应论点；未决事项有影响与处置。教学或参考任务不因缺少商业异议/推荐页而失败。

### 6.3 从 Narrative 到 ContentPlan

每页应有一项可以说明的沟通职责，并引用实现的语义节点。章节不能只是材料文件夹名；页数不能由“每段一页”或固定模板章节凑出。

规划应检查：删去这一页会丢掉什么；上一页留下什么问题；下一页为什么必要；证据和限定在哪页完整呈现。不存在唯一正确页序的参考稿允许多条阅读路径。

退出条件：核心语义有覆盖位置；重复与缺口已处理；页数/时长/密度具有可行方案；关键页型已有设计可行性判断。

### 6.4 完整写作

Writer 必须写出所有客户可见文字，包括图表标题、数值、单位、轴标签、注释和必要来源。占位词、只有页面主题的提纲和“此处放结论”不满足完整逐页稿退出条件。

正文、口播和制作说明分别写作。关键限定必须出现在实际承担该主张的交付层；不能用观众看不到的备注纠正误导的标题或图表。

退出条件：所请求页面完整；语义映射无遗漏；主张与限定一致；没有因排版先行而删去必要信息；口播策略要求的内容已具备；具体内容审查问题已处置。

## 7. 内容与设计的双循环

### 7.1 第一循环：语义与可视化可行性

Narrative 初稿、页面职责与篇幅预算形成后，Design 即介入。使用真实代表内容检查最密证据页、机制/流程页和最关键表达，提出关系图式与低成本 wireframe。

这一阶段不要求先写完整整套稿，也不应启动整套外部生产。若用示意文字探索纯风格，必须标明其不能证明真实正文的密度适配。

Content 与 Design 联合解决放不下、讲不完、关系不清的冲突。若解决方案改变用户硬约束或业务结论，由 Master 判断是否在现有委派内；超出时交给用户选择具体取舍。

退出时形成方向依据：当前 Narrative、ContentPlan、预算与设计可行性。用户需要决定的是主线与实质取舍，可以与首次任务理解合并为一次有产物的决定。

### 7.2 第二循环：完整稿件与真实样页

完整代表页通过内容审查后，以真实正文生成样页。初始设计必须支持目标 Page 已存在而旧 blueprint 不存在的路径，不能要求先完成旧版整套设计才允许首轮校准。

样页选择依据风险覆盖，不固定“两页”或“三页”。优先覆盖最密页及具有不同信息关系的关键页；同一页可覆盖多个风险。已有适用模板和有效委派时，可以以覆盖核验代替新增样页。

每个样页返回正文依据、视觉图、布局理由、适用页型/密度和未覆盖范围。用户可只接受配色、只接受构图或只接受信息密度；单个维度通过不能自动投影为全部通过。

样页采用与全套生产授权分开。样页仍是候选时，不可覆盖当前采用版本；用户只试一页时，结果返回后本次范围即完成。

### 7.3 冻结的含义

“冻结”表示下游任务绑定一个不可变版本，不表示用户不能再改。使用以下顺序建立依据：

1. 任务目标与本次范围有有效依据。
2. Narrative、页面职责、篇幅和设计可行性形成方向基线。
3. 当前 Page 正文及必要口播形成稿件基线。
4. 适用 recipe、样页与覆盖判断形成视觉基线。
5. 生产动作绑定上述基线、具体范围和有效授权。

任何新稿件或新样页都不能反向把旧决定标为已认可新版本。样页暴露内容问题时回到对应 Content 层修改，按依赖选择性失效；不能以缩字规避返修。

## 8. 停顿、复用与变更

### 8.1 停下来必须展示的内容

| 场景 | 用户看什么 | 用户决定什么 | 可自主继续的工作 |
|---|---|---|---|
| 输入方向存在实质分歧 | 理解摘要、已知事实、不同方向及差异 | 受众/任务，或委派其中一个方向 | 来源整理、冲突识别、候选分析 |
| 主线或预算存在取舍 | 论证骨架、页职责、保留/删除内容、时间与密度差异 | 业务优先级或有边界的取舍权 | 已选方案内的措辞与普通布局优化 |
| 视觉依据不足 | 真实样页、覆盖与未覆盖页型、布局原因 | 接受哪些视觉维度，是否需要返修 | 已授权且不依赖该样页的其他工作 |
| 请求扩张生产范围 | 现有范围、新增页/版本/成本、原因 | 扩张、拒绝或限额 | 已有效授权且独立的任务 |
| 最终结果有未满足要求 | 当前文件、缺口、分层审查结果、可交付用途 | 必要的业务取舍或明确降级 | 已授权范围内可以关闭缺口的修复 |

不设置无条件的“每阶段都请确认”。方向、稿件、样页和最终交付可以由同一次明确委派覆盖不同后续动作，但必须保留各自对象与证据，不能合成一个全局 approved。

### 8.2 决定与范围的复用

已有有效确认稿、模板、业务选择和执行委派必须直接复用。系统先说明所沿用依据，只对新冲突提问，不让用户重复搭建主线。

“继续”只延续明确的当前范围；“颜色可以”只证明配色意见；“就按这版完成六页”可以同时表达稿件采用与限定生产委派。语义解析不能根据沉默或文件生成成功补出授权。

聊天消息和 Studio 事件均可承载真实指令；关键区别是可核对的来源和适用语义。由同一 Host 执行 `decision record` 并不会自动把自报信息变为独立认证；证据强度及降级行为由合同统一规定。

### 8.3 选择性失效

- 受众、任务目标或核心主张变化：重新评估相关 Narrative、ContentPlan、稿件及生产依据；可以保留仍适用的品牌规范。
- 仅措辞修订且含义不变：更新受影响 Page、依赖它的视觉/输出与审查；不撤销所有无关方向决定。
- 页数、时长或用途变化：重新评估页面覆盖、密度、口播和样页覆盖，不自动删除证据。
- 样式变化：使相关视觉依据失效；没有语义变化时不重建论证。
- 来源更新：找出依赖该来源的主张与页面，区分数值替换和结论失效。
- 范围撤回：立即阻止新的相关动作；已在途结果保留调用事实，按现有晚到规则不得重新采用。

拒绝提案不等于删除项目；取消一次任务不等于撤回全部委派；恢复旧 revision 不得复活已撤销范围。续作必须读取最新控制事实。

用户只授权局部改字而关联页出现矛盾时，可以完成已授权修改并展示具体跨页影响；不得未经授权重写其他页，也不能把保留矛盾的结果标为内容通过。

## 9. 页数、时长、密度与视觉的取舍

预算必须区分上限、精确要求、估计和建议。`page_limit = 8` 不能被解释成“必须做八页”；“正好六页”也不能只留在一段自然语言里而在结果接纳时不校验。

现场时长预算至少分开讲述、演示/练习、停顿和问答。不能以每页固定秒数直接推出可讲性；cues 的字数也不能作为全部讲述时长。

Content 负责说明删留如何改变理解与论证，Design 负责说明密度、图式、字号和阅读距离的影响，Master 负责是否超出委派。用户决定不可兼容的业务约束，不逐项决定字号和边距。

冲突时至少提供两条实际不同且可行的路径，例如保留六页但收窄目标、保留目标但增加页数、把详细证据移至仍可访问的附录。不得提供三个仅标题不同的假选项。

每条路径必须列明保留/失去的内容、时长、页数、上屏/口播/附录位置和风险。必要限定不能移到目标受众看不到的地方；增加页数不能突破用户硬上限后再宣称已完成原要求。

默认禁止通过低于本次场景可读下限的字号或隐藏必要证据来“满足”页数。具体可读性由样页在约定尺寸和使用环境下验证，不在所有项目中硬编码同一个字号。

## 10. 口播、阅读稿与交付

### 10.1 明确策略

| 用途 | 默认口播产物 | 页面要求 | 验收边界 |
|---|---|---|---|
| live | cues：讲述意图、要点、过渡与时间预算 | 可由讲述补充解释，但屏幕主张本身准确完整 | cues 可支持讲述，不得宣称已经提供逐字稿 |
| live + 明确逐字稿请求 | verbatim：自然口语的完整逐字内容 | 口播与屏幕逐页对应，避免逐字照读所有正文 | 估时明确标 estimated；排练后才有 measured |
| read_alone | none | 主张、解释、证据与必要限制可独立理解 | 不强制生产口播稿，不以备注补齐阅读缺口 |
| mixed | primary_use 必须明确；确定后默认 cues，明确不要讲稿可 none | 按已定主要用途写稿，说明另一用途的限制和讲述页集合 | 不声称单一稿件已分别优化为两种用途 |

mixed 的 `primary_use` 由用户明确指定或在有效委派内选定；没有依据时，展示 read_primary + cues 的推荐及取舍，不因输入只有 mixed 字样就把推荐写成已确认事实。read_alone 始终默认 none。

用户明确要求两套优化版本时，共用 Narrative 和来源，分别派生 live/read 的 ContentPlan 与 Page；范围、生成成本和验收分别记录。没有两版范围时，不自动多做一套，也不为此建立第二套状态机。

用户明确指定的产物范围优先于默认策略：“只写逐页上屏稿，不要口播”应采用 none；不能以 live 默认 cues 为由扩张明确排除的范围。

none 表示本次不要求新生产口播，不是删除指令。用户已提供并要求保留的原有备注必须保留；导入时若与当前稿件冲突，应报告具体差异，不能静默清空。

### 10.2 写作与修改

口播应有可讲的开头、页内解释和页间过渡。逐字稿不能只是把 bullet 用逗号连接；cues 不能冒称逐字稿。讲述者使用的自然表达可以不同于上屏表述，但事实和限制必须一致。

只改口播不应重做无关视觉；改变事实、主张或关键限制的口播修改必须触发与上屏内容的冲突检查。只改上屏稿也必须检查旧口播是否仍适用。

拆页、合页、重排后重新生成整稿投影与时间合计，并检查过渡和重复。过去的实际试讲时间只适用于当时稿件版本。

### 10.3 交付承诺

当范围含口播时，交付清单明确它位于 PPTX notes、单独可读稿或两者。本轮目标实现默认提供 PPTX notes 与整稿只读投影；用户仅要口播稿时可不生成 PPTX。

当前原生编译路径尚无已确认的 notes 投影能力，不能仅因 Page 存在 speaker_notes 就宣布 PPT 已带讲稿。实现必须覆盖 notes 写入、逐页映射、拆并重排和实际回读；详见基线证据。

## 11. 质量前置与判定

### 11.1 前置内容审查

新生成 Narrative 的 full_deck 在整套视觉生产前必须完成内容审查，审查对象包括任务适配、论证、证据边界、页面覆盖、推进和用途预算。候选方案或内容稿可以先作为待审稿返回，但不能通过字段齐全自行获得 full production 资格。

默认质量 profile 为 `independent_model_or_human`，由独立模型或独立人审满足。能力不可用时返回具体缺口及已有审阅稿；用户明确接受 host_self 降级后可以继续相应范围，但审查者身份和证据等级保持 host_self，不得标记 independent 或 human。

普通“继续”“你自己定”不得自动解释为取消既定独立审查要求。过去已明确委派审阅方式且仍适用时直接复用，不重复询问。独立审查缺口不得阻止返回用户请求的只读审查稿、探索稿或内容草稿。

已确认稿且未改语义时，做适用性与忠实性核验，不强制重建 Narrative。局部修改只重审受影响维度；exploratory 产物保持待审状态，不伪装正式接受。

`professional_review_required_for_delivery = true` 继续表示人类专业复核要求。独立模型、另一个 Skill 或 host_self 不能满足该人类要求；不同要求由明确 reviewer policy 表达。

### 11.2 具体阻塞与返修责任

| 问题 | 必须返回的证据 | 返修责任 |
|---|---|---|
| 目标受众或任务错配 | 原任务与当前主线的具体差异 | Content 任务理解/Narrative |
| 无支持的主张或因果跃迁 | 具体节点、引用、缺少的推导或限定 | Content 证据与论证 |
| 页面只剩标题或关键标签缺失 | Page 与缺失字段的实际内容 | Writer |
| 口播讲不完、跳步或与正文冲突 | 相关片段、版本与估计/实测记录 | Writer 与 Content |
| 多页重复、下一页无必要性 | 重复职责或缺少的逻辑连接 | ContentPlan |
| 图式误导、密度不可读 | 样页、使用尺寸及被误读的关系 | Design；必要时 Content 取舍 |
| 文件漏字、错图、notes 丢失 | 当前文件与源 Page/notes 的差异 | Producer/Builder |

Review 不能用空泛“加强逻辑”“更美观”关闭问题。每个阻塞必须有对象、事实、影响、建议动作和可验证的关闭条件。

结构检查、Host 自审、独立模型、人类用户认可、目标听众验证与工程通过分别呈现。用户点击接受是范围内的业务选择，不是自动证明主张正确、视觉可读或目标听众已经理解。

## 12. 验收原则与规范落地

完整运行合同、验收场景与开发任务分别见 [CONTRACTS.md](CONTRACTS.md)、[ACCEPTANCE.md](ACCEPTANCE.md) 与 [TASKS.md](TASKS.md)；内容样例见 [EXAMPLES.md](EXAMPLES.md)。下列产品条件不可删减：

1. 模糊输入返回有内容的理解/方向产物；没有把空字段问卷当作访谈完成。
2. 确认稿、模板与明确委派被复用；未发生为了满足新合同而重问已知问题。
3. content_only 的四类 content_intent、design_trial 和 review_only 各自完成后停止在请求范围。
4. 首次样页无需先制作旧 blueprint；采用、覆盖判断和扩展授权分别生效。
5. 8 分钟六页培训合成案例保留未知值/紧急程度的两个独立判断，不把缺字段数据写成效率收益。
6. 阅读稿不强制口播；逐字稿交付与 cues 有实际内容区别；mixed 的使用承诺可被分别验证。
7. 方向、稿件、视觉和范围变化按依赖失效；撤回后没有新的越权调用或旧结果采用。
8. 同一当前快照在 export、handoff、final-readiness 等入口得到相同的资格结论与原因。
9. 前置内容审查能够找出具体故障样例，不能只通过非空 observations 获得语义质量证明。
10. 真实使用评估记录用户是否被迫重建核心主张、论证顺序或页面职责，并区分任务变更与首稿错配。

已证实的人类专业复核谓词问题可以作为独立修复先行。专业产物样例与评价锚点先于合同冻结完成；所有生产入口必须消费统一资格后才能对外宣称流程已修复。

允许内部以只读资格计算观察差异，但不允许向用户发布“部分入口受控、其他入口仍可绕过”的过渡版本。安装包、方法文件、CLI/Studio 文档与新合同须在同一发布边界一致。

历史 v1.1 规格中“业务决定仅留在 Host”“不新增 Planner/审批”等与本规范冲突的 living 引用，应在实现时明确标注由本规范替代。保留历史记录，不让两份互斥规范同时约束当前实现。
