# 验收合同：内容协作与受控生产 v1.2

2026-10-18 用户纠正后的当前口径：PPT 交付按任务要求、来源内容与实际成品检查；不要求招募听众、固定人数试用、现场试讲计时或完成对照实验才能结项。普通内容审阅可由 Agent 承担；人工专业复核仅在本次明确要求的政策适用时需要。原实验与运行记录保留历史身份，不再作为默认发布门槛。

2026-10-14 起，执行与目标版本统一到 [V1.0.0-RC3](../deck-master-v1.0.0-rc3/README.md)。本文件仍是原 37 AC、13 CQ、F0–F3 与 L0–L6 的唯一验收权威；[RC3 验收规范](../deck-master-v1.0.0-rc3/ACCEPTANCE.md) 只编排交接和汇总，[追踪表](../deck-master-v1.0.0-rc3/TRACEABILITY.md) 不新增另一套通过状态。原能力 Owner 保留，后续卡可提供证据回填；工程交接不自动关闭最终专业 AC。

本文件定义开发完成与候选验收所需的判据，不在规格正文登记执行结果。原规格编写阶段的条目初始为 `not_run`；当前结果、准确版本与适用范围统一见[RC3 执行台账](https://github.com/MainQuestAI/Deck-Master/blob/62dfcfc5637f0bee2358074c4458047689dd5299/docs/reports/rc3/evidence-ledger.json)和[当前收口报告](https://github.com/MainQuestAI/Deck-Master/blob/62dfcfc5637f0bee2358074c4458047689dd5299/docs/reports/rc3/closeout-20261018/README.md)。源码、安装、实际文件和备注仍需各自的真实证据，不由规格文字声明通过。

每条 AC 只有一个负责关闭的工作包；其他工作包可以提供依赖证据，但不得分别维护另一套通过状态。工作包编号与 `TASKS.md` 一致。本文中的“必须”是本版候选实现的验收要求；不把新增设计描述为当前 main 已有能力。

## 1. 证据与失败规则

### 1.1 证据分层，禁止相互替代

| 层 | 证据提供者与对象 | 能证明 | 不能证明 |
|---|---|---|---|
| L0 结构与静态检查 | schema、引用、类型、固定 SHA 源码、安装清单 | 结构与依赖关系符合合同；某条代码路径存在 | Host 实际应用方法、内容正确、用户认可 |
| L1 Runtime 行为 | 正式 service/CLI/HTTP 入口的合成运行、事件与调用账本 | 拒绝、放行、范围、失效、幂等和晚到处理符合合同 | 实际专业写作和真实生产可用性 |
| L2 真实 Host 工作流 | 实际 Host 会话、实际工作单与结果、模型/工具记录 | 会提有效问题、复用决定、完成方法产物并遵守范围 | 用户无需重建主线、目标听众能理解 |
| L3 专业内容审查 | 明确身份的内容审查者；独立模型须有独立执行证据，人类须有真实来源证据 | 可以定位论证、证据、稿件和视觉表达缺陷 | 人类专业认可、用户接受和使用效果彼此替代 |
| L4 用户认可 | 任务 Owner 审稿、具体改稿记录、接受或拒绝理由 | 对既定任务是否适用，用户是否仍需重建主线 | 所有事实与工程都正确、听众真正理解 |
| L5 可选使用反馈 | 用户自愿提供的实际使用反馈；未安排时不需要 | 所反馈任务的实际体验与问题 | 默认验收前置条件、长期 ROI 或统计效果 |
| L6 文件工程 | 实际 PPTX、渲染、正文与备注回读、文件 hash、编辑检查 | 文件与当前约定稿件一致，可在所测环境使用 | 内容方向、论证质量或用户认可 |

这些层是并列的证据维度，不是可以压缩为一个平均分的阶梯。L6 可以与 L2–L5 并行开展。报告必须分别显示 `pass / fail / not_run / not_applicable` 及证据；不适用必须写明场景依据。

`host_self` 是作者自审。名称为 `deck-review` 的 Skill、换一条提示词或填写不同 reviewer ID，不会自动产生独立审查。独立模型也不会变成人类专业审查者。

附件评审者声称“独立复跑 P01–P05”仅记为**该评审者报告的执行证据**。在没有其可核对的运行日志、环境与输出前，不写成本轮已复跑；即使可核对，也仍属于 L1 合成探针，不升级为 L2/L4/L5/L6。既有 PR 的合成 fixture、文档校验和历史验收也不替代候选实现的新执行记录。

### 1.2 统一失败分级

| 级别 | 定义与实例 | 处理 |
|---|---|---|
| F0 事实完整性或控制权失败 | 越权开始调用；撤回后采用旧结果；伪造用户/人类身份；旧文件审阅解锁新文件；把缺字段比例写成节省比例；遗漏改变结论的限定 | 必须修复；任何一个未关闭的 F0 都禁止该候选发布。不能用其他高分、用户笼统“继续”或另一案例通过抵消 |
| F1 任务与主线失败 | 在固定输入和既定目标下，需要用户重定沟通目标、替换中心主张或重建章节级论证关系，才能用于原任务 | 必须回到内容责任修复；稿件与任务对照发现系统误解导致的 F1 时须修复，可以继续开发与复查 |
| F2 局部实质缺陷 | 可定位的一页缺解释、一个过渡无法讲清、一处密度妨碍阅读；修复不改变主线 | 修复后复核受影响对象。最终约定用途仍受影响时不得标为该用途通过 |
| F3 局部偏好或润色 | 不改变事实、范围、主线和可用性的措辞、颜色、间距等调整 | 记录具体位置与决定；可由有效委派自主处理，或作为明确接受的局部差异 |

“改了多少页”是负担指标，不是主线重建的独立判据。拆页、合页、用户新增材料或改变目标可能造成高比例改页，必须与系统误解分开归因。不得机械使用“超过 20% 页面改职责”判定所有任务失败，也不得用低改页比例掩盖中心主张错误。

本节是报告、任务卡、内容锚点、审查回执与发布汇总的**唯一 F0–F3 分级来源**。错误类型（如解释缺失、练习泄题、关系错位）与严重度分开记录；任何锚点不得再定义并行的同名 F1。逐项按事实/控制权影响、是否需重建任务主线以及局部修复范围判定，不按旧等级批量升降。分歧统一提交 AC-B03 的裁决记录，引用本节并说明依据；历史评价记录只保留原判，不充当新口径通过证据。F2 虽不必重建主线，影响约定用途时仍须修复，不得以“非 F1”放行。

### 1.2.1 方法效果诊断中的评价时点

以下仅适用于开展方法效果比较或作出相应效果声明时，不是普通 PPT 交付的额外前提。已有稿件的错误与修订仍如实保留。

1. **原始完整生成稿**：首次形成全稿的产物；如做方法比较，保留其版本与内部审阅前状态。
2. **首次交付 Owner 的完整稿**：允许此前按冻结预算进行有界内部编辑；记录自主轮次和输入。首次 Owner 审阅发生系统误解导致的 F1，永久保留该轮首稿失败结论，即使后来由系统动笔修好，也不能改称首次可用。
3. **返修后当前稿／方法复测**：前者只说明该产物当前缺陷是否关闭；后者必须在方法或实现修订后，从原始输入重新运行并独立记录。两者分列，不能用手工改好的旧稿替代方法复测。

区分用户新增材料、目标变化与系统误解。已发生的首稿失败不能覆写为通过；当前稿修复后可按 AC-U02/U05 复核收口。只有主张方法本身已恢复时，才需要相应重新运行的结果；不为普通 PPT 交付默认新增方法实验。

### 1.3 单条验收的证据格式

每条执行记录至少包含：AC ID、唯一 Owner、状态、实现 commit、基线/候选标签、输入包版本与 hash、实际入口、Host/模型/工具版本、运行范围、Given/When/Then 实际结果、前后状态引用、输出或日志引用、发现的失败及关闭证据。外部调用记录另含开始/完成/取消/结算事实，严禁只保存最好的一次结果。

不得以 `observations` 非空、schema 合法、截图存在或一个总分作为专业验收通过的充分条件。每个内容判断必须指向段落、claim、page 或实际画面及其来源依据。

| Q4 既有技术 Deck 与生命周期 | 使用固定内容的两份状态 checkpoint：只有 Page、没有初始 blueprint；以及已有交付文件与审阅的版本。包含 P05 单页试作、局部修改、样页后方向变化、撤回、重开会话、晚到结果与旧格式迁移事件 | “配色可以”只证明对应维度；“采用这一页”不等于整套授权；局改不能静默扩张；恢复旧版本不能恢复已撤回授权。合成人类回执仅用于协议测试，不冒充真实人类复核 | V07、V08、V09、V10、V12；新密度页覆盖 V11 |

### 2.1 三类内容锚点

每类至少保存一份可用候选、一份明确失败候选，以及从失败稿到可用稿的差异和评价理由。评价员先独立判定，再记录分歧和裁决，不能以“多数给高分”消除事实错误。

| 类型 | 可用锚点必须展示 | 明确失败锚点 |
|---|---|---|
| 培训 | 目标是形成可接手记录；未知值准确记录；紧急程度决定流转；用“普通工单版本未知”和“紧急工单版本已知”两个新情境检验应用 | “38% 工单缺版本，所以能节省 38% 成本”；“版本未知就一律紧急升级”；“其他 62 单完整”；答案先展示后把照抄计为掌握 |
| 决策 | 区分观察、机制假设、备选方案、条件、待验证收益。至少一个在当前只读边界内的真实替代，例如仅改采集表单，以免把助手增量当作已证事实 | 把范围外自动写入当作唯一对照来美化推荐；“唯一可见的成本”改成“唯一成规模的成本”仍无全局测量；从缺失率推出收益；提案参数冒称用户已批准 |
| 研究阅读 | 读者不听讲也能定位主要发现、样本/单位/适用范围和不可比之处；按证据强弱表达，不强制口播或销售结尾 | 不同样本指标直接排序；限制仅在备注；模板导致关键列/单位消失；读者必须靠作者补写主线才能理解 |

两份附件中的内容示例只能作为待审候选，不直接成为 golden。Q2 固定原文只有访谈中的可能机制与未测量边界，不把旧附件的“往返通常发生”提升为本套件事实，更不能推出“检索尚未开始”。另一评审的“38% 缺记录”也不自动证明这 38% 已发生补问，除非材料另有明确观察。示例时长必须分项相加，不能仅从页数判断。8 页中两页各 90–120 秒、六页各 45–75 秒合计为 7.5–11.5 分钟，尚未包含提问，不得直接称已满足 10 分钟。

### 3.2 T01：professional delivery 的已知缺陷

本组保持现有合同含义：`professional_review_required_for_delivery=true` 表示用户要求**人类专业复核**。独立模型即使是有效独立执行，也不能满足该布尔政策。一般内容前审的 `independent_model_or_human` 是另一要求，不得共用一个宽松 OR 谓词。

| ID / Owner | Given / When / Then | 失败条件与必留证据 |
|---|---|---|
| AC-P01 / T01 | **Given** 工程检查通过、当前 PPTX、human professional policy=true；**When** 正式提交当前文件与必要内容依赖上的 `professional_use/pass` 人类复核，身份与证据来源可核对；**Then** export、handoff-check、final-readiness 对同一快照给出一致的政策满足结论 | 只填 `kind`、`reviewer.id` 或 `seed=human` 不得成为正例。证据：正式提交路径、真实类型 fixture、文件/依赖 hash、复核范围、统一解释结果。协议 fixture 只能证明 L1，不能声明真实人类已看稿 |
| AC-P02 / T01 | **Given** 同一当前快照；**When** 分别提交 host_self/pass、tool/pass、independent_host/pass、人类 not_evaluated/needs_review/not_applicable、人类错误 kind（如 privacy）、旧 PPTX、人类证据缺失、缺必需依赖、仍有开放阻断项的记录；**Then** 三入口均不得满足 human professional policy | 任一负例解锁、空依赖被 `all([])` 当充分条件、只检查 `status != fail`、模型借 `professional_use` 冒充人类均为 F0。证据：各正式 API 路径的结果与未产生 delivery 输出的断言；不要只直接插 Store |
| AC-P03 / T01 | **Given** policy=false，或 delivery 因缺人类复核阻塞；**When** 查询状态或请求审阅用途导出；**Then** 依据其他有效条件分别显示工程状态、专业证据和交付状态；允许的审阅稿可取得且不被标成人类认可 | 用“工程 verified”覆盖 professional 缺口、因为没有人类而拒绝所有审阅稿、把默认 host_self 宣称为当前合同违约均失败。证据：同快照三入口与审阅用途结果 |

### 3.3 T02：决定、授权与迁移数据

### 3.4 T03：专业内容、写作与评价时机

本版新论证驱动的 `full_deck` 默认前置内容审查要求为 `independent_model_or_human`。不可获得合格审查者时返回 `needs_reviewer` 与可审查稿，不静默改为 self-review。用户可以明确将这项普通内容前审降为 host_self；需要记录具体要求、范围与版本，普通“继续/你自己定”不构成该降级。已有明确审阅委派可复用。`confirmed_manuscript` 未改主线时可按 fidelity review 路径处理；不因此免除另行要求的人类专业交付政策。探索稿和只读报告不因独立审查暂缺而被扣留。

## 4. 按实际任务检查稿件与成品

优先复用现有完整稿件、来源和真实 PPT 产物，不为验收另造固定数量的任务或模型调用。按本次改动覆盖必要路径：材料到正文、正文到页面、notes 到文件、修改/导出/恢复。发现具体问题后修复并检查受影响对象。

1. 核对原材料支持的事实、数字、单位、限制与建议边界；没有收益数据不编造收益。
2. 检查主线、页间推进和每页信息增量，拒绝正确但浅、空表和泛化内容。
3. 对照实际 PPT 渲染检查关系、密度、可读性、截断和可编辑信息；按本次要求回读正文与备注。
4. 核对实际加载的方法、版本、安装及相关入口，不把源码存在当实际使用过。
5. 保留已发生的失败、原稿与修订依据；缺什么就记录具体对象，不把缺听众或缺试讲当软件未完成。

### 4.1 可选内部诊断（CQ-08/CQ-09）

E1（方法对照）、E2（同内容的设计对照）、E3（逐层制作对照）仅在需要定位具体问题时使用，不是每份 PPT 或 RC3 发布必须完成的实验。无需恢复旧实验、凑齐 A/B/C 组、跑十二会话或招募参与者才能交付。

若开展对照，仍应如实记录各版本和输入，保留原稿，不替某组补写，不把污染样本或手工精修称为原始方法效果。CyberPPT 的固定参考仍可用于学习材料分析、故事线、密度、制作和 QA；不要求用户参与比较。

## 5. 用途、篇幅与修改检查

### 5.1 按用户实际要求

培训稿应讲清步骤、条件和异常；决策稿应讲清结论、证据与真实取舍；阅读稿应在正文中保留必要解释和限制。只做用户所需产物，不额外要求两个 Owner 任务、最低人数或未见情境测试。

### 5.2 修改与首稿记录

检查员可以依据任务和来源指出主线问题。用户如已有意见，则按其意见修改。区分系统误解、材料冲突、用户新增材料和目标变化；历史失败不因后来修好而改写，但不要求用户提供完整正确答案或参加正式试用。

### 5.3 时长要求

只有用户明确提出时长限制才进行内容与篇幅适配，使用讲稿长度、页职责和必要停顿作合理估计并标为估计。实际试讲、真人反馈或现场计时仅按用户另行明确要求安排。

## 7. 依赖与退出顺序
