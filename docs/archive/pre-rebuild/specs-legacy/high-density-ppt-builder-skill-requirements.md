# 高密度 PPT Builder Skill 需求收集整理

日期：2026-08-03
状态：需求整理稿
适用范围：Deck Master 下一版高密度 PPT Builder 的 Skill 需求输入

## 1. 当前边界

本文件只做需求收集和整理，覆盖用户当前确认的参考 Skill、关键能力、必须沿袭的流程、待消解冲突和后续待设计问题。

本文件暂不做具体产品方案、架构设计、代码实现计划、命令设计、Schema 定稿或工程排期。这些内容后续通过 GStack 体系单独设计。

## 2. 参考 Skill 清单

### 2.1 CyberPPT

参考重点：

- 源材料到高密度咨询式 PPT 的三阶段链路。
- 内容分析、证据底表、内容脑暴、SCR、逐页页面计划和信息密度规划。
- ImageGen 图片版蓝图生成能力。
- 风格样张、风格锁定、提示词组织、组件签名和视觉 QA 证据体系。

继承要求：

- 新 Skill 必须继承 CyberPPT 的内容丰富框架，不能退化成普通大纲生成。
- 新 Skill 必须让 ImageGen 蓝图吃到完整页面密度计划、组件清单和真实内容锁定。
- 新 Skill 必须保留“蓝图只作构图、层级、密度和视觉语言参考”的边界。

### 2.2 PPT Master

参考重点：

- SVG 作为可见页面设计源。
- `svg_output/` 到 Native DrawingML PPTX 的转换经验。
- `data-pptx-page-role`、`data-pptx-bounds`、统一画布、语义分组和原生可编辑对象合同。
- 结构检查、预览、导出和质量门。

继承要求：

- 新 Skill 的 SVG 输出需要面向可编辑 PPTX 转换，而非整页图片封装。
- 新 Skill 需要保留“页面可见内容必须存在于 SVG 源”的约束。
- 新 Skill 需要吸收 PPT Master 在文字溢出、图表/表格 metadata、原生对象转换和视觉预览方面的经验。

### 2.3 Product Design `image-to-code`

参考重点：

- 把选定图片作为视觉真相源。
- 先拆解资产、测量区域、确认视口和密度，再实现。
- 源图与实现截图同状态对照。
- P0/P1/P2 阻塞式设计 QA。

继承要求：

- 新 Skill 需要引入“视觉目标先锁定，再重绘”的流程。
- 新 Skill 需要把同尺寸、同状态、同密度的对照检查做成硬门槛。
- 新 Skill 需要把局部区域裁图、重点区域复核、视觉差异记录纳入 QA。

### 2.4 Native SVG Redraw

参考重点：

- 将图片、架构图、流程图、业务蓝图重绘为原生可编辑 SVG。
- 文字用 `<text>/<tspan>`，卡片用 `<rect>`，连接关系用 `<line>/<path>/<polygon>`。
- 根节点、主要视觉区和逻辑对象带稳定 id 与 `data-pptx-bounds`。
- 禁止整页图片、`foreignObject`、外部依赖和不可控样式。

继承要求：

- 新 Skill 需要把图片到 SVG 的环节做成受控重绘流程。
- 新 Skill 需要逐项复核全部文字、卡片、连线、图标、边框、图例和页脚。
- 新 Skill 需要先生成 SVG 预览，再做原图与预览并排检查。

### 2.5 Office CLI

参考重点：

- PPTX 的结构查看、文字查看、问题检查、HTML/截图预览和 OpenXML 校验。
- PPTX 局部样式、文字、形状、表格、图表的后处理能力。
- watch 模式下的人工点选和局部修改。

继承要求：

- 新 Skill 可以把 Office CLI 作为 PPTX 后链路检查和局部修版参考。
- 新 Skill 不应把 Office CLI 当成图片到可编辑 PPT 的核心生成能力。

## 3. 必须沿袭的 CyberPPT 内容丰富框架

### 3.1 证据底表

新 Skill 需要保留 MBB 标准证据表。每条事实、数字、判断、建议、caveat 或管理层含义都要有独立记录。

建议字段：

- 证据 ID
- 论点或数据
- 数值
- 单位
- 期间
- 来源位置
- 置信度
- 冲突或 caveat
- 含义
- 推荐视觉表达

硬要求：

- 不能用常识补源材料没有的数据。
- 不能把 ImageGen 里的文字、数字、图表值和 Logo 当事实。
- 冲突数据要保留差异和来源，不能静默归一。

### 3.2 内容脑暴

证据表完成后，需要先做内容脑暴，再收敛到推荐故事线。

必须产出：

- 2-3 条可选故事线。
- 每条故事线对应的 issue tree 或 hypothesis tree。
- 每条故事线的核心管理层结论。
- 每条故事线最关键的 5-8 条证据 ID。
- 每条故事线的 caveat、冲突和缺失数据。
- 每条故事线适合的受众和汇报场景。
- 推荐故事线和放弃其他选项的原因。

### 3.3 SCR 与逐页计划

新 Skill 需要保留 SCR 结构，并把每页做成可辩护的管理层判断。

每页计划需要至少包含：

- 页面角色。
- 结论标题。
- 详细论证。
- 证据 ID。
- caveat。
- 视觉形式。
- 图表计划。
- 业务含义。
- 承接关系。
- 信息密度。
- 组件清单。

### 3.4 页面物料池

新 Skill 需要把材料转成页面物料池，供 ImageGen 蓝图和 SVG 重绘使用。

物料池至少包括：

- 关键数字、对比、排名、变化、分布、漏斗、矩阵和时间线。
- 表格、注释、图例、微图表、边栏洞察。
- 每页可承载的信息区数量。
- 主图和侧栏比例。
- 必须保留的证据 ID、SO WHAT 和 caveat。
- 低密度风险和需要补证据的问题。

### 3.5 内容锁定

逐页 ImageGen 蓝图前必须生成 `slide_content_lock`。

锁定内容包括：

- 标题、副标题和语境说明。
- 图表真实指标、期间、单位和数值。
- 表格行列结构和核心单元格内容。
- KPI、同比、CAGR、占比、差值等关键数值。
- 注释、caveat、来源口径和证据 ID。
- 右侧解读栏、管理启示、结论短句。
- SO WHAT 的标题、分区和要点。
- 不允许缺失的组件清单。

## 4. ImageGen 蓝图需求

### 4.1 蓝图定位

ImageGen 蓝图是新 Skill 的关键中间物。它的价值在于生成高密度、高完成度、咨询式排版和视觉构图。

蓝图不承担事实来源职责。最终 SVG 和 PPTX 的文字、数据、图表值、来源和脚注必须回到内容锁。

### 4.2 风格锁定

默认需要沿袭 CyberPPT 的 8 种固定视觉风格样张机制。

风格锁定至少包括：

- 风格编号和名称。
- 色板。
- 网格。
- 标题层级。
- 图表语言。
- 表格语言。
- 页面表面系统。
- 字体层级。
- 图标库。
- 页眉、页脚和来源体系。
- 信息密度规则。

### 4.3 蓝图提示词要求

蓝图提示词需要显式传递：

- 目标语言。
- 页面角色。
- 页面结论。
- 内容锁摘要。
- 信息区数量。
- 主图、侧栏、表格、注释、图例、微图表和 SO WHAT 要求。
- 风格编号、色板、网格、图表语言和页面表面系统。
- 禁止页码。
- 禁止内部标注、prompt 标签、wireframe 标签和执行元数据。
- 禁止让 ImageGen 自行补事实。

### 4.4 蓝图记录

每页蓝图需要记录：

- ImageGen prompt。
- 图片输出路径或生成记录。
- 风格编号。
- 目标语言。
- 信息密度目标。
- `slide_content_lock` 路径和 hash。
- `blueprint_component_signature`。
- `visual_element_registry` 初始目标。
- 复杂视觉候选。
- 原生重建目标。
- 允许图片资产候选。

## 5. 图片到 SVG 的还原需求

### 5.1 目标

把 ImageGen 生成的 16:9 图片蓝图转成可编辑、可检查、可进入 PPTX 转换链的 SVG 页面。

核心挑战：

- 视觉还原度。
- 文字溢出。
- 容器溢出。
- 坐标比例漂移。
- 图标、节点、箭头、曲线和标签的相对位置漂移。
- 表格密度失真。
- 曲线、流带、异形边界被简化。
- 生成图文字不可靠。

### 5.2 全元素拆解

每页必须建立 `visual_element_inventory`。

元素范围包括：

- 标题、副标题、页眉、页脚。
- 所有正文、数字、标签、来源、图例和注释。
- 图表条、点、线、轴、网格线、数据标签。
- 表格单元格、行列线、表头、关键单元格。
- 图标、徽章、编号、箭头、连接线。
- 卡片、面板、色块、分隔线。
- SO WHAT 区域的图标、标题、正文和分隔符。
- 背景纹样、装饰线和重复元素。

优先级：

- P0：标题、主图、SO WHAT、页脚、关键数字、核心面板、用户指出区域。
- P1：普通卡片、图标、标签、箭头、表格、分隔线。
- P2：装饰线、点阵、纹理、重复刻度、背景纹样。

### 5.3 测量与坐标换算

每页必须建立 `blueprint_measurement_table`。

需要记录：

- 蓝图画布像素尺寸。
- SVG viewBox。
- PPT 目标画布尺寸。
- `scale_x` 和 `scale_y`。
- 每个 P0/P1/P2 元素的 `blueprint_bbox_px`。
- 每个元素的目标 SVG 坐标。
- 每个元素的目标 PPT 坐标。
- 容差。

原则：

- 先量蓝图，再生成 SVG。
- 先按目标 viewBox 绘制，不依赖外层 `scale()`。
- 渲染后反测，超出容差即返工。

### 5.4 SVG 重绘规则

SVG 需要使用原生图元表达：

- 文字：`<text>` 和 `<tspan>`。
- 卡片和表格单元：`<rect>`。
- 分隔线和基础连接：`<line>`。
- 箭头、曲线、流带、异形：`<path>` 和 `<polygon>`。
- 图标：本地图标库、受控 `<symbol>/<use>` 或受控 path group。
- 主要视觉分组：稳定 `<g id>`。

禁止项：

- 整页 `<image>`。
- 大面积蓝图截图。
- `data:image`。
- `foreignObject`。
- 外部 CSS。
- 不可控脚本或 iframe。
- 用图片承载主要文字、数字、标签、来源、页脚和 SO WHAT。

### 5.5 文字和容器溢出处理

文字必须以内容锁为准，不能抄生成图里变形或漂移的文字。

处理顺序：

1. 先确认文字归属容器。
2. 使用固定 Typography Scale。
3. 检查行宽、行距、内边距、分隔线和归属边界。
4. 出现溢出时，优先调整容器尺寸、换行、分区、行高或内容精炼。
5. 如果仍无法满足密度和可读性，需要上升为页面结构问题，交给后续设计流程裁决。

禁止用持续缩小字号解决密度问题。

### 5.6 空间锚点和标签避让

中心图、流程图、架构图、生态图、矩阵图、时间线、路径图和图标密集页必须做空间锚点检查。

需要检查：

- 图标是否在对应节点或卡片锚点附近。
- 标签相对图标、节点和箭头的位置是否一致。
- 箭头端点是否接到正确边界或中线。
- 连接线方向和阅读顺序是否一致。
- 标签是否压住图标、节点、箭头、曲线、圆环和边框。

没有重叠只代表标签避让初步通过，还需要锚点位置通过。

### 5.7 曲线、流带和异形追踪

以下元素必须触发精确追踪：

- 桑基图。
- 流线图。
- Ribbon。
- 带状流。
- 曲线面积带。
- 弯曲箭头。
- 贝塞尔连接线。
- 弧线流程。
- 波浪分割区。
- 异形遮罩。
- 地图边界。
- 复杂图标轮廓。

需要产出：

- 局部参考裁图。
- 几何拆解记录。
- 采样点、边界点或控制点。
- trace debug 图。
- SVG path 或 custom geometry 资产。
- 渲染后局部裁图。
- 局部对照结果。

核心曲线不能用少量折线点粗略拼接。流带需要分别追踪上下边界。

### 5.8 表格语义和密度

表格需要按语义决定字号和排版。

要求：

- 表格正文、行动项、风险项、解释句和建议句使用正文级别文字。
- 微标签只用于极短列名、单位、刻度和图例。
- 单元格文字不能越过表格单元或分隔线。
- 字号、行高、列宽和换行需要共同保持蓝图密度。
- 大面积空白、阅读重心塌陷或内容被压成微标签都应视为失败。

## 6. 视觉 QA 需求

### 6.1 QA 证据

每页至少需要：

- 已批准蓝图图。
- SVG 渲染图。
- PPTX 渲染图。
- 蓝图与 SVG side-by-side。
- 蓝图与 PPTX side-by-side。
- 关键区域局部 overlay 或 bbox 对照。
- 测量表。
- 渲染后 bbox / delta 报告。
- 视觉差异记录。
- 字段级证据映射。

### 6.2 必须检查项

- 页面表面系统是否匹配。
- 主图语义是否匹配。
- 视觉语义是否保留。
- 主要信息是否可编辑。
- 空间锚点是否通过。
- 曲线保真是否通过。
- 标签避让是否通过。
- 文字溢出是否通过。
- 容器溢出是否通过。
- 连续文本流是否通过。
- 表格语义字号是否通过。
- 表格密度是否通过。
- 蓝图背景是否未被当成交付背景。

### 6.3 失败处理

任何关键项失败，页面不得进入交付确认。

失败后需要：

- 记录差异。
- 生成返工清单。
- 修改当前页。
- 重新渲染。
- 重新对照。
- 重新生成 QA 证据。

## 7. 实现路径冲突记录

这些冲突只做记录，具体消解方式留给后续 GStack 设计。

### 7.1 PPTX 生成引擎冲突

CyberPPT 第三阶段强调 PptxGenJS / pptx-generator。PPT Master 当前参考链路使用 SVG 到 Native DrawingML 的转换栈。

后续需要裁决：

- 新 Builder 是否自研 PPTX 编译器。
- 新 Builder 是否以 SVG 为唯一中间表示。
- 新 Builder 是否支持多个后端。
- 如何保证客户最终 PPTX 可编辑和视觉高保真同时成立。

### 7.2 复杂视觉资产策略冲突

CyberPPT 允许复杂非文字视觉小范围保留为图片资产。Native SVG Redraw 更强调禁止整页图片和尽量原生 SVG 重绘。

后续需要裁决：

- 哪些元素允许作为图片资产。
- 图片资产最大面积和准入条件。
- 图片资产是否允许进入最终 PPTX。
- 图片资产如何披露可编辑性牺牲。

### 7.3 蓝图随机文字与真实内容冲突

ImageGen 蓝图里的文字、数字和图表值不可靠。SVG 重绘和 PPTX 最终输出必须使用真实内容。

后续需要裁决：

- OCR 结果在流程中的地位。
- 内容锁如何覆盖蓝图文字。
- 文字区域如何在保留蓝图视觉结构的同时替换为真实文本。

### 7.4 高还原度与可编辑性冲突

越接近蓝图，越容易依赖图片或复杂路径。越追求全量可编辑，越容易损失视觉质感。

后续需要裁决：

- 视觉语义和可编辑信息层的双硬门槛如何量化。
- 哪些内容必须原生可编辑。
- 哪些非文字视觉可以用 SVG path、custom geometry 或图片资产。

### 7.5 批量效率与逐页验收冲突

高保真页面需要逐页测量、重绘、渲染、反测和返工。批量生成会提高速度，但会放大漂移和密度下降风险。

后续需要裁决：

- 哪些阶段允许批量。
- 哪些阶段必须逐页。
- first-page gate 和 final gate 如何设置。

### 7.6 风格体系冲突

CyberPPT 默认 8 种固定风格稳定，但用户也指出现有 CyberPPT 视觉可能偏单调。

后续需要裁决：

- 新 Builder 是否沿用 8 种风格作为默认基线。
- 是否引入更丰富的 Deck Master 风格锁。
- 如何避免风格扩展破坏高密度内容规划。

### 7.7 代码复用边界冲突

当前目标是参考两套 PPT Skill 的能力和经验，真实代码开发需要重新完整实现。

后续需要裁决：

- 哪些参考脚本只作为行为样例。
- 哪些数据合同可以迁移。
- 哪些实现需要重写。
- 新实现如何吸收旧链路踩坑，同时避免被旧技术路线绑定。

## 8. 后续 GStack 待设计问题

后续进入 GStack 体系时，建议重点讨论：

- 新 Skill 是 Deck Master `deck-builder` 的高密度模式，还是独立 Skill。
- 新 Skill 的阶段边界、确认门和 handoff artifact。
- 证据底表、故事线、内容锁、蓝图记录、SVG 重绘记录和 QA 记录的合同形态。
- 图片到 SVG 的核心能力采用 AI 标注、视觉模型、人工确认还是混合流程。
- SVG 到 PPTX 的新实现目标、可编辑对象范围和渲染验收方法。
- 视觉 QA 的自动化程度、人工验收入口和返工循环。
- 如何把 CyberPPT 的内容丰富能力稳定接入 Deck Master 的 Page Package。
- 如何处理长篇 deck 在 20-30 页后密度下降、重复拖沓和内容增补不足的问题。

## 9. 当前结论

新 Builder 的核心需求可以概括为三句话：

1. 内容上继承 CyberPPT 的 MBB 证据、内容脑暴、SCR 和页面密度框架。
