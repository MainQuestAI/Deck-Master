## Diagnosis and changes

- **#159:** `project_info` constructed separate collaboration/migration Stores
  and Documents. It now passes one explicit snapshot and a local `ReadFacts`
  object reader to pure snapshot projection helpers, including completion.
  Repeated immutable task/object reads are shared within this response only.
  `ReadFacts` checks reference grammar and delegates initial byte/hash checks to
  Store. There is no global or ContextVar permission cache. Later writes and
  later public requests construct fresh readers and revalidate their facts.
- **#145:** an icon candidate's list eligibility path called `_plan`, which
  loaded all candidates again, then preview context loaded them a third time.
  Listing now constructs the validated collection once and explicitly passes
  it to its preview checks. Normal plan/adoption paths still independently
  load the collection/current state. Tool checks, preview identity and native
  proof gates remain; no native preview is fabricated.
- **#156:** list_changes previously called complete handoff per group, including
  Store/snapshot scans, full task payload, schema, command and JSON text.
  It now indexes tasks once, validates selected frozen facts, and uses the same
  status aggregation as handoff. Ordering, unknown-call precedence, verification
  flags and corrupt referenced-plan/call-record refusal remain. It retains
  first-match task lookup and preceding damaged-task refusal semantics.
- **#161:** page lineage now dispatches task facts to page-row, prepared-prompt
  and generation consumers in one full Document task traversal. Consumers
  project only the relevant subsets. It was already O(N), and its existing
  `_ReadContext` prevented repeated JSON decoding; this is **not** a claim of
  eliminating three JSON decodes or an O(N²) lineage algorithm. Other lineage
  paths (production projection/ancestry) still do their own work.

## RP-08 follow-up: intermediate ancestry invalidates currentness

Parent review suggested an unguarded ancestry dependency. Before changing cache
policy, a real isolated fixture reproduced it: warm summary, modify a revision
between head and dispatch to a foreign project (head and dispatch unchanged),
then compare warm versus cache-cleared cold. Warm equaled the original summary;
cold differed precisely at:

- `/next_actions/actions/0/state`: warm `derived`, cold `unknown`.
- `/pages/0/attention/items/0/state`: warm `derived`, cold `unknown`.

The action is `compare_candidates`; counts remained the same. This did **not**
prove a write bypass: adoption still rechecks. It did prove an incorrect warm
read projection. A second diagnostic with only the previous cache-publication
policy injected reproduced the same two fields; original pre-fix repro and
comparison are in `/tmp/rp26-ancestry*` (temporary, no customer data).

Fix: summaries consuming dispatch-ancestry currentness are explicitly marked
non-cacheable. Each request recomputes that proof; no endpoint-only revision
signature is treated as complete ancestry evidence. Immutable object-byte
caches retain their separate guards. Partial failures still never publish a
summary cache entry. **This has a performance cost** for those summaries;
the table above does not measure or claim removal of that cost. No change to
RP-29 `FixedSnapshotReader` is made.

New foreign-project and missing-intermediate tests assert warm == cold,
`derived` becomes `unknown` in both locations, and restoring exact ancestor
bytes restores the original projection. No fabricated current qualification.
