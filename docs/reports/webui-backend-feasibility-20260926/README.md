# Web UI 后端可实现性核验与建议

日期：2026-09-26。范围：用户已认可的 v3 结构与功能，以及本轮读取的 OpenDesign 当前原型。

**结论：可以沿用这套结构开发，现有后端架构能够承载；但不能把现在的原型直接接到旧 Web 接口，就认为功能已经成立。** 整稿查看、正文编辑、材料更新、版本和生产链路都有可复用基础。实际提示词记录、试作候选、结构化批量意见、完整恢复和三类文件交付，需要补充核心行为。

建议保留五个工作面和 12 个开发包，先验证后端的“记录请求 → 真实执行 → 返回候选 → 比较采用”小闭环。前端的视觉调整继续采用用户在 OpenDesign 中的版本。原型展示的是产品目标，不能作为后端已实现的证明。

本轮有三类证据：当前源码与活动契约核对；**214 项既有后端专项测试通过**；真实 Python 服务及 HTTP 的 **17 项有名探测**。后者同时验证“支持的行为”和“确实存在的缺口”，不表示 17 项新功能验收通过。探测使用临时合成项目，没有调用真实 Host 或模型。

## 3. 必须在正式接线前处理的差距

### 3.1 “先试，再采用”与当前结果接收机制不同

现在 `task accept` 完成校验后直接把结果写进当前 Document，并清理受影响的下游。独立探测让两页修复以相反顺序返回，两页都能正确接收，但结果已经进入当前稿，没有用户另外点“采用”的环节。跨页结果隔离的基础可以复用，候选机制尚未存在。

**建议：** 在 W07 区分正常生产与用户试作。正常生产保留自动更新；试作先保存独立候选，采用时再检查目标页、目标阶段和依据，更新当前引用。保留、再次试作、只修 SVG 才会有真实含义。不要用“先自动替换，用户不满意再恢复历史”模拟候选。

依据：[tasks.py](../../../src/deck_master/tasks.py) 行 828、1060、1088、1123；探测 **P10**。这是新语义，不是旧自动生产行为本身有错。

### 3.2 预备 prompt 已保存，实际 prompt 仍可能缺失

`project_prompt` 会生成预备文本和投影，并在派发时作为 Task 输入保存；这部分无需重新发明。Artifact 也支持 `submitted_prompt` 和调用引用。但探测确认：不提交实际 prompt 的蓝图结果仍会被接收。旧图是否有实际 prompt，取决于当时是否回传，不能由 UI 保证。

**建议：** W02 把“调用前冻结的请求”与“每次执行记录”串起来，并通过一次真实 Host 调用证明请求、参考图和输出属于同一次执行。显示来源等级：预备、已冻结、Host 申报、工具或供应商证据。用户修改 prompt 应生成下一轮请求，不能改旧图的历史说明。旧记录缺失时只标未记录，不能靠当前稿或反推文本补造。

依据：[production.py](../../../src/deck_master/production.py) 行 81；[service.py](../../../src/deck_master/service.py) 行 512；[tasks.py](../../../src/deck_master/tasks.py) 行 393；探测 **P12、P13**。

### 3.3 现有反馈接口会忽略原型需要的结构化信息

`POST /api/feedback` 目前只把一页的文字要求送入 repair 任务。探测传入选区、所看产物和客户端操作 ID 后，请求返回成功，但选区没有保存，操作 ID 也没有作为重试身份使用。同一客户端 ID 换一段要求，会得到另一条任务。批量请求形状则报 400。相同页、相同文字的待处理任务去重已经存在，但它不是可靠的操作重放。

**建议：** W06 增加结构化目标：项目/章节/页面/产物、所看版本、整页/点/框/文本定位；一次提交先验证全批再原子写入。同页意见保留各自选区后合并执行。API 明确接收哪些字段，对未知字段报错，不能“200 成功但悄悄丢意见”。用户意见与正式质量 Review 应是不同对象。

依据：[web.py](../../../src/deck_master/web.py) 行 115–127；[service.py](../../../src/deck_master/service.py) 行 892；探测 **P05、P06**。

### 3.4 固定版本比较在核心可做，当前 HTTP 会返回错版本

`project_view(..., revision=...)` 可以读历史，实测旧标题和新标题不同。可是 `GET /api/view?revision=旧版` 与单页同类查询都忽略参数，返回当前内容；不存在的版本也返回 200 当前稿。如果现在接比较 UI，会出现“标题说旧版，内容已经变新”的错误。

**建议：** 提前补通整稿/单页的指定版本读取，未知版本明确拒绝。比较双方固定真实引用，后台刷新只提示出现新结果，不改变正在比较的对象。W01/W05 即应完成，不能推迟到 W11 的完整历史导航。

依据：[view.py](../../../src/deck_master/view.py) 行 20；[web.py](../../../src/deck_master/web.py) 行 166–184；探测 **P01、P02**。

### 3.5 “保存结果未知”还缺统一的恢复事实

正文编辑和 inputs 更新已有各自的幂等/恢复措施。但 Host 结果路径先提交当前稿，之后另写操作回执。注入两者之间的写入故障后，结果确实已经成为当前稿；重试原结果却因“任务已完成、仅允许原操作重放”报冲突，因为用于识别原操作的回执没有成功写入。

**建议：** 在 W06 的操作基础中解决提交事实与回执之间的可恢复关系，并覆盖 Host 结果接收。已有 Store 原子切换继续复用，不能把“文件指针原子”扩大解释为“所有业务操作可在丢回应后重放”。UI 的核实/重放必须查询持久事实，不能依赖最后一次 HTTP 是否成功或重新触发模型。

依据：[tasks.py](../../../src/deck_master/tasks.py) 行 860、875、1155–1177；[store.py](../../../src/deck_master/store.py) 行 251；故障探测 **P16**。这是本轮复现的实际恢复缺口；本轮没有修改它。

### 3.6 运行台需要的结果归属和超时信息尚不完整

Task 契约有 `result_refs`，但本次蓝图成功回包含结果引用，持久 Task 的该字段仍为空。现有 `/api/tasks` 只返回 ID、种类、状态、要求和更新时间，未暴露接手身份/完整结果。把任务时间置为远早于 30 分钟后执行 `continue`，任务仍保持 running；当前没有原型要求的超时恢复语义。

**建议：** W06/W07 写入请求—任务—执行—结果关联，W10 统一投影。接手时间应独立记录，不能长期把会变化的 `updated_at` 当接手时间。超过 30 分钟进入“需核实”，用户取消或重新交接后才创建新任务；不能自动认定失败并重复外部调用。取消后晚到结果拒绝已有基础，本轮已实测通过。

依据：[tasks.py](../../../src/deck_master/tasks.py) 行 640、1060、1177；[service.py](../../../src/deck_master/service.py) 行 1624；[web.py](../../../src/deck_master/web.py) 行 185；探测 **P07、P08、P11、P15**。

### 3.7 审阅、交付、工程包需要真正分开

当前导出只接收 review/delivery（working 是 review 别名），且都要求已经有当前 PPT。只有正文或原图时，review 也会拒绝。review 还会复制工程对象库、版本记录与当前指针，因此不能直接沿用为新定义的外发审阅包。指定历史版本参数不支持；现有文件路由仅服务对象库，拒绝导出目录中的文件。当前 PPT 原件可通过已有对象读取展示，不等于三类导出包都可在浏览器下载。

**建议：** W11 固定导出开始时的版本。review 允许稿件、已有预览和可读缺项说明；engineering 承接恢复材料；delivery 继续服从真实质量检查。补内部导出 ID 与下载入口，以及工程内容从 review 移出的兼容说明。正文变更后旧 PPT 仍可从历史找到，但应明确过期原因，不冒充当前成品。

依据：[editing.py](../../../src/deck_master/editing.py) 行 282–373；[web.py](../../../src/deck_master/web.py) 行 204；探测 **P09a、P09**。review 包内容核验使用明确标注的合成 PPT 容器，不是成稿质量证据。

### 3.8 内容、大纲与整稿操作不能靠前端临时数组维持

Document 已有材料、Page 和页序，Page 也有 citations；但活动模型没有独立内容整合/章节大纲，也没有合并拆分的来源关系。局部 `content_update` 可以新增、删除和调整页序，但目前仅接受在 `compose / input_revision` 任务下的结果，不是通用的页面重排/合并接口。没有现成的专用 reorder/remove 服务可直接照旧方案描述调用。

**建议：** W02 增加简明内容计划；W09 把可复用的局部更新底座用于明确的结构变更。直接重排/移除由核心校验和事务完成，复杂改写交给 Host。合并拆分生成新页身份并记来源，旧选区不迁移。材料“已写入/提取”与“Host 已理解并判断影响”分开；已有 `inputs_update` 可以直接复用，毋须重做 A 线。

依据：活动 [document schema](../../../src/deck_master/resources/contracts/document.v1.schema.json)；[tasks.py](../../../src/deck_master/tasks.py) 行 665、733；[service.py](../../../src/deck_master/service.py) 行 1115；探测 **P14**。

### 3.9 刷新保护与独立入口仍需服务配合

目前 Web 服务以单项目启动，没有统一最近项目注册/打开入口；`/v2/` 和 `/api/view/summary` 均不存在。旧前端的编辑草稿是内存 Map，刷新会丢；v3 原型的 localStorage 不能自动成为正式的项目持久化方案，尤其服务端口变化时。

**建议：** W03 增加独立入口与项目路径授权；W01/W10 增加轻量变更摘要；W03/W05/W10 按已定规格实现项目侧 UI 草稿保存和浏览器临时缓冲。业务 revision 不应被滚动位置、已查看标记和输入中的草稿反复改写。

依据：[web.py](../../../src/deck_master/web.py) 行 229、264；[旧前端](../../../src/deck_master/resources/static/app.js) 行 5、44、99；探测 **P03**。本轮没有验证真实跨端口草稿恢复。

## 4. 可以复用的底座，不建议推倒重做

- **版本与文件存储：** 不可变对象、历史快照、当前指针原子切换、冲突检查已经存在。旧产物没有因当前引用清空而被删掉；需要的是历史可见性与适用性说明。
- **按页修改与影响范围：** 单页直接编辑会保留原图引用、清理本页 SVG/预览并使整稿输出失效；未改页保留。它按现有“原图作重建参考”的路线继续，并不会自动重新生一张蓝图。新 UI 应明确区分改正文后重建、重新生图、仅修 SVG。
- **局部结果与取消保护：** 不同页的结果可以逆序接收；同页/输入变化要拒绝旧结果，取消后晚到产品不得采用。核心已有检查，本轮专项与探测均覆盖相应路径。
- **材料与任务事实更新：** 受众、用途、既定决定、材料新增/替换/移除及后续局部内容协调已在合并主线。
- **SVG → PPT 与质量检查：** 编译、逐页预览、整稿 PPT 渲染、回读和评审基础已有。新 UI 负责准确展示这些事实，不能用“用户已看过”替代质量通过。

这里的复用指已有核心职责和行为可接入；每个新接口和新场景仍须做相应回归。保持 Python + 原生 ES Modules 即可，没有因为这套结构而引入新框架、独立模型执行器或另一套项目数据库的必要。

## 5. 可以设计出来，但不能由后端无条件保证的事

| 产品表述 | 可以承诺的范围 |
|---|---|
| 查这张图的实际提示词 | 新流程可记录并绑定；旧图未记录就无法可靠补回。已有预备文本只能按真实来源呈现 |
| 借第 7 页风格，保留第 8 页事实 | 可固定参考图、文本、目标范围和借用维度；模型是否保留全部事实、是否改善指定风格须真实阅图，不能用任务成功替代 |
| 看图就定位 prompt 的问题 | 人可以对照，Host 可给建议；归因只能是解释或推测，后端没有确定性的逆向提示词能力 |
| 整稿画廊先看 24 张原图 | 已有原图可一起看；当前自动调度先完成本页 SVG/逐页复核，再推进下一页，不能承诺先一次性生产全稿原图。改变调度是独立范围，不属于画廊 UI |
| 图片文字可直接编辑 | 首版应从意见跳到真实逐页稿/下一轮 prompt。当前没有 OCR 文本层或自由画布；PNG 框选是修改指示，不是像素或文本对象编辑 |
| PPT 完全可编辑且可交付 | 已有原生形状/文字能力声明和工程检查；不等于每个图表都支持 Office Edit Data、桌面操作验证或专业认可 |
| 30 页流畅、300 页压力通过 | 本轮实测了 24 页数据读写，没有压测真实大图、并发解码或 300 页；既定性能目标仍需 W04/W12 验证 |

这些限制无需改变五个模块，但应约束按钮文案、状态和验收口径。

## 6. 对 12 个开发包的建议

| 包 | 后端工作判断 | 本轮建议 |
|---|---|---|
| W01 链路读模型 | 扩充现有投影 | 优先把版本参数真正接到核心；补任务/来源/产物适用性和 summary，不复制第二套状态真相 |
| W02 过程产物与请求 | 新核心对象与 Host 协议 | 提前至 W01 后；保留既有预备请求，补内容计划、冻结请求、执行/结果绑定；先真实验证一次 |
| W03 独立入口 | 新启动/注册服务，复用单项目服务 | 实现最近项目、打开/新建、路径授权及服务身份核对；用项目侧草稿服务支持恢复 |
| W04 画廊与矩阵 | 主要前端，补资源读取效率 | 先解决现有 20–30 页整稿观看；没有图片就留空位；不顺带改变生产调度 |
| W05 单页链路 | 新投影和请求编辑入口 | 先展示已记录事实和未知；W02 真绑定通过后才使用相应实际提交强语义 |
| W06 标注/计划/交接 | 结构化请求与操作事务 | 先做批量原子性、操作重放、Host 结果回执故障恢复；随后接框选/文本定位及复制交接 |
| W07 阶段重跑/候选 | 最大的核心行为改动之一 | 明确 auto 与 trial；返回只存候选，采用才影响当前；先验证单页原图和仅 SVG 两条路 |
| W08 跨页风格 | 新工作流，复用 W02/W07 | 固定参考与目标内容；真实检查事实保留、指定风格改善、未选部分退化，再扩到多页 |
| W09 内容与来源 | 部分能力已在 main，补结构编辑 | 复用 inputs/content_update；新增直接重排/移除与合并拆分来源，避免重新实现 A 线 |
| W10 完整运行与恢复 | 扩充生命周期和投影 | 写入结果归属、独立接手时间、超时核实；把未知保存当服务事实问题，不能仅改提示语 |

阶段性验收应看具体结果：

1. **能看：** 真实项目的整稿、缺项、来源与固定历史读取正确，刷新保留位置，旧产物不会混作新版。

4. **能交付：** 无成品时仍可导出审阅材料，三用途包与固定版本一致，正常安装验证资源、下载及回退。
