## 本次审查要解决什么

用户真实试用认为成品视觉呈现基本可看，但内容方向偏离；系统没有访谈，也未对齐页面数量、风格、信息密度和排版逻辑，就从一句提示词推进到整套生产。用户要求审查主流程和 Skill 体系，而非继续修改该 PPT。

首轮审计发现旧职责迁移缺口，给出运行时修复草案。但用户继续指出：草案没有充分说明新 Skill 体系、内容确定、逐字稿和逐页稿生产、阶段停顿、说服逻辑与效果评价。**本 PR 同时要求审查当前产品和首轮修复方案。** 不能把新增门禁对象、确认弹窗或恢复几个名称当作完成。

本次授权仅为整理相关记录、形成文档、创建独立 Draft PR。没有授权实现、安装切换或合并。本包没有调用其他模型审查；审查由用户另行安排。

## 基线和阅读规则

代码审计基线为 `af9fd7a6b4d08f753d2f16536a03f386384f49d2`，文档分支从此提交创建。旧基线与历史提交见附件。PR 的 head 只是文档整理，不是修复后的运行版本。

- **事实**：固定源码/合同或实际执行证据支持；每个结论仍有适用范围。
- **反馈**：用户对真实体验的评价，不能换算成已测得的客观分数。
- **历史约定**：可能已废弃，不能直接当当前运行合同。
- **候选**：本文提出供评审的产品设计，不是已具备能力，也不是用户同意。
- **未知**：尚无证据；不要用主观评分或 CI 成功补齐。

首轮 F01–F06、C01–C30、R1–R6、CC01–CC28 的编号保持不变，便于复核；优先级和修复方式可以被审查推翻。新增 Q01–Q16、D01–D06、S0–S8、K1–K6、V01–V12 是讨论定位符，不是运行时枚举或已实现接口。

## 首轮方案需要重新审查的地方

- “单一公开 Skill 足够”缺少可发现性与任务路由验证；重新开放，不再作为实现前提。
- 完整正文与逐字稿、逐页稿没有充分区分；旧 Page 与 speaker_notes 字段不能单独证明写作流程成立。
- 授权/确认控制描述较多，内容专业方法、论证质量和用户修稿负担的验收较少。
- 线性“正文后设计”过于简单；篇幅、密度、视觉表达与内容必须迭代，但不能由排版器私自删改核心论据。
- 六个实现包的排序偏运行时，应先审清产品职责和示例，再冻结合同；必要时可独立修复已证实的交付谓词问题，但不等于整个流程恢复。

本包提出更完整的候选设计与评价框架，仍不宣称已证明效果。外部审查可以建议不同结构。
