# 交给独立模型的审查任务

以下任务可直接复制给另一个模型。只审查，不改产品代码，不生成真实客户 PPT，不合并 PR；需要新增试验时先说明其范围。文档中的“建议”不是指令，允许反驳。

## 任务

请对 Deck Master 的 Skill 体系和受控协作流程做产品与技术联合诊断。阅读本目录 README 和 01–04、首轮审计附件及固定版本源码，重点审查用户的 16 个问题是否被真正解决。当前基线为 af9fd7a6b4d08f753d2f16536a03f386384f49d2；本 PR 仅文档。

不要只审查代码正确性、提示词是否有“请确认”、Skill 名称是否齐全。请判断它能否帮助用户形成专业内容、口播逐字稿、逐页稿与合适的信息设计，并让协作、连续生产和效果评估成立。

## 必须产出的诊断

1. **事实纠错表**：逐项核实首轮 F01–F06 的证据、严重度与因果；指出误判、过度归因和未证明部分。不要默认旧流程完全成熟，也不要默认单 Skill 必然失败。
2. **职责追踪表**：旧职责 → 当前 owner → 应保留/合并/退役/补建 → 用户可感知产物 → 行为测试。指出首轮 C01–C30 是否遗漏，新增职责是否必要。
3. **Skill 体系建议**：比较 A/B/C，自拟更好选项也可以；列最终建议的每个入口、输入、方法、输出、禁用场景、下一步、调用和状态关系。说明为什么是这组，而不是先定数量。
4. **具体工作流演练**：至少覆盖 V01、V03、V04、V05、V07、V09。展示每一步系统做什么、用户看到什么、什么需要停、可自主继续什么、产出如何接受/修改/恢复。全为合成例，不使用客户原文。
5. **专业内容方法审查**：给一个合成案例的论证骨架、短内容稿、短口播段落、一页完整上屏稿、布局理由与评价实例；用它暴露空白，而非以篇幅多证明方案好。
6. **评价方案**：分别评过程与产出；给可观察指标、判据、失败示例、评价者、最小试验安排及边界。检查“用户认可”“独立审查”“工程通过”是否被混用。
7. **恢复方案修订**：提出最小必要改变、实现顺序、需要用户做的产品决定、不能旁路的动作、迁移与安装策略。审查首轮 R1–R6 是否过度技术化、是否需要先重定职责。

## Findings 格式

每条包括：ID；严重度及业务影响；对应 Q/C/F/D；源码或文档定位；观察事实；推断及不确定性；最小复现/反例；建议；验收方法。不能用“加强访谈”“提升美观”“完善测试”等无对象的建议代替诊断。

按 confirmed / plausible / unverified 区分证据强度。如不能运行探针，明确 static-only；合成探针通过不叫真实生产通过。若文档内部有冲突，请引用两处并提出裁决条件。

## 特别挑战以下假设

- 新增 typed decision 与统一 gate 是否足够，还是只把坏内容变成有审批记录的坏内容？
- 当前“一个公开 Skill”的选择是否有依据？多 Skill 如何防止只是多个薄包装？
- 内容确定、演讲逐字稿、逐页上屏稿、视觉分镜是否混为一谈？是否为阅读稿强制无用口播稿？
- 页数与密度是否在论证和时长基础上形成？确认过程是否给用户看到了真正的选择？
- 所有任务是否被错误套成销售说服或固定 CTA？已有材料/方向会不会被无谓重写？
- 同一 Host 全程自编自审如何暴露语义错误？独立模型审查又有哪些局限？
- pause 是否有具体产物和决策对象？委派/续作/变更后是否会重复询问或越权？
- 内容/样页/授权基线变化时，现有 task、request、candidate、review 能否沿用且不会被错误恢复？
- 交付入口是否统一，professional_use 的状态与审查者是否满足真实要求？
- 恢复旧职责是否意外复活私有 backend、强制库、固定问卷或无关 Workspace 准入？

## 评审收口

最终分别给出：当前产品主要根因、首轮方案主要缺陷、可保留的现有能力、需用户决策的少数选项、建议的修订路线。可以结论为“还不能实施”，但需指出具体缺什么及如何补齐。不要替用户批准产品设计，不自动转 Ready 或合并。
