Projects have two pages, N synthetic committed task-update revisions of fixed
text length, and N independently validated cleared draft backups. Total ancestry
is N+3. History requests use fixed head:start near the oldest task update and
limit 2. Operation workload queries one canonical operation N times. No fixture
fallback is used: ordinary storage, clear and recovery APIs execute on synthetic
local projects. No production/model benchmark claim is made.

Cold clears only process ancestry/operation caches before **each** observation;
warm primes each workload, then takes three samples. Filesystem cache is not
flushed. Baseline and candidate processes use the exact same project bytes and
sequence. Revision reads count revision-file read_bytes/read_text calls (header
parsing plus full Document parsing); warm header cache avoids full JSON parsing.
Header checks count `_header` calls, including signature checks. Logs, operation
atomic writes and os.fsync are instrumented separately. Timing includes this
identical instrumentation overhead; CPU values below are medians in ms, not p95.

Backup log reads are 9/17/33 before and 1/1/1 after for both temperatures.
Operation index writes are 8/16/32 before and zero after; fsync is 16/32/64
before and zero after. Other measured workloads perform zero index writes/fsync.
Counts repeat identically in all three observations. Backup context still has
its own identity traversal, hence two linear header walks total per list;
no claim of only one total walk is made.

History cold CPU and short-history warm CPU regress because the new reader
validates the entire same-project, acyclic chain instead of trusting skipped
parent documents. Cold history has 16/24/40 reads rather than 11/19/35. Warm
selected-page reads stay constant at five; signature checks remain linear.
This trades cold work for safety and avoids repeated full Document parsing; it
is not a universal latency improvement. No numerical speed target was assumed.
