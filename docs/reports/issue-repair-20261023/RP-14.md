## Diagnosis and change

The review packet carried Task facts and manuscript objects but omitted the
current request's instruction bytes and applicable collaboration decisions.
Review freshness used artifact content, so adding an applicable editorial
requirement without editing a Page could leave an old review usable.

`effective_requirements.py` is a read projection of the existing ledger, not
another instruction store. Packet and author/reviewer Skill readers share
current audience/brief/use mode, request intent/scope/evidence, and effective
accepted decisions with exact immutable source refs and text/JSON bytes.
Binary evidence is explicitly `binary_read_required`. Replaced, rejected,
deferred, ineffective, foreign-request and out-of-scope decisions are excluded.
A rejection replacing an accepted decision withdraws that requirement using the
existing public decision API; no new disposition or schema is invented.

Direction/manuscript/tradeoff constraints follow their page and layer scope;
speech constraints enter only speech review; visual/delivery/call-policy
changes do not invalidate editorial units. Reading a deck planning decision
never grants page authorization. A review policy enters only when it explicitly
sets the existing `content_review_requirement`.

New Tasks compare against their immutable packet projection (including changes
in effectiveness after dispatch); legacy Tasks derive their basis from their
immutable dispatch snapshot. Pending stale Tasks are not silently reused.
The acceptance receiver rejects a concurrent changed requirement through its
existing stale-input boundary. Already accepted review units are rechecked
against their actual Task/result provenance. External or human records without
Tasks use the first committed introduction snapshot, without inventing an
executor or receipt. This detects changes after import, not whether a human
actually read requirements before import; existing identity checks remain.
