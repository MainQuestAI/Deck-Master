# RP-07 · 显式协商的紧凑任务回执

基准 PR #184：`55adc97c5bb5f16ae7fcff7c33c43969fae9ce97`。关联 #183。
本批实现 `task_receipt.v1`，只有明确选择该协议时才减少回执正文；旧默认未改变。

## 根因与实现

`task_start` 和 `task_cancel` 经 `_commit_task_update`，以及首次 `accept_result`，原先都调用 `_pending_host_tasks`，为每个待办展开完整工作单、方法及来源。材料原件存储并没有重复；重复发生在回执构造和传输。

新协议返回单个 task 的身份、scope、execution、dispatch/produced_against、调用事实和结果引用；接受候选时仍保留 candidate IDs/refs、影响摘要及 operation_result。它没有 pending_tasks，也不宣称输入已就绪，返回 `context_ready=false` 和单任务 `methods` 的 `work_context.v2/full` 读取指引。当前任务尚需正常读取、当前性和权限检查。

未知协议在事务开始前拒绝。接受后的精确重放使用原应用快照，保留原结果与当前 revision 的区别；紧凑领取/取消使用刚提交的固定快照，不把随后前进的 head 冒充本次写入结果。权限、身份、CAS、来源、调用结算与晚到结果处理未放宽。

## 消费者兼容表

| 消费者 | 既有行为 | 显式选择入口 | 验证 |
|---|---|---|---|
| Python service（当前 SDK 边界） | 省略参数仍返回旧结构 | start/accept/cancel 的 `response_protocol='task_receipt.v1'` | 领取、同身份重领、接纳、精确重放、取消、错误和快照前进回归 |
| CLI Host | 不带参数仍返回旧结构 | `task start/accept/cancel --response-protocol task_receipt.v1` | CLI 领取集成测试；三入口参数均透传 |
| HTTP | 现有 `/api/cancel` 旧请求不变；没有 task start/accept HTTP 写入口 | `/api/cancel` JSON 同名字段 | 真实本地 HTTP 请求、同源 session token 和取消回执 |
| 原生 review 内部调用 | 未选择协议，保留旧默认及嵌套 acceptance 格式 | 后续调用者可按声明能力选择 | 本批不改变原生 review 消费合同，不声称已迁移所有 Host |
| 单任务读取 | 原有权威读取和冻结方法不变 | `methods --project … --task-id … --read --read-protocol work_context.v2 --body-mode full` | 新测试实际读取唯一 task 及完整材料正文 |

`capabilities.task_response_protocols` 公布支持范围；共享 Skill 指引明确先发现协议再使用，回执不是输入读取证明。新选项仅协商响应，未升级持久化生产协议。

## 同 workload 测量

六份固定来源，各 17,754 字符；待办数为 1/13/30。公开服务派发一个真实协议任务，其余是仅用于读取负载的合成 Task refs，未执行或接纳模型结果。两个协议读取同一固定快照。真实 claim 之后，只测**回执构造**，不包含事务、HTTP、JSON 序列化 CPU 或端到端延迟。每种协议先预热一次，再采样三次；读数为 `Store.read_object_json` 调用次数，不冒充磁盘 I/O 次数。
