# RP-23 — cross-turn recovery diagnosis

Baseline plan: PR #184, `55adc97c5bb5f16ae7fcff7c33c43969fae9ce97`.
Diagnostic implementation base: `ae79d4c6` (integrated RP-00/02/03/05/06/13).

## Findings

| Situation | Actual supported behavior | Classification |
| --- | --- | --- |
| Task claimed in turn A; Attempt begun; transport definitely never sent | `task call settle --outcome not_sent --attempt-id ...` releases that allowance. Task execution identity remains A. | Existing API works; not a missing release API. |
| New turn B tries `task start` on that running Task | `TaskConflict: another execution already claimed this task`. The released allowance does not transfer identity. | Correct protection. |
| User changes the request scope after the known-not-sent settlement | Explicit `collaboration.start_request(...replace_request_id...)` retires old request Tasks. Once the new request has its real applicable authorization and required review, `continue` issues a new Task; B claims, freezes and begins a new Attempt. | Supported public recovery path; synthetic reproduction below. No mutation of old execution or selector. |
| Sending is unknown | Empty-report `not_sent` is refused; unknown state retained, new calls blocked. | Correct protection. Resolve actual observation first. |
| Completed output belongs to the originally claimed execution | Read original Task/Request/Attempt; settle its observed completion and accept its matching bytes. Exact replay returns original accepted revision; one allowance and one Attempt remain. | Supported no-regeneration acceptance path. |
| Completed output selector instead belongs to turn B while Attempt belongs to A | Desktop selector mismatch is refused before observation collection. Protected SDK controller binding mismatch is also refused. Honest Host-only consumed reporting retains consumption but does not make output adoptable. | Identity protection is correct. No formal cross-execution reassociation endpoint found in CLI, generation or SDK surfaces inspected. Already-produced mismatched output remains unadopted. |
| Task cancelled before completed result is submitted | Settlement retains consumed facts; adoption is rejected as late result. | Correct cancellation boundary; not a reason to regenerate automatically. |

The six new tests use schema-valid neutral fixtures and the public CLI/Runtime services. Synthetic Desktop event and protected-controller fixtures are explicitly test-only. No native model/tool request was made, no customer project was used, and no claim of authentic image evidence is made.

## Reproduced sequence

`test_confirmed_not_sent_cli_then_scope_replacement_can_claim_new_task` executes:

1. `service.task_start` using the current Task's protocol/capabilities and execution A.
2. `generation.freeze` from the exact returned `generation_input`; `tasks.call_begin` binds its request and execution A.
3. Attempt to claim under B fails and leaves the document unchanged.
4. Because this fixture invoked no transport, the actual CLI `task call settle --project ... --task-id ... --allowance-id ... --attempt-id ... --outcome not_sent` succeeds. `generation.show` reports `released` and original execution A.
5. Attempt to claim the same running Task under B still fails. This is expected, not an API retry opportunity.
6. `collaboration.start_request` with the original request ID in `replace_request_id`, real new instruction evidence and narrowed scope marks the old Task `superseded`.
7. The synthetic fixture explicitly supplies authority for the replacement request and its current fidelity review through the existing public services. This is test setup, not an instruction to manufacture user authorization or repeat valid independent review in production. Existing applicable authority must be evaluated normally; a superseded request's grant is not silently copied.
8. `service.continue_project` yields a distinct Task. B claims it; `generation.freeze` and `tasks.call_begin` return distinct request/Attempt identities. Historical Attempt and released call facts remain byte/field equivalent; only the read response's current revision changes.
9. The diagnostic sends no image request; its new begun allowance is also settled `not_sent`.

`test_existing_correctly_bound_completion_can_be_accepted_later_without_new_call` separately proves the supported completed-output path: original immutable bindings are retained, `settle` and `accept_result` use them, and exact adoption replay creates no Attempt or call. It does not reclaim the Task as a different executor.

## Existing guidance versus gap

`skills/deck-master/references/blueprint-svg.md` already requires actual current execution, freeze before begin, actual selector binding, unknown settlement handling and exact output acceptance. `docs/agent-recovery-playbook.md` already distinguishes unknown from not_sent and directs formal cancellation followed by a scoped plan, retaining successful calls. The missing operational guidance is the combined cross-turn decision sequence: **before sending**, read the claimed Task/Attempt identity; if the current execution differs, resolve actual call state and formally replace/reissue work instead of sending against the old Attempt. Neither changing the selector to the old turn nor resetting the Task is a recovery procedure.

RP-24 should add that narrow Host guidance and test an actual handoff session. For an image already completed under the wrong execution, current code has no verified reassociation path in the inspected surfaces. RP-24 must keep this limitation explicit and, if that capability is required, implement a separately bounded recovery transaction that verifies original transport/output, exact input, current scope/control and single consumption. It must not amend the existing Attempt, import arbitrary JSON as proof, or regenerate to conceal the gap. This diagnostic intentionally does not introduce such a transaction.
