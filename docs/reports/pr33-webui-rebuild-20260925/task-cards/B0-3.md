## 目标

把 03 方案 §9.1 的六个接口领域，逐项对到现有 `deck_view.v1` 字段、`/api/*` 路由和 service 函数，得出“已有 / 部分具备 / 缺失”的结论，以及每项缺口的最小增量方案和归属（A 路 / B 路 / 共享接口）。这份草案是 S2-1、S3-2、B4-3 的直接输入。

## 背景与输入

- 源码：`view.py`（`project_view`）、`web.py`（路由见 do_GET / do_POST）、`service.py`（`open_host_task`、`task_start`、`task_cancel`、`accept_result`）、`editing.py`（`edit_page`、`restore`、`history`、`export_project`）、`tasks.py`（`TASK_STATUSES`、`new_task`）。
- 04 执行单 §1 的 G1–G6。
- 拆卡时已核实、需要本卡复核的补充事实：
  - F1：`/api/feedback` 不接收 `operation_id`，只靠“同 kind + 同页 + 同 instruction + 进行中”去重（`service.py:726-729`）；`/api/edit` 和 `/api/restore` 需要 `operation_id`。
  - F2：`/api/export` 没有 revision 参数，始终导出当前版本；`output_dir` 默认为 `exports/<uuid12>`（`web.py:131-134`）。
  - F3：review 导出会把 `.deckmaster/objects`、`revisions`、`current.json` 整个复制到 `project/` 下（`editing.py:317-323`），也就是说“审阅文件”里混有工程内容。
  - F4：`/api/history` 返回的是 revision 链的元数据，不含每个版本的页面内容；`project_view(revision=...)` 在函数层面已支持读取历史版本，但没有暴露为路由。
- 03 方案 §9.1、§9.2、§14 第 2–5 项。

  - 结构化区域（G1）：建议字段结构（如 `region: {revision_id, slot, artifact_sha256, x, y, w, h}`，坐标 0–1 归一化），并说明 Host 怎么读取；

  - 写入幂等（F1）：feedback 带上 `operation_id`；
  - 按版本读取和导出（F2、F4）；
  - 审阅包与工程包分离（F3）。
- [ ] 4. **§14 第 2–5 项的初步结论**：请求与结果关联、整稿命令、预览适用性、导出分离，每项一段结论加依据。
