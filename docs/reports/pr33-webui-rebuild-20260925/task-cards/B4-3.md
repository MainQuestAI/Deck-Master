## 目标

导出**固定到用户选定的 revision**，并清楚区分审阅包、交付包和工程材料，避免把内部工程数据误交给客户（U13）。

## 已知事实（B0-3 F2、F3）

- `/api/export` 没有 revision 参数，默认输出到 `exports/<uuid12>`。
- `export_project` 只接受 review / delivery（working 是 review 的别名）。delivery 要求检查状态为 pass；review 会把 `.deckmaster` 复制到 `project/`，并附带每页的 page.json。
- 结果写入 `delivery.json`，其中有 `revision_id`。

## 接口部分（S 类 PR）

- [ ] 1. `export_project` 与 `/api/export`、CLI `export` 增加可选的 `revision` 参数；不传时保持现状（当前 revision）。传入非当前 revision 时，从该 revision 的对象中导出；该 revision 没有对应的 pptx 时明确报错，**不能悄悄用当前的 pptx 代替**。
- [ ] 2. 在设计说明中明确三种包的边界（由验收人确认后实现）：
  - **交付包**：只包含给客户的内容（deck.pptx + 必要的预览）；不含 `.deckmaster`、page.json 或内部审阅记录。
  - **审阅包**：给内部审阅，可以包含 page.json 与预览。是否继续复制整个 `.deckmaster` 需要重新评估（F3 的风险：体积、内部数据）。
  - **工程包**（如需要）：完整项目状态，只用于排障或迁移，命名与目录上明显区别。
  - 如果决定改变 review 包的内容，这属于行为变更，必须在 PR 中写明，并由老板确认。
- [ ] 3. 测试：固定到旧 revision 导出，`delivery.json.revision_id` 等于请求的 revision，且 pptx 内容与该版本一致（比较 sha）；交付包中不存在 `.deckmaster`/`page.json`；未通过检查时 delivery 被拒绝（现有行为保持）；不存在的 revision 报错。

## 前端部分

- [ ] 4. 导出面板：选择版本（默认当前，可以选历史版本）、选择用途（交付 / 审阅 / 工程），每种用途附一句话说明其中包含什么、适合给谁。
- [ ] 5. 交付被检查拦截时，显示原因和下一步（去修复哪些页）。
- [ ] 6. 导出完成后显示：输出位置、版本、用途，以及“在 Finder 中显示”（只显示路径，不在 Web 中打开本地文件系统）。
- [ ] 7. 测试：选择历史版本导出，请求带 revision；被拦截时有提示。

## 可改范围 / 禁止

- 接口部分：`editing.py` 的 `export_project`、`web.py`、`cli.py` 的 export 参数与测试。
- 前端部分：`static/v2/` 与测试。
- **禁止**：放宽 delivery 的检查门槛；没有设计确认就改 review 包的内容；导出到项目目录以外的任意路径时不做校验。
