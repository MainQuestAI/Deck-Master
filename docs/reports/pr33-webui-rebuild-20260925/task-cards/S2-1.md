## 目标

补齐第一条真实切片（U03、U04、U05）所需的最小读写接口，让新前端不用解析文本、不用自己推断状态。最终范围以 07 草案 + B1-3 定稿为准；**下列增量清单是预期基线，只能收窄或明确，不能扩大**。

## 增量清单（预期基线）

| 编号 | 缺口 | 增量 | 验收要点 |
| --- | --- | --- | --- |
| I-1 | G1 区域是文本 | `POST /api/feedback` 新增可选字段 `region`（结构以 07 为准，至少含所看画面的 slot 与 artifact sha256、基准 revision、归一化 x/y/w/h）；持久化到 task 对象上，Host 可以直接读取结构化数据 | 旧请求（不带 region）行为不变；`instruction` 不再需要拼 JSON |
| I-2 | F1 无幂等键 | `/api/feedback` 接收可选 `operation_id`；同一 `operation_id` 重放返回同一个 task，内容不同则 409 | 重放不产生第二个 task |
| I-3 | G2 看不到完成结果 | `project_view` 投影全部任务（或最近 N 条 + 全部进行中的），每条含 `status`、`scope_pages`、`region`、`dispatch_revision`、结束时的结果 revision（若有）、`updated_at` | 已完成、已取消、被取代的任务出现在 view 中；新增字段不破坏旧字段 |
| I-4 | G3 无刷新机制 | 轻量变更探测：例如 `GET /api/view/summary` 只返回 `revision_id` + 任务状态摘要，或 `/api/view` 支持 ETag / `If-None-Match` 返回 304 | 没有变化时响应体 ≤1KB 或 304 |
| I-5 | G4 只能单页 | 批量提交：`POST /api/feedback/batch` 接收多条修改（每条自带页面、区域、意见），一次事务写入；具体是拆成多个 task，还是一个 task 覆盖多页，以 07 为准 | 批量请求中任一条校验失败时整体不写入 |
| I-6 | 按 G0 | 如果 G0 选择手动批量交接：`GET /api/handoff?task_ids=...` 生成可粘贴的交接文本（项目路径、task_id、读取命令、`task start` 命令），只读、不改状态 | 文本中不含 token 和绝对路径以外的敏感信息 |

## 可改范围 / 禁止

- **可改**：`src/deck_master/view.py`、`web.py`；`service.py` 中 `open_host_task` 的参数扩展（`region`、`operation_id`），以及只读的投影辅助函数；`tests/rebuild/test_web.py`、`test_workbench_e2e.py`、`test_service_flow.py`。
- **需要时可改**：`resources/contracts/` 中 task 对象的 schema（只能加可选字段）。
- **禁止**：修改 `resources/static/`（前端属于 B2 卡）；改变 task 状态机、审阅判定、导出规则；删除或重命名 `deck_view.v1` 的现有字段。如果不得不做不兼容变更，把 `schema` 升为 `deck_view.v2`，并在 PR 描述中写明迁移方式。

## 实施步骤

- [ ] 1. 从 `origin/main` 开分支，先跑 `python3 -m pytest -q tests`，记录基线结果。
- [ ] 2. **先写测试**：为 I-1 到 I-6（按定稿范围）各写至少一个失败的测试，再实现。必须包含的测试：
  - 带 region 的 feedback 写入后，读回 task 对象，region 字段完整，坐标在 [0,1] 范围内；坐标越界时返回 400；
  - 同一 `operation_id` 提交两次，只有一个 task；同 id 不同内容返回 409；
  - task 走完 `awaiting_host → running → completed` 以后，`/api/view` 仍能看到它，并能拿到结果 revision；
  - task 取消后，在 view 中显示为 cancelled；
  - 变更探测：没有变化时返回 304 或极小响应，有变化时返回新的 revision；
  - 批量提交：一条非法时整体不写入（revision 不变）；
  - 旧客户端兼容：原 `test_web.py` 中的用例全部不改就能通过。
- [ ] 3. 实现。保持现有代码风格（`web.py` 是紧凑写法，匹配它）。
- [ ] 4. 更新 `docs/` 中描述 `deck_view` 的文档（如果有），写明新增字段。
- [ ] 5. 跑完整测试，开 PR 到 `main`。PR 描述附：增量清单与定稿的对照、兼容性说明、测试输出。

## 验收方法

1. `git diff origin/main...HEAD --stat` 检查范围。
2. 亲自跑完整测试。
3. 起一个测试项目，用 curl 完成：取 token → 带 region 和 operation_id 提交 → 重放 → `task start` → 构造结果 `task accept` → 读 `/api/view`，核对 AC4–AC6。
4. 用旧前端（未改的 `resources/static/`）打开，确认旧功能正常（兼容性）。
