## 目标

补全主路径的后半段：**等待 Codex → 修改中 → 结果到达 → 修改前后对比 → 接受或再改**。用户能看清每条请求对应哪个结果（U04 后半段、U05）。

## 可改范围 / 禁止

- **可改**：`resources/static/v2/`；`tests/rebuild/test_workbench_v2_*.py`。
- **禁止**：改后端；根据时间先后猜测“哪个结果对应哪个请求”（必须使用 S2-1 投影中的 task → 结果 revision 关系）；在 Host 没有 `task start` 之前显示“修改中”。

## 实施步骤

- [ ] 1. **刷新机制**：使用 S2-1 的变更探测。页面可见时每 2–5 秒轮询一次，不可见时暂停（`visibilitychange`），网络失败时指数退避。发现 revision 或任务状态变化后，再拉取完整 `/api/view`。
- [ ] 2. **状态呈现**：严格按 08 的状态映射——
  - `awaiting_host` → “等待 Codex 接手”（按 G0 结论附带下一步提示，例如“在 Codex 中说‘继续处理’”，或提供“复制交接指令”按钮）；
  - `running` → “Codex 正在修改”；
  - `completed` → “已完成，可对比”；
  - `cancelled` / `superseded` / `failed` → 08 中的对应文案和下一步。
- [ ] 3. **请求 ↔ 结果**：每条请求卡片显示意见原文、框选缩略、提交时的版本，以及完成后的结果版本；点击后进入对比。
- [ ] 4. **对比视图**：修改前（`dispatch_revision` 时的画面）和修改后并排或叠加切换；原框选区域在“修改前”画面上高亮。修改前的画面来自 `/api/file` 读取的历史 artifact（sha 校验）；取不到时明确显示“修改前画面不可用”，不用当前画面冒充。
- [ ] 5. **再改**：从对比视图直接发起新一轮框选/意见，基准为新 revision。
- [ ] 6. **批量交接**（按 G0 与 B1-3 的首版范围）：多条待交接请求的汇总视图，一次交接，逐条追踪状态（U05）。
- [ ] 7. 测试（用测试夹具模拟 Host：直接调用 `task start` / `task accept` 推进状态）：
  - 提交 → 界面显示等待 → 夹具执行 `task start` → 5 秒内界面变成“修改中”，**无需手动刷新**；
  - 夹具 `accept` 产生新 revision → 界面变成“已完成”，对比视图中两侧 sha 不同；
  - 两条请求先后完成，各自对应正确的结果（按 task_id 核对，不按顺序）；
  - 标签页隐藏期间不发请求（抓请求计数）；
  - 在 `awaiting_host` 状态下，DOM 中没有“修改中 / 处理中”文案。

## 验收方法

1. 亲自运行测试。
2. 手工模拟 Host：在终端执行 `deck-master task start / accept`，观察浏览器状态的变化和时间。
3. 核对对比视图两侧图像的 sha（从网络请求中读取）。
