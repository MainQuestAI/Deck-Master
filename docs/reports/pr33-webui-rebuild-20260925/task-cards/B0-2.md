## 目标

回答 03 方案 §14 第 1 项和 §7.1 的七项验证内容：正常安装下，Web 提交的修改能不能被 Codex **可靠地自动接手**？如果不能，最好的手动退路是什么，用户要做几步？结论直接决定 G0。

## 背景与输入

- 缺口 G6：运行时已有 `task start --task-id --execution-ref`（把 `awaiting_host` 变为 `running` 并记录执行方）和 `task accept`，但 Web 没有唤起 Codex 的能力。
- `skills/deck-master/` 主 Skill；`docs/agent-task-index.md`；`deck-master continue`。
- 03 方案 §7.1（七项验证内容）、§7.2（手动退路标准）。

## 可改范围 / 禁止

- **可改**：只写产出文件。验证脚本放仓库外，脚本内容可以作为附录代码块写进 06。
- **禁止**：修改产品代码和 Skill；把当前 Agent 自己能调用的桌面工具当作 localhost 网页可用的能力（03 §7.1 明确要求）；写入 Codex 的内部配置或会话文件。

## 实施步骤

- [ ] 1. **列候选路径**，每条都要给出实测结果，或给出不可行的具体证据（文档链接、命令输出、报错）：
  - a. **拉取模式**：Host 会话按 Skill 指引，在每轮开始或结束时运行 `deck-master continue` / `view --json`，发现 `awaiting_host` 任务后接手。
  - b. **外部触发**：Codex Desktop 是否提供可从外部调用的入口，逐项检查深链接（URL scheme）、MCP、CLI、文件监听、AppleScript/快捷指令。
  - c. **手动批量交接**：Web 生成一段可直接粘贴的交接内容（项目路径、任务 ID 列表、页面、区域、基准版本、读取命令），用户粘贴进已有会话，Host 调 `task start` 接手。
- [ ] 2. **按 §7.1 七项打分**：对每条候选路径，逐项评估连接入口、目标识别、实际接手、会话忙碌、结果返回、重复与恢复、安装可用性，结论为 `满足 / 部分满足 / 不满足 / 未验证`，并附证据。
- [ ] 3. **真实往返（至少一次）**：选最可行的路径，在测试项目上完成：Web（或 `POST /api/feedback`）提交一条修改 → Codex 接手（`task status` 显示 `running`，并有 `execution_ref`）→ Host 产出结果并 `task accept` → `/api/view` 或 `history` 能看到新 revision。记录每一步的时间、命令、任务 ID、revision 前后值。
- [ ] 4. **失败路径**：至少实测以下两项：重复粘贴同一交接内容会不会重复执行；会话中途断开后，重新接手的行为。
- [ ] 5. **计用户步数**：对每条路径，写出从“点提交”到“看到结果”用户必须做的每一步操作。
- [ ] 6. **提需求**：列出为了支撑推荐路径，Skill 和接口需要补什么（例如“Web 生成交接内容”需要什么字段），交给 B0-3 合并。

## 验收方法

1. 在执行者提供的测试项目上运行 `deck-master task status --project <dir> --task-id <id>` 和 `deck-master history list --project <dir>`，核对往返记录中的状态和 revision。
2. 对“外部触发不可行”的证据至少抽查一项（例如亲自查询该 URL scheme 或 MCP 是否存在）。
3. 核对 06 中没有把当前 Agent 自己具备的工具当作产品能力。

## 失败去向

所有自动路径都不可行时，这就是有效结论：推荐手动批量交接，并把限制写清楚交给 G0。真实往返因为老板无法配合而没做成时，卡片状态标为“阻塞”，不能标为完成。
