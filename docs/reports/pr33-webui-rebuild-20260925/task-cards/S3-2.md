## 目标

把 S3-1 的整稿能力和 A1/A2 的输入更新能力通过 Web 接口和读模型暴露给前端，服务 U06–U08。范围以 07 中“S3-2 组” + B1-3 定稿为准，只能收窄。

## 增量清单（预期基线）

| 编号 | 增量 | 验收要点 |
| --- | --- | --- |
| J-1 | `POST /api/pages/reorder`、`/remove`、`/merge`、`/split`：薄封装 S3-1 的 service，带 `base_revision`、`operation_id` | 与 CLI 结果一致；409 与幂等行为一致 |
| J-2 | `/api/view` 投影每页的 `derived_from` 与“需要重新制作”标记 | 合并 / 拆分后前端能显示来源 |
| J-3 | 跨页改写：`/api/feedback` 支持 `page_ids` 多页（一个任务作用于多页，与 S2-1 的批量接口区分清楚） | U07 跨页 |
| J-4 | 读取和更新工作单的 brief / 受众 / 用途（依赖 A1） | U08 |
| J-5 | 补材料：上传或登记新材料，返回影响页面清单（依赖 A2）。**材料文件只能写入项目目录，不进入仓库和 gbrain** | U08 |

## 可改范围 / 禁止

- **可改**：`web.py`、`view.py`；只读投影辅助函数；`tests/rebuild/test_web.py` 等。
- **禁止**：在 Web 层重新实现业务逻辑（只调用 service）；修改前端；在 A1/A2 未就绪时伪造“影响页面”结果——未就绪的部分从本卡中移出，并在 PR 中写明。

## 实施步骤

- [ ] 1. 核对 S3-1、A1、A2 实际合入的能力，确定本卡的实际范围，写在 PR 描述开头。
- [ ] 2. 先写测试：每个路由的成功、409、幂等重放、缺 token/Origin 时拒绝（沿用 web.py 现有的鉴权）；材料上传的路径校验（不能写到项目目录以外，不接受 `..`）。
- [ ] 3. 实现；更新 view 投影；兼容性同 S2-1（只加字段，或升 v2）。
- [ ] 4. 跑完整测试，开 PR 到 `main`；合入后 A、B 两路 rebase。

## 验收标准

| AC | 标准 | 对应 |
| --- | --- | --- |
| AC1 | 完整测试全绿；旧测试未改动 | — |
| AC2 | Web 路由与 CLI 行为一致（同一操作分别通过 CLI 和 HTTP 执行，结果 revision 内容等价） | U06、U07 |
| AC3 | 所有写路由都需要 token + Origin，并有路径穿越测试 | 安全 |

| AC5 | 输入更新只包含已真实具备的能力，未具备的在 PR 中列出去向 | U08 |

## 验收方法

1. 亲自跑测试；用 curl 调用每个路由，与 CLI 结果对比。
2. 手工构造恶意路径和缺 token 的请求，确认被拒绝。
3. diff 范围检查。
