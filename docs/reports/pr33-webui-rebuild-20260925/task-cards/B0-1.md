## 目标

用真实浏览器记录当前工作台（`resources/static/` 旧 UI）的实际体验和缺陷，给 P1 设计提供一手事实。凡是能用浏览器看到的，不靠读代码下结论。

## 背景与输入

- 01 报告 §4–5 的问题清单；04 执行单 §1 缺口 G1–G6。
- `tests/rebuild/test_workbench_e2e.py`、`tests/rebuild/conftest.py`：构造项目的夹具方式。
- 启动方式：`deck-master --json view --project <dir> --open --no-open`（输出中含 `review_url`；只带 `--no-open` 不会启动服务，见 05 文档 N01）。
- 旧 UI 的读取入口：`GET /api/view`、`/api/pages/<id>`、`/api/tasks`、`/api/reviews`、`/api/history`；写入入口：`POST /api/edit|feedback|cancel|restore|check|export`（需 `X-Deck-Token`，由 `/api/session` 取得）。

## 可改范围 / 禁止

- **可改**：只写上述产出文件。一次性脚本放仓库外（如 `/tmp/dm-b0-1/`），不提交。
- **禁止**：修改 `src/`、`tests/`；使用客户项目或真实材料截图。

## 实施步骤

- [ ] 1. **构造测试项目**：在 `/tmp/dm-b0-1/project` 下用夹具或 `examples/` 构造项目，满足：≥4 页；至少 1 页有 `svg_preview`，至少 1 页有 `ppt_preview`；至少 1 页只有正文（没有任何预览）；≥1 条未关闭的审阅发现；≥1 个 `awaiting_host` 任务。把构造命令、项目 `revision_id` 和各页具备的槽位写进 `assets/b0-1/fixture.md`，保证可复现。
- [ ] 2. **启动工作台**：记录命令、URL、`/api/health` 返回值。
- [ ] 3. **Playwright 走查**：在 1280×800 和 1440×900 两种尺寸下各走一遍以下 12 步，每步截图，文件名为 `<尺寸>-<步号>-<动作>.png`：
  1. 首次打开；2. 切到第 2 页；3. 依次切换 content / svg_preview / ppt_preview / blueprint 视图；4. 切到只有正文的页；5. 直接改一处标题并保存；6. 保存后刷新；7. 在另一页输入不保存，然后切页再切回；8. 框选一块区域并提交意见；9. 查看任务列表；10. 取消该任务；11. 打开历史；12. 导出 review。
- [ ] 4. **逐项复核**：把 01 §5 的每一项、04 §1 的 G1–G4 列成表，逐项标注 `已复现 / 未复现 / 与描述不同`，并附截图或网络请求记录（Playwright 抓取请求体与响应）。G1 必须附上 `/api/feedback` 的实际请求体。
- [ ] 5. **新发现**：记录报告没列出、但实际操作中出现的问题（布局溢出、焦点丢失、错误无提示、内部术语外露等）。
- [ ] 6. **按 U 场景归类**：把每个问题对应到 U01–U15 中的场景，没有对应场景的标注“其他”。

## 产出格式（05 文档）

1. 环境：源码 SHA、Python 版本、浏览器版本、夹具说明链接。
2. 复核表：`编号 | 来源(01§5/G1..) | 操作 | 观察 | 结论 | 截图 | 严重度(阻断/高/中/低) | 对应 U`。
3. 新发现表：列同上。
4. 结论：一段话概括旧 UI 哪些可复用（交互或代码层面），哪些必须重做。

## 验收方法

1. `git diff origin/codex/webui-rebuild...HEAD --stat`：只允许出现 05 文档和 `assets/b0-1/`。
2. 照 `fixture.md` 重建项目，抽查 3 个步骤（必须包含第 7 步和第 8 步），在浏览器中复现，与截图对比。
3. 抽 2 项“未复现”的结论，亲自复现一次，确认结论成立。

## 失败去向

构造不出符合条件的项目时（例如缺少 ppt_preview 渲染器），在 05 中写明缺什么、为什么，用已有部分完成其余步骤，并在回填里把它标为未验证项，不伪造。
