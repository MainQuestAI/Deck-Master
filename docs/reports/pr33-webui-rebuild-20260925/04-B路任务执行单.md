# Deck Master B 路（Web UI 工作台重构）任务执行单

**版本：v0.2｜日期：2026-09-25｜分支：`codex/webui-rebuild`｜基线：`main@c93f5a2`**

本执行单把 [03 方案](03-Deck-Master方案工作台重构方案-v1.0.md) §11.2 的 P0–P5 拆成可派发的执行卡。每张卡可以单独交给一个 AI 执行者，卡内写明输入、可改范围、产出和验收。P0–P5 的详细任务卡已落在 [task-cards/](task-cards/README.md)（每卡含可改范围、实施步骤、验收标准、验收方法与回填表）；**派发与验收以任务卡为准**，本单保留总览、已核实缺口与决策记录。执行由其他 AI Agent 完成，Claude Code 负责验收。

## 0. 通用规则（每张卡都适用）

- **起点**：从 `codex/webui-rebuild` 最新提交开始；开工前 `git fetch && git rebase origin/main`，rebase 后跑 `python3 -m pytest -q tests`，全绿再动手（仓库内无 `.venv`，用本机 `python3`）。
- **共享文件归属**：`src/deck_master/view.py`、`src/deck_master/web.py` 属于共享接口。改动必须先作为独立 PR 合入 `main`，B 路再 rebase 获取（见 01 报告 §9）。B 路不直接改 `service.py`/`tasks.py`/`editing.py` 的行为；需要时提出接口需求，由 A 路或共享接口负责人实现。
- **B 路自有范围**：`src/deck_master/resources/static/`（前端）、`docs/reports/pr33-webui-rebuild-20260925/`（本线文档）、新增的前端/浏览器测试。
- **禁止**：用样本数据冒充真实状态；借 UI 重构改 Builder、制作链或审阅规则；客户原始资料、运行目录、密钥进入仓库。
- **证据**：每张卡交付时回填卡末“交接回填”，至少写：源码 SHA、实际命令与结果、截图/记录路径、未验证项。截图只能用测试夹具或示例项目，不用客户项目。
- **不能沿用旧关闭记录**：T14 已关闭，不代表新 UI 通过验收。新 UI 验收以 03 方案 §12.2 的 U01–U15 为准。

## P0 基线与连接验证

### B0-1 旧 UI 浏览器基线复核

- **目标**：用真实浏览器记录当前工作台的实际体验和缺陷，为新设计提供事实依据，而不是只靠读代码判断。
- **输入**：01 报告 §4–5 的问题清单；`tests/rebuild/test_workbench_e2e.py` 的夹具构造方式；`deck-master view --open --project <dir>`。
- **范围**：只读，不改源码。可以在仓库外（如 `/tmp/dm-p0/`）用夹具或 `examples/` 构造一个至少 4 页、带 SVG/PPT 预览、带一条未关闭审阅发现的项目。
- **步骤**：
  1. 构造项目，启动工作台。
  2. 用 Playwright 在 1280×800 和 1440×900 两种尺寸下走一遍：打开 → 切页 → 切换四种视图 → 直接改字 → 框选并提交意见 → 查看任务 → 取消 → 历史 → 导出。
  3. 对 01 报告 §5 的每一项标注：浏览器中已复现 / 未复现 / 与报告描述不同。
  4. 记录报告没列出、但实际操作中出现的问题。
- **产出**：`05-P0-旧UI浏览器基线.md`（问题表：场景、操作、观察、截图、严重度）；截图放 `assets/p0/`。
- **验收**：01 §5 每一项都有复现结论；两种尺寸都有截图；所有观察都来自真实浏览器操作，不从代码推断。
- **建议执行者**：Claude Code（配合 Playwright）。

### B0-2 宿主交接验证

- **目标**：回答 03 方案 §14 第 1 项：正常安装下，Web 提交的修改能不能被 Codex 可靠地自动接手？不能的话，最好的手动退路是什么？
- **输入**：G6；`docs/agent-task-index.md`；`skills/deck-master/` 主 Skill；`task start/accept` 命令；03 方案 §7。
- **范围**：只读加实验。可在仓库外写一次性验证脚本，不改产品代码。
- **步骤**：
  1. 列出候选路径，逐一实测或给出不可行的证据：
     - a. Host 会话按 Skill 指引主动运行 `continue`/`view`，发现待处理任务（拉取模式）；
     - b. Codex Desktop 是否有可从外部触发的入口（深链接、MCP、CLI、文件监听）；
     - c. 手动批量交接：Web 生成一段可以直接粘贴给 Codex 的完整指令（包含页面、区域、基准版本），Host 接手后调用 `task start`。
  2. 至少用一条真实修改走通最可行的路径：Web 提交 → Codex 接手（任务状态变为 `running`，记录执行方）→ `task accept` → Web 显示结果。
  3. 记录每种路径需要用户做几步、会在哪里失败、失败后能否恢复。
- **产出**：`06-P0-宿主交接验证结论.md`：候选路径对比表、实测记录、推荐主路径和退路、对 Skill/接口的需求清单。
- **验收**：推荐路径至少有一次真实往返记录；不可行的路径有具体证据（不写"应该不行"）；明确说出哪些能力没有验证。
- **建议执行者**：Claude Code 主导分析；实测需要老板在 Codex Desktop 中配合一次。

### B0-3 接口映射与缺口清单

- **目标**：把 03 方案 §9.1 的最小接口语义，逐项对到现有 `deck_view.v1` 字段和 `/api/*` 路由，得出一份共享接口草案。
- **输入**：`view.py`、`web.py`、`tasks.py` 的任务状态机；本单 §1 的 G1–G5；03 方案 §9。
- **范围**：只读，不改源码。
- **步骤**：
  1. 为 03 §9.1 的每项语义标注：已有（字段/路由）/ 部分具备（缺什么）/ 缺失。
  2. 复核并补充 G1–G5，给出每项的最小增量建议：字段名、路由、属于 B 路还是 A 路。
  3. 对 03 §14 第 2–5 项（请求与结果关联、整稿命令、预览适用性、导出分离）逐项给出初步结论。
  4. 把增量映射到现有任务卡（T12/T13/T14/T15）和 AC；超出原卡范围的部分标为规格增量。
- **产出**：`07-P0-共享接口草案.md`：映射表、增量列表（按 B 路 / A 路 / 共享接口归属分组）、任务卡对应关系。
- **验收**：03 §9.1 每项都有结论；每个增量都能追溯到 U01–U15 中的具体场景；不写 PR33 并不具备的能力。
- **建议执行者**：Claude Code。

### 决策点 G0

P0 三份产出齐备后，由老板确定：交接主路径（自动 / 拉取 / 手动批量）、接受哪些接口增量、首版是否包含批量交接。决策结果回写到本单 §6 决策记录。

## P1 工作模型与交互

### B1-1 用户动作与状态表

- **目标**：把内部任务状态翻译成用户能理解的状态，并定义每个动作的即时反馈。
- **输入**：G0 决策；07 接口草案；03 方案 §6、§8。
- **产出**：`08-P1-动作与状态表.md`，包括：
  - 动作表：用户动作 → 调用的接口 → 立即反馈 → 最终结果 → 失败时显示什么；
  - 状态映射：`awaiting_host`/`running`/`completed`/取消/冲突/过期 → 用户看到的文案和可做的下一步；
  - 覆盖 03 §8 的全部异常情况。
- **验收**：03 §6 的每个操作都在表中；每种状态都有"下一步是什么"；表内不出现 hash、SVG、Host 枚举等内部术语。

### B1-2 可交互原型

- **目标**：在接入真实接口之前，用原型验证"看整稿 → 改一页 → 等待 → 比较 → 再改"这条路径能否被理解。
- **范围**：独立原型文件，放在 `docs/reports/pr33-webui-rebuild-20260925/prototype/`，不替换 `resources/static/`。数据使用真实规模（≥12 页、真实标题长度），每个样本状态都标注"样本"。
- **必须包含的画面**：整稿概览、单页阅读与修改、等待 Codex、修改中、结果对比、冲突、失败、部分完成、仅有正文（U01）。
- **验收**：1280/1440 两种尺寸可用；老板能在不看说明的情况下走通主路径；缺少接口支撑的状态已登记到 07 草案。
- **建议执行者**：设计与原型交给前端能力强的 AI；Claude Code 负责走查和评审。

### B1-3 首版范围定稿

- **产出**：更新 03 方案（v1.1）：首版包含的场景（从 U01–U15 中选）、明确后置的能力、P2 切片的精确边界。
- **验收（决策点 G1）**：老板签字确认后，才开始 P2 编码。
