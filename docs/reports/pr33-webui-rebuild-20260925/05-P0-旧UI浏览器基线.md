# 05 · P0 旧 UI 浏览器基线（B0-1）

> 任务卡：[task-cards/B0-1.md](task-cards/B0-1.md)。本文所有结论都来自真实 Chromium 走查截图，或 Playwright 抓到的请求和响应。没有依据读代码得出的推断。

## 0. 结论先行

旧 UI 的**数据通路基本可用**：读稿、切槽位、改字保存、框选提交、取消、导出审阅稿、下载 PPT 都能在浏览器里跑通。但**交互层没有一处能直接给新产品用**：

- 内部术语直接外露，比如 `awaiting_host`、`repairawaiting_host`、`edited`、`title/item_text`、原始 finding JSON。
- 页面导航只显示 `p1 · p01`。
- 修改意见会串页。
- 历史记录一点就恢复。
- 页面不会自动刷新。
- 框选区域被当作 JSON 文本拼进 instruction。

可以复用的只有底层能力：`/api/*` 的数据形状、revision/page_hash 并发保护（双击第二次被拒绝）、正文编辑器的按页草稿、区域框选的归一化坐标。页面结构、文案、状态呈现、历史、任务、审阅都要重做。

## 6. 结论

**可复用（交互或代码层面）**：

- `/api/view`、`/api/file`、`/api/edit`、`/api/feedback`、`/api/cancel`、`/api/export` 的数据通路在浏览器里都能跑通。
- base_revision/page_hash 的并发保护真实生效。R15 的第二次点击被正确拒绝，意见也保留下来了。
- 正文编辑器按页保存草稿的机制（R13 对照组）可以直接沿用，并推广到修改意见。
- 框选的归一化坐标和 revision/artifact 绑定，数据本身是准确的，只是传输方式错了（G1）。
- 1280 和 1440 下布局没有溢出。

**必须重做**：

- 信息架构：项目目标、页导航、主动作层级，以及布局从两栏改为三栏。
- 全部面向用户的文案与状态：去掉英文代码、JSON、hash、路径。
- 修改意见的作用域：按页保存或清空，提交后给出明确的成功状态。
- 区域作为结构化字段传输，并支持多页和批量。
- 任务的完整生命周期和自动刷新（G2、G3）。
- 问题（finding）成为可以操作的工作对象。
- 历史改为先看后恢复。
- 下载、审阅稿、交付稿三者的语义与未完成项说明。
- 编辑导致 pptx 失效时要主动告知（N04）。
- 失败提示要给出下一步。

其中**阻断级**两项必须在 P1 设计里优先解决：R13 意见串页、N04 改字后交付物静默失效。
