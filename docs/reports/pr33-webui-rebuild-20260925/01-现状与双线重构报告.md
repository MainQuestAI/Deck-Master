# Deck Master：PR33 现状与 Web UI 双线重构讨论报告

日期：2026-09-25（同日按 PR33 第三轮修复 `c93f5a2` 更新基线）。用途：供项目负责人和 GPT6PRO 共同讨论下一阶段方案。本文是代码与项目记录审查，以及产品建议；不是新 UI 已实现或已验收的声明。

## 1. 结论：保留制作基础，重建用户工作的组织方式

PR33 已修复一批真实影响成稿的编译、逐页审图和修改恢复问题。项目记录明确：用户已认可当前输出内容、整体效果和 Builder 可用性。这部分应作为下一阶段基础，继续针对真实问题改善。

Web UI 则需要重新定义产品职责、工作对象、信息架构和交互闭环。当前界面把正文、蓝图、SVG、PPT 四种产物，以及编辑表单、修改意见、任务列表、历史、下载堆在同一工作页上。它具备不少底层操作，却没有把这些操作组织成清楚的用户工作路径。

建议从 PR33 的固定提交分两路推进：

- **A 路：效果与流程。** 让现有任务、材料和决定可靠传入成稿与制作；补资料、改要求和局部返修可以持续推进；按真实问题改善效果。
- **B 路：Web UI 产品重构。** 重新回答它服务谁、用户为什么进入、主要做什么、与 Codex 如何分工，以及每次操作如何抵达明确结果。重写界面实现，保留可信数据和执行基础。

最重要的共同约束：两路共享同一个当前项目、页面、任务、审阅结果与导出判断。不能为了漂亮的新前端再建立第二套状态或模拟执行流程。

## 4. 为什么当前 Web UI 定位尴尬

### 4.1 三种定义没有统一

项目总定义是 **Agent-operable Solution Deck Run OS**；任务卡当前范围收敛为 **Codex Desktop 专用版**；`DESIGN.md` 却将 Web UI 定义为 **Agent 唤起式 run 审查面板**，围绕批准、补证据、驳回和交付确认组织动作。

实际界面标题是 Review Workbench，但提供正文修改和 AI 返修，同时展示 Pending Host Tasks。用户既被当成审查者，又被要求面对内部生产任务。它没有清楚说明：这里能完成什么，哪些事情交给 Codex，什么时候需要回到 Codex，以及回来后怎样确认结果。

这是职责不清带来的交互问题。仅更换框架、颜色或三栏布局不会解决它。

### 4.2 以产物格式为主导航，不能直接回答用户的问题

首层标签是“正文 / 原图 / SVG / PPT”。这些产物都值得保留，但用户通常首先要判断的是：

1. 整套方案是否讲清楚了？
2. 哪几页需要修改，为什么？
3. 刚才修改是否完成，实际变好了什么？
4. 当前下载的是哪一版，是否适合发出去？

四种格式可以成为页面内部的对照工具；不必继续承担整个产品的信息架构。

### 4.3 有提交动作，没有可理解的交接闭环

`/api/feedback` 创建 `repair` 任务并返回 `awaiting_host`。这是诚实的后台行为，但按钮写“交给 Codex 修改”，容易形成“Codex 已收到并开始处理”的期待。

当前页面没有 Host 唤起/连接机制；JS 也没有定时轮询或事件订阅，仅首次加载、手动刷新及本页动作后刷新。用户提交之后，无法依靠界面持续知道“待接手、已接手、正在修改、结果已回来”的完整过程。

需要准确区分：**运行时已有“接手”事实，缺的是投影和刷新。** 任务状态包含 `awaiting_host` 与 `running`；`deck-master task start --execution-ref` 调用 `service.task_start` 把任务登记为 `running` 并记下执行方，另一执行方重复接手会冲突；`accept_result` 写回后任务变为 `completed`。因此“待接手 → 已接手 → 结果已回”可以由现有事实支持，前提是 Host 按约定调用 `task start`。B 路要补的是：`project_view` 投影这些状态与执行方、前端持续刷新、以及约束 Host 必须先登记接手；不需要另建一套执行状态。

新方案必须明确选择：可靠接入宿主，或提供诚实、具体且可回来的手动交接。不能显示假的运行进度。

## 5. 现有 UI 问题清单：事实、影响与重构要求

| 问题 | PR33 实现事实 | 用户影响与重构要求 |
| --- | --- | --- |
| 项目目标缺席 | `project_view` 没有投影完整任务 brief/受众/用途/既定决定，也没有完整材料工作区 | 无法对照“这份稿为什么这样做”。需要可见的任务摘要和选入资料；结构化信息可从自然语言提取，不加必填问卷 |
| 页面导航贫弱 | `renderPageList` 显示 `p序号 · page_id`，未显示页面标题、缩略图及可处理问题摘要 | 难以按业务内容找页。导航应能按标题、位置、问题和进展找页 |
| 内部状态直接外露 | 顶部输出 `view_status`；任务显示 kind/status 与截断的 instruction | 用户需翻译工程术语。应显示当前情况、影响、责任人和下一步；技术详情可展开 |
| 操作层级不清 | 下载、导出、历史、正文表单、反馈、审阅记录位于预览下方；没有随工作情境变化的主动作 | 看稿与处理问题分离，操作意图混杂。应围绕当前用户任务安排控件，而非围绕 API |
| 修改入口缺乏语义 | 正文编辑标签使用 `atom.kind`；字段按内容原子展开 | 用户在改结构化数据，不易辨认页面部位。需要保留内容结构和位置的编辑方式，明确保存对成品的影响 |
| 问题不是工作对象 | 审阅 finding 直接 `JSON.stringify`；当前 UI 没有按问题定位并处理的完整控件 | 可寻址的数据尚未成为可操作体验。需要问题列表→定位页/区域→修订→复核→关闭 |
| 审阅现行性投影不足 | `current_output` 以是否引用当前整套 PPTX 判断；页面筛选依赖当前 Page 引用 | 页级 SVG/蓝图审阅可能无法得到准确的“当前产物”标签，历史页面记录也可能被筛掉。需按审阅对象和依赖判断适用性，不靠前端猜测 |
| 对照功能不足 | 当前是互斥标签切换，没有并排原图/成品或修改前后对照 | 用户需记忆差异。新方案应支持同页、明确版本的比较，不能拿旧预览当新结果 |
| 历史查看即恢复 | 历史列表每个按钮点击就 POST restore；没有先查看差异的步骤 | 恢复是有影响的修改，应该先看版本内容和影响，再明确执行。恢复仍创建新版本 |
| 下载和交付语义不清 | 有 PPTX 引用就显示“下载当前 PPT”；另有“导出工作稿”；无明确 delivery UI | 用户不能仅靠按钮判断文件用途。需区分当前文件下载、审阅稿和交付稿，说明实际未完成项，不额外新建审批链 |
| 失败恢复缺少指引 | 请求失败主要展示异常字符串；无结构化的恢复动作 | 服务断开、版本冲突、宿主未连接不应只有报错。需保护草稿并给出明确下一步 |
| 设计规范与实现脱节 | `DESIGN.md` 要求三栏决策台；当前 CSS 是两栏；旧路径仍指向已退役 UI。静态 CSS 声明字体名但没有 `@font-face` | 现有规范不是当前产品的可靠蓝图。需要重写产品和交互定义后再整理视觉规范；字体实际加载需浏览器核验 |

另外存在待浏览器定向复核的代码风险：框选区域在切页时清空，但反馈文本未按页保存/清空；放大状态在重建图像 DOM 后未重新应用；修改动作没有统一的处理中防重提交状态。这些不在本报告中冒充已复现缺陷，也不应抢占整体产品定义工作的优先级。

T14 虽记录“整卡关闭”，其 U07 证据包括静态源码断言和沿用的 2026-09-16 目视证据。它不能证明 PR33 当前所有交互在真实浏览器中可用，更不能代替用户对新产品体验的验收。

## 6. 定位必须先做选择

| 候选定位 | 核心职责 | 好处 | 代价/风险 |
| --- | --- | --- | --- |
| 纯审阅台 | 看稿、提意见、检查问题、导出 | 职责最窄，与 Codex 分工简单 | 修改和推进仍要频繁回到 Codex；必须明确放弃制作控制职责 |
| **Codex 协同的方案制作工作台（建议主方案）** | 围绕整套方案和页面组织看稿、修改、对照、问题处理、推进、交付；Codex 承担理解和生成 | 接近现有能力，也更符合专业用户改稿过程 | 必须补可靠宿主交接和状态更新；需要明确哪些修改自动生效、哪些需生成 |
| 独立 AI 演示应用 | 在 Web 内从资料到 AI 执行和交付全程完成 | 单界面闭环 | 要新增执行器/会话/工具接入与连接管理，超出现有 Web 壳重写；还要重新决定 Codex 的位置 |

建议以第二种为默认讨论起点，但 GPT6PRO 应能挑战它，不能被迫只为既定方案画界面。若最后选择第三种，需要明确扩大的产品范围和新的执行责任，不能只新增一个聊天框就宣称独立运行。

推荐定位的一句话：**帮助专业用户把一份方案做对、改好并交出去；Codex 做内容理解与制作，Web 工作台让用户看清成果、准确修改并掌握进展。**

## 7. B 路应重新定义的工作模型

### 7.1 四类核心对象

- **方案**：目标、受众、场景、选入材料、当前整稿、待解决问题与交付版本。
- **页面**：业务标题、正文、视觉结果、来源、当前进展和相关修改。
- **修改请求/问题**：针对什么、想改成什么、谁处理、是否接手、结果如何、是否仍待处理。
- **版本/交付物**：改动范围、产物更新时间、比较与恢复、导出用途。

蓝图、SVG、hash、operation ID 等继续存在，但不应要求普通用户先理解这些概念才能改稿。

### 7.2 建议的工作空间

这是可讨论的逻辑结构，不是已批准的界面布局：

```text
当前方案：业务名称 / 简短任务目标 / 真实进展 / 当前需要做什么
│
├─ 整稿：页面缩略图与顺序，快速理解叙事和未完成范围
├─ 当前页：成品主视图，正文修改，来源，对照，区域意见
├─ 修改与问题：待接手 → 处理中 → 结果待看 → 已解决/需继续修改
└─ 版本与交付：改动记录、前后比较、恢复、审阅稿/交付稿

任务目标与材料：随时可查看/更新的上下文入口
执行详情与诊断：按需展开，不抢占主工作区
```

“已解决/待看”等是用户层表达，不是直接新增一套存储状态。必须由当前任务、产物和审阅事实支持；哪些事实缺失，列为 A 路或共享接口增量。

### 7.3 一个必须贯通的例子

用户打开第 6 页，发现流程箭头方向错误：

1. 在当前成品上框选箭头并写“应从渠道指向平台”；提交前能确认针对哪页、哪个版本。
2. 提交成功显示“修改请求已保存，等待 Codex 接手”。若宿主没有连接，说明实际交接路径，不假装开始。
3. Codex 真正接手后，界面更新为处理中；保留旧成品可看，同时明确它不是新结果。
4. 新结果写入后，界面提醒“第 6 页已更新”，直接提供修改前后对照；不打断正在编辑的另一页。
5. 相关复核结束后展示实际结论；用户仍不满意可继续补充意见。未受影响页面不重制。
6. 下载或交付时明确当前版本，以及是否还有未完成页和必须修复的问题。

这条链路必须在真实宿主和真实产物上验证。只有交互原型点击得通，不算完成。

### 7.4 状态表达至少覆盖这些场景

| 实际情况 | 用户应看到 | 合理动作 |
| --- | --- | --- |
| 尚无页面，任务待接手 | 已登记任务，等待开始；展示已有目标和材料 | 按真实连接方式交接/继续 |
| 正在制作部分页面 | 哪些页已有结果、哪些页在做 | 浏览已有成果，必要时取消具体任务 |
| 修改已提交但未接手 | 请求已保存，尚未执行 | 查看/撤销请求，完成宿主交接 |
| 页面更新但预览未生成 | 正文已保存，成品待更新；旧图清楚标旧版 | 继续制作，不能误以为修改丢失 |
| 版本冲突 | 服务端已有更新，本地草稿保留 | 比较并重新提交，不自动覆盖 |
| 发现必须修复问题 | 问题、位置、实际影响 | 定向修改及复核 |
| 差异合理且证据充分 | 差异已接受及其理由 | 继续，不重复阻断 |
| 服务断开或宿主未连接 | 分清数据服务与执行宿主的连接状态 | 重连/重新打开/交接，保留输入 |
| 可导出审阅稿但不可交付 | 说明未完成内容 | 导出审阅稿或处理真实阻碍 |
| 同一产物反复审阅仍未关闭（`review_no_progress`） | 哪页哪条问题反复未通过、上次修复改了什么 | 补本页修复与复核证据，或对 needs_judgment 明确接受合理差异；不能只有停止提示 |

## 8. A 路：继续解决效果和流程

PR33 收录的前链路评审已指出以下问题。本次核对代码确认任务投影、CLI 输入和目录接入缺口仍在；安装链接问题只是当时机器环境记录，本次未重新审计，不能推广到所有安装。

| 顺序 | 工作 | 完成标准 |
| --- | --- | --- |
| A1 | 工作单带上已存盘的 brief、受众、用途、篇幅、既定决定；CLI 能登记这些事实 | 新建与恢复不依赖旧聊天记忆，不重复询问已决定的问题 |
| A2 | 普通材料目录的选入、版本与排除规则；任务事实/材料中途更新 | 只选有效来源；补资料后能解释影响哪些内容和页面 |
| A3 | 精简主 Skill 与活动引用，同版本 CLI/Skill 可发现 | 独立候选可按正常入口工作，避免旧术语与失效指引 |
| A4 | 用正常真实需求验证前链路与局部改稿 | 首稿对应实际任务；后续改动不让用户手工维持内部流程 |
| A5 | 有证据的问题驱动制作专项修复 | 对角渐变先比较真实 SVG/PPT；额度幂等按重复提交/重试行为验证 |
| A6 | 审阅停滞出路：`review_no_progress` 按页/按发现计数，并给出可执行恢复动作 | 无关页编辑不重置计数；用户或 Host 能沿提示走出停滞，而不是死胡同（与 PR33 第三轮延后的 P3 同源） |

效果应看首次完整稿的任务匹配、业务表达、视觉与可编辑成品。不能仅看测试数，也不默认重做用户已认可的对照稿。

## 9. 双路如何并行而不互相拖住

PR33 合并后已从 `main`（`c93f5a2`）创建两条分支：`codex/flow-quality`（A 路）与 `codex/webui-rebuild`（B 路，worktree `webui-rebuild`）。尚未修改运行时代码或启动多 Agent 工作。

同步规则：

- `main` 是修复汇入点；新的已验证修复进入 `main` 后，两路各自 `git rebase` 到 `main`，不做逐个 cherry-pick，避免同一修复在两路形成不同提交。
- A 路修到 `view.py`/`web.py` 共享接口的改动，先合入 `main` 再由 B 路 rebase 获取；B 路不直接改 A 路负责的 service/tasks 行为。
- 两路之间不互相合并；最终集成顺序由 `main` 决定。任一路 rebase 后必须重跑完整 `tests` 通过再继续。

| 责任 | 主要边界 | 交接内容 |
| --- | --- | --- |
| A 路 | service/tasks/editing/sources/CLI/Skill，以及具体效果缺陷 | 稳定任务事实、按页影响、执行结果、恢复和交付行为 |
| B 路 | 产品定义、用户旅程、信息架构、原型、静态前端与浏览器交互 | 需要什么事实和动作；页面与组件；真实状态和异常体验 |
| 共享接口负责人 | `view.py`、`web.py`、必要合同增量 | 单一读模型、命令语义、状态解释；两路共同验收，避免各写一套 |

先形成一份薄的接口约定，至少明确：任务摘要与材料、页面标题/缩略图/产物适用版本、问题与位置、请求作用页与执行状态、下一步动作及原因、导出用途。字段是待设计的增量，不是声称 PR33 已提供。

特别要明确三项：

- **宿主交接**：谁能真正启动/接收 Codex 任务，什么事实能证明接手；自动桥接不可行时采用何种真实回到宿主的动作。
- **持续更新**：轮询或事件机制如何刷新状态，如何保留草稿、选择页和对照版本；不要求先上复杂事件平台。
- **写入反馈**：每个操作返回已发生什么、影响哪些页、尚未完成什么；保留现有冲突/取消保护。

B 路可以先用标明为设计样本的状态数据做原型，但连接真实 API 是交付门槛。未实现能力不能被样本卡片隐藏。

## 10. 推进顺序与验收

1. **定位与边界**：确定主用户、核心工作、Codex/Web 分工；决定旧审查台定位和三栏审批逻辑哪些废弃。颜色字体不必先改，但不能让旧布局锁死新工作流。
2. **工作模型与接口**：贯通“看整稿→找问题→改一页→宿主执行→比较→交付”，确认真实状态与缺失能力。
3. **可交互原型**：至少包含正常过程、等待宿主、修改中、冲突、失败、部分完成；用真实内容规模检查 1280/1440 桌面空间。
4. **接入与实现**：B 路实现界面；A 路补流程；共同验证实际请求、页面版本、审阅与导出。
5. **真实任务验收**：从一项正常需求贯通，记录自然出现的问题及修复。通过后再决定默认切换，不借本次报告自动部署。

验收重点：

- 用户能说明当前是什么稿、做到哪、谁在处理、下一步做什么。
- 不理解 SVG/hash/Host 枚举也能浏览、修改、比较和获取文件。
- 提交请求不等于开始执行；任务完成不等于成品已就绪；状态与真实事实一致。
- 改一页不无故重制全套；切页、刷新、冲突和重连不丢输入。
- 问题能到达相关页面/区域，修订后能看见实际差异与复核结果。
- 下载、审阅稿、交付稿的版本与用途清楚；不把真实阻碍藏起来，也不追加没有业务价值的审批。
- 在正常浏览器中实际验证四视图、编辑、框选、状态更新、取消、恢复和导出。静态字段、HTTP 成功或单元测试不代替用户操作。
