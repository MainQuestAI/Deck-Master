# Deck Master 方案工作台重构方案

**版本：v1.0｜日期：2026-09-25｜状态：正式方案稿，供产品与实施评审**

**技术基线：PR33 `c439f686744ec72f8933521ca3cb103d7eee08a0`（起草时）。** 本方案以该固定版本及已完成的讨论为依据，不随分支变化自动更新。

> **实施基线更新（2026-09-25）：** 实施以 `main` 上的 `c93f5a2d1bb1ce9cc038ed3d42671cd5d3db7710` 为准（PR33 第三轮修复，已合并）。它修复了 `c439f68` 中“最终审阅缺 PPTX 引用导致发现永久无法关闭”的 P1，只改审阅闭环（`review.py`/`tasks.py`/`service.py`），未改 UI 相关文件，本方案的产品判断不受影响。B 路分支为 `codex/webui-rebuild`，A 路为 `codex/flow-quality`，两路均 rebase 到 `main` 同步。文中目标能力均为拟建要求；不表示已经实现、完成浏览器验证或获得发布授权。

## 一、方案决策摘要

Deck Master 的 Web UI 定位为 **Codex 协同的方案工作台**：用户在这里阅读方案、修改正文、指出画面问题、比较修改结果并取得对应版本的文件；Codex 负责理解、创作与制作，运行时负责项目事实、文件、任务和结果的可靠保存。

首版集中解决“看稿—修改—返回—比较—交付”的连续工作。工作台可以从完整正文阶段介入，不要求整套 PPT 制作结束后才打开。长期定位保留整稿组织与持续制作能力，避免收缩成只服务成品批注的审阅附件。

基于 PR33 分两路推进：

- **A 路：效果与流程完善。** 修通任务和材料交接、输入更新、持续制作、局部修改及具体成稿问题。
- **B 路：工作台重构。** 重新定义并实现信息架构、整稿与单页操作、修改往返、结果对照、版本和导出体验。

两路共享现有项目与运行时，不建立第二套任务和交付状态。先验证宿主交接，再确定自动交接主路径；手动批量交接作为明确退路。第一项联合成果是一条真实可用的修改往返，随后补齐整稿调整、异常恢复和交付。

| 决策项 | 本方案选择 | 取舍 |
| --- | --- | --- |
| 产品定位 | 方案工作台；首版聚焦看稿、修改、比较、交付 | 不建设独立模型应用，同时保留整稿工作的空间 |
| 首要对象 | 稿件、页面和用户修改 | 内部任务仅在执行详情中出现 |
| 主工作面 | 稿件、修改 | 材料、版本、导出和诊断按需打开 |
| 默认内容 | 有成品时看实际成品；只有正文时完整读稿 | 不用空幻灯片或虚构预览占位 |
| 宿主协作 | 优先验证可靠自动交接，保留批量复制退路 | 不预先承诺连接能力，也不将人工搬运固定为长期体验 |
| 普通修改 | 保存意图后在授权范围内连续执行，返回真实结果 | 不增加逐页批准、逐步确认 |
| 重构边界 | 替换 UI 与必要共享接口，保留可信核心 | 不借 UI 重构重做已认可的 Builder |

## 二、现状与问题依据

PR33 主要修复编译、逐页审图、结果接收和修改失效恢复。项目记录保留了用户对当前内容、整体效果及 Builder 可用性的认可。这些基础应继续使用，后续效果改进以实际问题为依据。

当前 Web 已具备页面浏览、正文/原图/SVG/PPT 查看、正文修改、框选反馈、任务取消、历史恢复及工作稿导出。核心问题在于这些能力按内部对象和接口排列，没有形成清楚的工作路径。

| 当前问题 | 已核实的基线事实 | 本方案的处理方向 |
| --- | --- | --- |
| 定位混杂 | 审查台定义下同时出现编辑、返修、内部任务管理 | 明确用户在此围绕稿件工作，执行细节退到次级入口 |
| 找页与读整稿困难 | 页列表以序号和 page_id 为主，格式标签承担主要导航 | 业务标题、缩略图、正文阅读和整稿概览优先 |
| 提交与执行脱节 | 反馈接口创建 awaiting_host 任务，不自动唤起 Codex | 分清保存、送达、接手、执行和结果回传 |
| 修改结果难比较 | 四视图互斥切换；无完整修改前后对照 | 以本次请求所对应的前后产物为比较对象 |
| 状态缺少业务解释 | 工程枚举及原始 finding 数据直接呈现 | 运行时提供事实，UI 解释影响和下一步 |
| 任务上下文不完整 | Host 工作单未完整携带已存盘的任务事实；目录输入等仍有缺口 | A 路补任务、材料与既定决定的可靠交接 |
| 历史与交付语义不足 | 历史点击直接恢复；下载当前 PPT 与工作稿导出并存 | 历史先查看和比较，再恢复；导出明确用途与快照 |

以上来自固定版本代码和项目记录。前期报告未进行本次浏览器目视验收，因此旧布局、字体和具体交互风险仍须实际核验。不得将“两栏变三栏”或符合旧样式规范作为重构成功依据。

## 三、产品价值、用户与范围

### 3.1 产品价值

工作台最重要的价值，是把用户看到的稿件、提出的修改、实际执行和返回结果连接起来。用户不需要重复描述截图、维护任务编号、寻找新文件或猜测当前是否已改好。

单次生成后直接在 PowerPoint 中精修的用户可以不经过工作台。需要与 Codex 持续协作、多轮修改方案的用户，是首版重点。

### 3.2 目标用户与核心工作

第一用户是对最终方案负责、已经使用 Codex 的个人方案负责人，包括售前、咨询顾问和解决方案架构师。

其核心工作包括：理解整稿与业务表达；调整页面和整稿叙事；修改文字和画面；比较实际结果；获取正确版本的文件。用户负责专业判断，不负责维护内部任务、依赖、哈希和编译顺序。

### 3.3 首版范围

| 纳入首版 | 本轮不建设 |
| --- | --- |
| 正文阶段与成品阶段的整稿阅读、页面定位 | 独立模型执行器和完整 Web 聊天应用 |
| 结构化正文编辑、区域意见、跨页修改请求 | PowerPoint 式自由排版、任意对象拖拽编辑 |
| 整稿顺序调整，以及删除、合并、拆分、全稿改写的明确入口 | 模板市场、知识库、团队项目管理 |
| 宿主交接、真实进展、结果关联、前后对照 | 多 Agent 调度平台、多人审批体系 |
| 任务与材料可见及更新、影响说明 | 通用文件管理器、全局素材中心 |
| 草稿保护、冲突与失败恢复、历史查看恢复、用途明确的导出 | 外部 PowerPoint 任意修改自动回写 |

“不建设自由排版”不限制用户准确表达视觉要求。用户仍可框选区域、引用对象和关系，将制作任务交给 Codex。

## 四、工作对象与职责

### 4.1 用户对象

```text
方案：目标、受众、用途、既定决定、选入材料
  └─ 当前稿件：按顺序组织的页面
       ├─ 页面：正文、实际画面、依据和待处理事项
       ├─ 修改：用户意图、范围、执行进展、对应结果
       ├─ 问题：期待与实际差异、位置、影响和处理依据
       └─ 版本与交付物：变更内容、比较、恢复和固定文件
```

方案复用既有项目，不引入云端空间。页面以稳定 ID 标识，页码只表示当前顺序。用户修改与质量问题分开：调整语气可以没有缺陷，修复漏字则可关联已有 finding。

一项修改可以驱动多个执行任务。用户始终看到“修正业务流箭头”这项工作，系统管理其重构、编译、预览与复核。执行任务结束不能直接等同于整项修改已经形成可比较成品。

版本面向有意义的用户变更组织，底层事务继续完整保存；不把每次状态更新都呈现成一份新稿。版本摘要缺少可靠描述时，展示实际修改范围，不生成未经依据的解释。

### 4.2 职责分配

| 参与者 | 负责 | 交接要求 |
| --- | --- | --- |
| 用户 | 业务目标、需要改变的内容、对结果的判断 | 已给出的决定持续有效；仅实质歧义或超范围时提问 |
| Web UI | 阅读、定位、编辑、请求、比较、恢复与获取文件 | 每个操作说明真实结果，保护输入和当前工作位置 |
| Codex Host | 理解材料、正文创作、整稿调整、制作、修订与审阅 | 读取当前事实，登记接手，提交真实产物和必要说明 |
| 运行时 | 持久化、版本、任务、依赖、结果采用、取消和导出判断 | 单一事实来源；所有写入经过既有服务与存储层 |

## 五、信息架构与界面组织

### 5.1 两个主工作面

**稿件**用于阅读和修改当前方案，包含整稿概览、正文阅读和页面阅读。**修改**用于查看本轮要求、执行进展、对应结果和后续修订。

任务与材料、版本、导出采用上下文面板。制作详情与诊断按需展开，不占据默认主工作区域。

首次打开已有初稿进入整稿概览；再次进入恢复上次页面与本地草稿；从修改结果入口进入对应比较。后台返回新结果时提示用户，不强行跳转正在编辑的页面。

### 5.2 整稿概览

```text
┌──────────────────────────────────────────────────────────────┐
│ 方案名称 · 面向业务负责人                 [任务与材料] [导出] │
│ 稿件  修改(2)                         [版本] [查找标题/正文]  │
├──────────────────────────────────────────────────────────────┤
│ [整稿概览] [连续阅读]               [全部页面 / 待处理]       │
│                                                              │
│ 01 背景与目标       02 关键问题        03 方案选择             │
│ [真实缩略图]        [正文待制作]       [真实缩略图]            │
│                                                              │
│ 04 能力与案例       05 业务流程        06 实施安排             │
│ [真实缩略图]        [修改待接手]       [有新结果]              │
│                                                              │
│ 选择页面后：[调整顺序] [提出跨页修改] [移除页面]               │
└──────────────────────────────────────────────────────────────┘
```

没有预览的页面显示真实标题与正文摘要。没有章节资料时不强造章节。筛选依据真实事项，不用综合质量分替代专业判断。

### 5.3 页面阅读与操作

```text
┌──────────────────────────────────────────────────────────────┐
│ ← 整稿  05 业务流程                          [版本] [导出]    │
│ 当前画面：修改前成品 · 正文已有更新，画面待更新                │
├────────────┬─────────────────────────────────────────────────┤
│ 页面导航   │ [改正文] [指出要改的地方] [比较] [制作详情]      │
│ 标题       │                                                 │
│ 缩略图     │                 实际页面                        │
│ 待处理提示 │                                                 │
├────────────┴─────────────────────────────────────────────────┤
│ 本页修改：箭头方向待处理                     [查看本次修改]   │
└──────────────────────────────────────────────────────────────┘
```

编辑、框选与问题详情打开面向当前动作的面板。对照模式可临时收起导航，保证内容可读。默认布局不永久占用一栏展示内部任务与审阅数据。

### 5.4 产物呈现规则

| 情况 | 默认呈现 | 补充入口 |
| --- | --- | --- |
| 只有正文 | 完整结构化正文，可连续阅读和编辑 | 任务、来源、待制作说明 |
| 当前有 PPT 成品 | 实际 PPT 渲染 | 正文、来源、制作详情 |
| 只有中间制作结果 | 可用制作预览，明确尚非 PPT 成品 | 原图、SVG 与阶段说明 |
| 正文已更新、成品未更新 | 新正文与明确标旧的画面 | 继续制作的实际状态 |
| 查看一次修改 | 固定的修改前后结果 | 文本差异、复核结果、制作对照 |

原图、SVG、PPT 的专业对照保留；它们不再作为普通用户必须逐步经过的导航。

## 六、整稿与单页交互方案

### 6.1 直接修改正文

用户在“改正文”面板中按标题、段落、条目、标签、表格与脚注编辑。保存产生新正文版本，并登记需要更新的相关产物与制作工作。界面说明“正文已保存，成品待更新”，保留旧画面。

多页小改可以汇集后一次处理。已经接手的修改不被后续编辑暗中改变，新编辑形成可追溯的后续修改。直接编辑不默认重新审批整稿；涉及事实与来源的变化，按实际影响进行检查。

### 6.2 区域意见与单页返修

用户在实际画面上框选，填写“箭头应从渠道指向平台，保留其他布局”。提交时保存稳定页 ID、所看画面、基准版本、归一化坐标与文字要求。

系统根据交接能力显示“保存并发送”或“保存修改请求”，分别返回实际保存和送达状态。只有 Host 登记本次请求接手后才显示处理中。结果返回后提供同页前后比较；只有 SVG 时说明是制作结果，不称 PPT 已更新。

用户可基于新版继续提出意见。系统保留修改链路，不要求先批准本页。原框选对应的画面已经变化时，不将旧坐标直接套用到新图。

### 6.3 整稿操作

| 操作 | 用户表达方式 | 系统行为 | 完成判据 |
| --- | --- | --- | --- |
| 调整页面顺序 | 在整稿中选择并移动，支持键盘操作 | 保存新顺序；沿用页面身份；更新受影响的页码、导航或整稿装配 | 新顺序准确，内容与意见仍对应原页面；无关视觉不重制 |
| 移除页面 | 选择页面后执行移除，明确范围并可恢复 | 从当前稿件移除；保留历史；处理该页未完成任务 | 当前稿不再含该页，历史可查，晚到结果不复活已移除页 |
| 合并页面 | 选中若干页，说明要保留的结论与内容 | Host 组织合并内容、制作并复核；记录原页到新页的关系 | 新页完整表达，来源保留；旧意见适用性有明确处理 |
| 拆分页面 | 选中密集页，说明阅读目标 | Host 提出并执行合理拆分；保持业务关系和阅读顺序 | 内容未遗漏，拆分页之间连续；历史可对应 |
| 调整叙事 | 选择范围或整稿，提出结论前置、压缩论证等要求 | Host 基于任务与正文调整，不由前端按关键词套规则 | 主线与目标一致，受影响页面和必要制作完成 |
| 统一跨页表达 | 选择相关页，要求统一术语、数字或图示关系 | 批量检查和修改；同一事实冲突时依据来源处理 | 相关页一致，未选页只有发现必要影响时才扩展并说明 |
| 改变受众或用途 | 更新任务事实并说明意图 | 保留已有决定，识别实际影响后继续执行 | 内容适合新要求，旧结果未被误标为新要求下的成品 |

合并、拆分产生新页面时须保留来源关系。旧页上的问题和区域意见不能自动搬到新页并宣称仍有效；需要重新定位或标为仅适用旧稿。具体关系字段在接口设计阶段确定。

顺序与页面集合变更优先复用既有核心能力；缺少服务命令时先补命令，不允许前端改项目文件绕过版本控制。

### 6.4 材料和目标更新

任务与材料面板展示当前目标、受众、用途、关键决定、所选材料及版本。用户可补选文件或更新要求，不重新填写一套完整问卷。

材料状态区分已登记、已选入、已读取及已形成影响判断；不能只凭上传成功宣称内容已被充分理解。浏览器文件选择与运行时目录选入使用各自真实入口。

运行时保存输入变化与已知依赖，Host 判断语义影响并说明涉及哪些页面。用户已经明确要求的调整连续执行；只有来源冲突、目标歧义或需要明显扩大范围时提出具体问题。普通补材料不增加例行批准步骤。

### 6.5 查看、比较与恢复版本

历史首先只读查看，用户可比较正文、顺序、页面集合与实际成品。比较对象固定，不随后台返回自动漂移。看过某版不构成质量通过。

恢复操作说明恢复范围及对当前工作的影响，并创建新的当前版本。历史不删除，真实调用和取消事实不倒退。正文、产物与进行中请求的处理必须由运行时完成。

### 6.6 导出与外部编辑

主界面提供统一“导出”入口，区分审阅文件、交付文件和制作工程。审阅文件可带真实未完成说明；交付文件使用当前实际检查；制作工程用于继续制作，不默认混入面向客户的文件包。

导出固定到明确版本。若旧版 PPT 仍可下载，但尚未包含最近正文修改，必须说明文件对应的旧版范围。缺少可导出成品时给出真实原因，不提供空文件。

当前运行时的 review 导出包含工程内容，需在实施时明确可分享文件与工程包的边界，不能只改按钮名称就将既有包称为客户审阅包。

PowerPoint 外部编辑在首版视为导出副本的后续工作，不自动同步回项目。重新纳入工作台需另行定义导入方式，本方案不承诺往返编辑。

## 七、宿主协作与持续执行

### 7.1 先验证，再选主路径

宿主连接是本方案的关键技术待验证项。验证必须针对产品实际可用的能力，不能把当前助手能调用的桌面工具直接当成 localhost 网页可用的 API。

| 验证内容 | 必须取得的结果 |
| --- | --- |
| 连接入口 | 有明确、可重复使用的宿主接收方式，不依赖临时人工改内部文件 |
| 目标识别 | 请求进入正确项目与会话；无法确定时不发往其他会话 |
| 实际接手 | 送达与接手可区分，接手对应本次请求 |
| 会话忙碌 | 有明确排队或延后行为，不随意中断其他工作 |
| 结果返回 | 真实产物被运行时接收，并能关联原请求与原画面 |
| 重复与恢复 | 重试不重复执行；取消、断开和晚到结果遵守核心规则 |
| 安装可用性 | 正常安装环境可复现，不能只在开发者当前会话成立 |

自动交接满足这些条件后作为默认路径。若尚不能满足，首版可采用手动批量交接，并在交付说明中明确限制；后续自动接入复用同一请求语义，不另造数据模型。

### 7.2 手动退路

工作台保存本轮修改，由运行时生成可直接复制的交接内容，带上准确项目身份、选定请求与可读取的上下文位置。用户粘贴到已有 Codex 会话后，Host 读取并登记接手，完成制作并回写结果。

交接不要求用户重写提示词、重新截屏或重新找材料。复制成功不等于已送达，更不等于已执行。手动模式没有可靠宿主在线信号时，只说明“尚无接手记录”。

手动方式是否可作为首版，取决于真实操作验证：多项修改可一次交接；用户无需维护路径和任务状态；结果自动回到对应位置。如果仍需逐项重复描述或寻找文件，则不满足可用标准。

### 7.3 状态同步与执行分离

首版可用轻量轮询读取版本和请求摘要，在有工作时较频繁更新、闲置时降频、窗口重新获得焦点时刷新。具体频率按响应负载验证确定，后续可替换为事件更新。

刷新只读取事实，不启动模型。接手、制作、检查与结果采用由真实动作产生。界面保留当前页面、草稿、缩放和固定比较对象；新结果只提示，不抢走用户工作位置。

## 八、状态与异常处理

同一页面可同时存在“正文已保存”“旧成品可看”“新制作待接手”。不将所有情况压成一个全局状态，不新增与运行时平行的 ready 判断。

| 对象/情况 | 事实来源 | 用户表达 | 操作 |
| --- | --- | --- | --- |
| 本地草稿 | 本地输入与基准版本 | 尚未保存 | 保存、撤销，切页保留 |
| 修改已保存 | 运行时持久化成功 | 修改要求已保存 | 发送、批量交接、撤销 |
| 已送达 | 宿主连接实际回执，仅自动模式存在 | 已送达，等待接手 | 查看、取消 |
| 已接手/处理中 | Host 接手及真实执行记录 | 正在处理相关页面 | 看旧稿、查看进展、取消 |
| 正文与画面不同步 | 当前内容与产物依赖 | 正文已更新，成品待更新 | 看新正文和标旧画面 |
| 有新结果 | 与当前输入匹配的结果被采用 | 页面有新结果 | 比较、继续修改 |
| 待复核 | 当前适用检查尚未完成 | 新结果待复核 | 看产物和真实待处理项 |
| 已取消 | 运行时确认不再采用后续结果 | 本次修改已取消 | 查看旧结果、重新提出修改 |
| 可交付导出 | 运行时统一检查当前整稿 | 当前版本可导出交付文件 | 导出固定版本 |

异常处理要求：

- **服务断开**：保留最后同步内容并明确标示，保护未提交输入；恢复后先取当前版本，再判断冲突。
- **保存结果未知**：按操作身份核实结果，不能因超时直接重复创建任务。
- **版本冲突**：保留基准、服务端新内容和本地草稿。无关变化不迫使丢稿；真正冲突才让用户选择或重新修改。
- **执行失败**：说明失败动作、保留结果和恢复方式，不重新初始化整套方案。
- **取消**：区分取消请求和已确认取消；外部调用不能立即停止时，明确其后续结果不会覆盖当前。
- **并行修改**：同页或同内容的冲突由运行时处理。UI 不凭提交先后自行合并，不把新要求写入已接手的旧请求。

用户“已查看”只作为阅读提示；问题是否关闭依赖实际复核；能否交付依赖统一检查，三者互不代签。

## 九、技术结构与共享接口

```text
Web 工作台                    Codex Host
阅读 / 编辑 / 请求 / 比较      理解 / 创作 / 制作 / 审阅
        │                           │
        └────── 统一服务与命令 ──────┘
                      │
        项目事实 / 请求关联 / 当前视图 / 导出判断
                      │
        现有对象存储 / 版本 / 任务 / 产物 / 检查
```

复用现有 `src/deck_master/` 核心，继续遵守新旧包边界；UI 不直接写 `.deckmaster/current.json`。前端可以重写，但现有真实产物、原件、版本和调用事实不能因 UI 切换丢失。

### 9.1 最小接口语义

| 接口领域 | 必须提供的事实/行为 | 重点 |
| --- | --- | --- |
| 方案上下文 | 目标、受众、用途、既定决定、材料版本 | 已确认事实能恢复，不依赖聊天记忆 |
| 页面集合 | 稳定身份、顺序、标题、正文、预览、适用内容版本 | 内容与预览分别表达现行性 |
| 修改关联 | 用户意图、范围、基准、关联执行任务与结果 | 一次用户工作可跨多个内部任务 |
| 问题解释 | 位置、期待/实际、影响、适用性与关闭依据 | 不将原始 JSON 交给用户理解 |
| 写入返回 | 已发生的动作、影响范围、后续工作与冲突 | 保存、送达、执行不能混写 |
| 历史与导出 | 只读版本、比较、恢复影响、用途与固定文件 | 不因后台更新改变下载对象 |

以上是接口语义，不要求新增六套 schema。具体采用扩展现有对象还是最小关联字段，在实施设计中逐项映射；能由当前事实推导的内容不另行持久化。

### 9.2 必要的一致性要求

保存正文与登记后续制作需求需保证一致，失败不得出现“正文已变但后续工作不可恢复”的悬空状态。请求基准和结果关联须可查询，以支持提交超时后的核实。稳定页面身份应支撑重排；合并拆分须明确新旧关系。

审阅适用性由共享服务按实际对象与依赖判断，不由前端凭时间或文件存在猜测。原件保持不可变；旧结果可查看但不能被标为新要求下的产物。

前端框架不是本方案的先决条件。详细实施设计再根据组件、打包、离线资源和测试要求选择；无论采用何种框架，均需支持当前本地安装形态。

## 十、视觉与交互原则

保留严肃工具感、冷墨底、克制的琥珀铜强调色、实面与清晰边界。第一视觉主体是稿件内容；状态只在影响用户决策时突出。默认减少常驻信息，以清楚的操作层级代替更多面板。

字体、样式和离线加载应通过真实浏览器验证。1280 与 1440 桌面窗口须能看图、编辑和比较；键盘操作有可见焦点；状态同时用文字表达；长标题、长稿、多页和加载失败不破坏主要路径。

本方案提出替换旧审查台 IA 与审批动作组织方式。方案评审后再同步更新 `DESIGN.md` 和相关入口说明；本次文稿不修改现行规则或把旧规范偏差直接认定为产品缺陷。

## 十一、A/B 双路实施安排

### 11.1 责任边界

| 工作线 | 主要范围 | 交付 |
| --- | --- | --- |
| A 路 | 输入、材料、工作单、持续制作、局部失效、真实效果缺陷、主 Skill | 可可靠执行和恢复的制作流程 |
| B 路 | 产品交互、原型、前端、草稿保护、浏览器验证 | 用户可理解并完成工作的界面 |
| 共享接口负责人 | view/web、请求关联、命令语义、宿主交接、状态解释 | 两路共同使用的一份接口及集成行为 |

两路从相同固定基线开始，显式同步后续修复。共享文件有单一负责人，另一条线通过接口需求和集成验收参与，不各自建立状态层。两条分支已从 `main` 创建，尚未启动并行开发。

### 11.2 推进顺序

| 阶段 | 工作内容 | 完成产物 |
| --- | --- | --- |
| P0 基线与连接验证 | 复核真实旧 UI；验证宿主交接；映射已有接口与缺口 | 浏览器问题记录、连接验证结论、共享接口草案 |
| P1 工作模型与交互 | 完整走通单页修改和整稿调整；定义异常与导出 | 可交互原型、动作/状态表、确定的首版范围 |
| P2 第一条真实切片 | 打开稿件→框选→保存/交接→接手→实际修改→结果比较→再改 | 真实 Host 与浏览器往返记录 |
| P3 整稿与输入更新 | 正文小改、重排/移除、合并拆分与跨页修改、补材料和改受众 | 整稿行为与影响传播验证 |
| P4 恢复与交付 | 冲突、取消、断线、历史恢复、固定版本导出 | 异常测试、真实文件及对应版本核对 |
| P5 候选与默认切换 | 打包/离线资源/Skill 同版本验证，更新规范和入口 | 可回退候选、真实使用记录、未验边界说明 |

A 路输入修复可与 B 路原型并行；B 路接线以相关接口完成为前提，不等待所有效果专项结束。对角渐变等制作专项只有影响当前切片时才成为其依赖。

正式编码前，将实施项映射到现有任务卡和 AC；超出原卡范围的部分先形成明确规格增量。不使用原 T14 的关闭记录替代本次新 UI 验收，也不重开已经认可的内容成果。

## 十二、验收方案

### 12.1 三个完成层级

| 层级 | 必须证明 | 不能据此声称 |
| --- | --- | --- |
| 设计原型完成 | 用户能走通场景，理解动作、等待、结果与异常；模拟状态已注明 | 已接真实核心或宿主 |
| 接线完成 | 所有真实读写、请求、版本、产物和检查来自核心；无第二套状态 | 已获用户体验或业务验收 |
| 真实流程可用 | 正常浏览器与 Codex 下完成修改、比较、再修改和正确导出 | 未测试材料的泛化、未记录的桌面编辑或正式发布 |

### 12.2 场景验收矩阵

| 编号 | 场景 | 必须观察到的结果 |
| --- | --- | --- |
| U01 | 仅有正文时打开 | 完整读稿、找页与修改可用；没有虚构预览 |
| U02 | 初次进入与再次返回 | 首次能理解整稿；再次恢复位置、草稿和比较对象 |
| U03 | 直接改字后刷新/切页 | 已保存正文准确，本地输入不串页；旧画面明确标旧 |
| U04 | 框选箭头往返修改 | 请求携带准确页面与画面；真实接手；箭头改对；结果可比较 |
| U05 | 多项修改批量交接 | 无需逐项重述和补图；请求与返回结果一一可追溯 |
| U06 | 重排和移除 | 页面身份不乱，意见不串页，移除页不因晚到结果回归 |
| U07 | 合并、拆分与跨页改写 | 内容与来源保留，新旧页可关联，意见适用性不假迁移 |
| U08 | 补材料、改受众 | 既定决定保留，影响说明有依据；无无意义整套重制或重复确认 |
| U09 | 双击、超时和重试 | 可核实是否已保存，不重复创建或执行同一操作 |
| U10 | 并发编辑与版本冲突 | 保留草稿，明确真正冲突；不以最后写入直接覆盖 |
| U11 | 取消、失败和重连 | 旧结果可用，输入不丢，晚到结果不覆盖，恢复不重走初始化 |
| U12 | 历史比较和恢复 | 先看后恢复，创建新版本，不抹去调用和取消事实 |
| U13 | 导出时后台返回新版 | 文件固定到选定版本，审阅/交付/工程内容边界准确 |
| U14 | 桌面与键盘操作 | 1280/1440 下画面和比较可读，框选准确，焦点与状态可理解 |
| U15 | 正常安装候选 | 无开发源码补丁也能完成真实往返，资源与 Skill 版本一致 |

业务判断单独检查：首次正文是否符合任务；整稿调整后主线是否成立；单页修订是否真的改对且未破坏原有内容。自动化用于验证确定行为，实际读稿、阅图与用户操作保留对应证据。

不要求新增事后计时登记，也不以测试数量、页面数量或静态截图代替使用结论。

## 十三、主要风险与控制方式

| 风险 | 对产品的影响 | 控制方式 |
| --- | --- | --- |
| 宿主不能可靠自动接收 | Web 仍有跨应用摩擦 | P0 先验证；批量手动退路须过真实使用验收 |
| 首版滑向批注器 | 无法支持方案级修改 | 将整稿重排、合并拆分、跨页改写纳入模型与验收 |
| 新 UI 另造状态 | 画面与真实结果矛盾 | 统一事实投影；UI 只管理草稿和显示偏好 |
| 前端先做完但无法接线 | 漂亮原型没有执行能力 | 第一条真实切片优先，缺口在原型阶段显式登记 |
| 新要求扩大为全稿重制 | 返工增加，用户失去控制 | 依赖与语义影响结合；只重制必要页面并说明范围 |
| 方案不断扩成平台 | 核心改稿闭环迟迟不可用 | 保留明确首版边界，新增能力按实际场景评估 |

## 十四、尚需验证的技术项与评审结论出口

本方案已给出产品取舍，不把全部决策留给后续会议。以下事项由实施验证解决：

1. **宿主交接方式**：是否存在可用于正常安装的可靠自动接收机制；不满足时记录手动退路和限制。
2. **请求与结果关联**：现有 Task/版本哪些字段可复用，最小增量如何支持多步制作及后续修订。
3. **整稿命令能力**：重排、移除、合并拆分的已有支持和缺失服务入口，以及失效范围。
4. **预览与审阅适用性**：旧成品、新正文、页级审阅和整稿审阅能否被准确投影。
5. **导出内容分离**：审阅文件、交付文件和工程包的具体文件集合与版本约束。

产品评审通过后，下一份实施输入应包含：更新后的工作台定义、界面原型、上述验证结论、接口映射及任务卡对应关系。达到这一步再开始全面替换 UI，避免将讨论稿直接转成大量前端代码。
