# RC3 campaign controller

This is an experiment controller, not the product's content generator. It never
calls a model or an image tool. It reads the selected arm's own installed SDK,
records actual operations, and consumes complete native envelopes without
filling their substantive fields. The immutable earlier `actual-content-runner`
driver/protocol are not inputs to this controller and remain unchanged.

Use the selected installation's absolute Python with `-I -B`. Keep actual project
paths short, for example `/workspace/work/rc3/r05/f02/p`; place evidence elsewhere.
Do not activate HOME Skills or change the admitted installation.

## Admission and identities

`freeze-campaign --registration <json> --out <new-directory>` checks a separately
reviewed `rc3-campaign-registration.v1` and saves it exclusively. It pins this
controller's bytes, protocol, shared public technical grammar, frozen exposure
registry, actual admission review, installation identities and G04/GID/GADAPTER/
GENTRY/GFREEZE evidence. A registration is evidence bookkeeping, not an external
signature. Root must verify the referenced facts independently before writing
`ADMITTED`; merely writing that string or a hash does not establish a gate.

An `ENGINEERING_ONLY_NOT_ADMITTED` registration may expose **only** a separate
neutral `GENTRY` case. It exists to run engineering admission without leaking a
benchmark answer or creating circular admission. It cannot initialize Q1–Q4 or
unseen tasks. Its observations are not benchmark results.

Each `installations[arm]` contains `source_sha`, `source_tree`, `wheel_sha256`,
`python`, `module_file`, `manifest: {path,sha256}`, and complete `package_files`
entries `{relative_path,sha256}` relative to the installed `deck_master` directory.
All non-pyc installed members must match, with no additional members. Every
command checks interpreter, module origin, original manifest and installed bytes.
Final/E1/E2 use their actual managed `capabilities.installation_identity`.
The tree is always checked against the pinned actual candidate manifest. Some
release metadata does not expose `source_tree`; that SDK observation remains
null. When the SDK does expose a tree, it must also match. A missing observable
field is never filled from the specification or treated as a different tree.

A0 uses `adapter_profile: "A0-public-legacy"` plus the actual original
`wheel: {path,sha256}`. A0 has no new capabilities/read-task-method API; the
adapter reads A0's own `task_summary` entries and their exact installed bytes.
Its own create/continue/input updates and supported envelope schema remain
unchanged. An absent modern review bridge stays absent; the original public
review entry and its actual blocker are recorded. No final-only migration,
capability, Task, receipt or package code is imported into A0.

The fixed CyberPPT reference is native content, not a Deck Master installation.
Its native-only recorder and the bounded native-image observer have separate
admission scopes. They must not manufacture Deck Master objects or use this
controller's installation check as their admission.

## Minimal real Host sequence

1. `init --campaign <frozen-directory> --out <new-run> --arm <arm> --case Q1
   --repetition 1 --project <short-new-project>` freezes one whole workflow
   identity. Q1/Q2 permit repetition 2. Q4A/Q4B remain separate checkpoints.
2. `public-operation --run <run> --operation service.create --arguments <json>`
   uses the arm's public entry. `service.continue_project` returns actual pending
   work. The adapter does not migrate, open extra framing phases, or cancel an
   input revision. Arguments are frozen verbatim in the journal.
3. `prepare --run <run> --stage <unique-name> --task-id <actual-pending-id>
   --role initial_writer` freezes the actual Task, work order, full method bytes,
   contracts, technical grammar and current manuscript. Give only the allowed
   packet and frozen source paths to the fresh Writer; never dispatch the whole
   registration, answer bank, private oracle, old native FINAL or other arm.
4. Root actually invokes a fresh `collaboration.spawn_agent(fork_turns="none")`,
   then records that response using `begin-native --run ... --stage ...
   --invocation <actual-root-observation.json>`. A continued workflow Writer uses
   a genuinely observed `collaboration.followup_task`. The Writer waits for the
   returned execution directory's `launch-ready.json` before claiming; Root may
   send that path after recording the real invocation. No observation is created
   by the Writer or inferred from a filename.
5. The Writer runs `claim-read --run ... --stage ... --ordinal <actual-ordinal>
   --executor <actual-canonical-id>` and reads the **entire** returned method/work
   order and source bytes. It writes one complete formal envelope. Root records
   full FINAL and actual completed status, then calls `observe --run ... --stage
   ... --ordinal ... --result <file> --result-sha256 <hex> --observation <file>
   --observation-sha256 <hex>`. Original bytes, including malformed outputs, are
   frozen before parsing or SDK consumption.
6. `accept` consumes that unchanged envelope. Format rejections, real reruns and
   changed-input Tasks count as separate actual Writer executions. Continue only
   through actual public operations and returned pending Tasks.

For `input_revision`, the formal contract requires stored proposal Refs. Before
any SDK storage, the Writer writes the complete formal envelope and its own JSON
proposal-object files inside the allowed stage. It computes each ordinary Ref
from its own Runtime's public `canonical_json_bytes`: UTF-8 JSON, Unicode kept,
keys sorted, separators `,`/`:`, non-finite numbers refused; SHA-256 gives
`.deckmaster/objects/<first-two-hex>/<sha256>.json`. This is pure calculation,
not a Store write. Root's full native completion binds every sidecar's
`{path,sha256,declared_ref}` in `native_object_files`. `observe` first freezes
all originals outside the project. `materialize-native-objects --run ...
--stage ... --ordinal ...` validates the complete file/Ref/proposal collection,
own installed schema types and existing own-project references before its first
Store write, then stores those exact objects without moving current. It changes
no envelope field or semantic content. `accept` then consumes the unchanged
Writer envelope. Validation failure writes no proposal object; a real storage
interruption may retain immutable orphan bytes and requires reconciliation.
This technical sequence must be shared, frozen and independently reviewed for
both arms before a Writer runs. It does not loosen the product's envelope schema.

An invocation observation contains `observation_kind`, `assurance:"host_attested"`,
`observed_at_utc`, actual `project_id`/`task_id`, and `spawn` with `tool`, actual
`canonical_task_name`/`returned_task_name`, `fork_turns`, `inherited_identities`.
A completion additionally pins `method_release`, `model_output_bytes_sha256`,
`method_read_record_sha256`, `all_method_bytes_read`, and `completion` with actual
`sender`, `message_type:"FINAL_ANSWER"`, entire `raw_final_message`, actual
`collaboration.list_agents` status observation and completed-agent identities.
These are Root's actual native transcriptions with host assurance, not platform
signatures, proof against a malicious coequal Host, or human acceptance.
Unobservable provider/model/seed/tokens/cost remain unknown.

## Scripted events and scope

`cases[case].materials` is the exact material allowlist. `events[event-id]` pins
`planned_dispatch:true`, `message:{path,sha256}`, source, and optional
`required_snapshots`. `scripted-event --event-id ... --trigger <file>` releases
only those bytes after a Root-attested actual trigger with exact source
observation references and an explicit explanation. The controller does not use
keyword matching to decide a business question was answered. Repeated questions
and unmatched questions remain separately recorded observations.

`materialize-instruction --event-id ...` stores exactly the already released
message and returns technical `host_attested_instruction` evidence. It never
creates a human receipt. Formal `service.inputs_update`, current request,
decision and proposal adoption remain distinct public operations with their
actual args/results. Root must use the predeclared technical mapping or native
Writer fields, never fill changed layers, prose, timings, claims or speech after
a refusal. Q1's real `input_revision` must execute; only current P5 is authorized
by its sample message. Q2's five-minute event follows the frozen comparison
timepoint. Q3 preserves the original absent-template checkpoint before a common
new-material event. Q4 keeps A and B projects and unmodified pages distinct.

`public-operation` supports create/continue/intake, input changes, collaboration
requests/decisions/grants, proposal adoption, styles/changes, generation freeze,
actual call allocation/begin, immutable image binding, candidates, exports,
readiness and operation queries. Store-taking public functions receive the
actual selected project's Store. Frozen generation parameters are exactly
`{"transparent_background":false}`; freeze **and** begin/binding recheck them.
Image execution, protected sealing and settlement use the separately admitted
image observer. There is no automatic image call or generation settlement here.

## Manuscript timepoints and independent review

`snapshot --name original_complete --native-manifest <file>` stores only the
actual raw-native sequence and optional lossless read-only conversion. The
manifest has format `rc3-native-complete-draft-manifest.v1`, the exact
`raw_stage_ordinals`, `assurance:"host_attested"`,
`complete_native_manuscript_observed:true`, a `completeness_source_observation`
matching one frozen completion, and optional `readonly_conversion` reference.
SDK outcomes are retained separately; the current Store cannot be renamed into
the raw draft. `first_sdk_complete` separately freezes the accepted manuscript.
The controller does not decide whether substantive writing is complete from a
successful SDK exit; Root must observe the actual complete draft.

Only after both timepoints are frozen does `review-prepare --role feedback
--bootstrap <actual-live-root-channel-observation>` dispatch current required
review units. This uses an opaque protected provider for modern installations.
The independent reviewer follows the same actual begin/claim/read/observe chain;
`review-accept` binds its unchanged envelope to its actual native observation,
all formal authors, current subjects, dependencies and packet. Review-only
acceptance must not change manuscript or production pointers.

`deliver-feedback` freezes at most one actually accepted feedback. If it contains
a defect, `repair-begin --necessity <file>` permits one autonomous cycle and up
to three necessary Writer layers (`argument`, `page_copy`, `speech`) referring
to actual finding IDs. Actual Tasks must match those layers. No defect means no
invented repair. After real fixes, a separate `review-prepare --role verification`
records read-only current required units and explicit historical finding closure.
The same independent feedback reviewer may continue as verifier; an author may
not. New verifier/blind feedback is not returned for another equal-budget repair.

`snapshot --name qualified_for_owner` requires actual current gate `pass`, no
missing units/blockers, post-repair verification where applicable and no exceeded
budget. The Runtime's explicit current `replaces`/finding closure determines
qualification. A separate empty passing review cannot erase old findings.
`equal_budget_evaluated`, `owner_later` and `extra_work` remain distinct.

`production` cannot label a compose Task, nor can production review label a
preproduction review. Post-comparison writing requires an already frozen
comparison manuscript and actual Q2 change event. Extra writing needs
`declare-extra --evidence <file>`. Either branch prevents any later current
manuscript being called the equal-budget/qualified comparison snapshot.

## Failures, recovery and limits

Every SDK write records an exclusive intent and actual outcome. An exception or
interruption leaves commit state unresolved. Use actual Runtime operations
query/current-state evidence, then `reconcile --record <file>`; the record has
`operation_key`, `observed_state` (`committed`, `not_found`, `unknown`) and pinned
`runtime_observations`. Unknown remains blocked. Reconciliation never resends a
command. A new retry uses actual Runtime idempotency/CAS rules, not the journal
as authority. For an unresolved intent, `status` shows the immutable operation
arguments, including real SDK operation ID where supplied; query the selected
arm's public CLI directly and preserve that read-only result.

The common comparison budget is five initial substantive Writer executions, one
feedback, one autonomous repair cycle and at most three necessary repair Writer
executions. Actual over-budget calls remain recorded and cannot be consumed as
equal-budget results. Verification and production calls are separately counted.
This is not a claim that phase count equals the original twelve whole workflows.

## Separate native image observer

`image_controller.py` records separately admitted bounded image trials. Its
global budget pins one canonical ledger root before the first call; every batch
uses the same root and whole-workflow/repetition/page/arm keys. A new batch or a
copied ledger cannot reset consumed/unknown rights. Each prepared trial binds
the real own-installed Task/Request/Attempt, authorization, exact tool arguments
and reference bytes. Root alone makes the actual literal image-tool call; only
after its genuine completion may the new observer seal and settle it. It never
reads historical pilot keys. Each new observer root owns its own private key,
which must never enter reports or portable evidence.
