# 内容方法｜公共成稿方法参考稿

本文件是 Deck Master 的公共内容方法：跨用户、跨类型可复用的成稿方法，
不绑定某个人的表达习惯。它回答"一份首次交付就能进入正常业务审阅的
Deck 是怎么写出来的"，并说明方法如何落到 Deck Master 的产物和命令上。

方法来源为精选的个人优秀方案实践，已按公共方法改写：保留"为什么在
这类任务中这样做"，并补充不适用条件。文中所有示例均为合成材料，仅
用于说明方法，不是客户事实或真实项目结论。

## 0. 方法如何落进流水线

| 方法 | 主要落点 |
| --- | --- |
| 判断交流任务 | deck_brief / narrative_plan 的任务定义；开场与结尾的取舍 |
| 解释业务机制 | 每页正文与业务机制图（visual_spec、流程图） |
| 形成观点 | claim_map 的核心论点；页面 core_claim |
| 选择方案 | 方案比较页与推荐理由；page_tasks 的 decision_intent |
| 组织整稿 | narrative_plan.beats 的页面集合与顺序 |
| 写成页面 | page_packages 的 customer_visible 正文、speaker_notes、引用 |
| 实际编辑 | local-edits 流程：改 Page Package → 刷新下游 → 重新读回 |

方法不是七个新阶段，也不要求每页出现对应字段。一份 Deck 的正常工作
顺序是：理解材料与场景 → 写出完整正文 → 导入（`import-plan`）→ 制作
→ 审阅并修订。完整定稿导入见
[新建 Deck playbook 的整稿导入节](../playbooks/codex-run-solution-deck.md)。

## 1. 判断交流任务

**可执行写法。**从已有信息确定三件事：对方已知什么、本次需要他们理解
或选择什么、这份材料因此必须提供哪些实质内容。任务类型决定结构：
首次能力交流要交代企业是谁、擅长什么、能力如何发挥、什么案例能支持
适配判断；已有客户方案评审不复述已知背景，直接进入当前目标、推荐方
案、关键机制与实施依赖。结尾同样由任务决定：能力交流可以总结适用任
务范围；方案评审结尾呈现本次真正需要判断的事项。

**为什么。**结构与详略从交流任务推导，才能解释"为什么这份 Deck 长
这样"，而不是套一个通用目录。

**不适用条件。**用户明确指定页数或结构时按用户要求执行；纯展示类材
料（如产品手册翻新）不强制推动式判断。

**反例。**所有首次交流都用痛点诊断开场；所有结尾都呼吁启动 POC；
已有客户评审还从公司介绍讲起。

## 2. 解释业务机制

**可执行写法。**对方案涉及的业务过程，讲清参与者、触发条件、输入、
各方（人/系统/Agent）执行的动作、产出写回哪里、哪里发生了有意义的业
务变化。写完用一句话回放这段过程；回放不出来，说明方案还没想清，先
补机制再拆模块。图示优先画这条机制（有责任边界的流程、状态变化），
而不是画几个互不关联的能力卡片。

**为什么。**客户按机制判断方案是否成立；机制讲不清，任何形容词都无
法建立信任。

**不适用条件。**纯数据展示或日程通知类页面不需要完整机制链，讲清
"看什么、怎么读"即可。

**反例。**"AI+数据+平台"即解决方案；用"赋能、打通、闭环"替代过程
描述；架构图与正文各说各话。

## 3. 形成观点

**可执行写法。**对照事实、目标和约束提出值得讨论的判断，并区分三个
层次：材料证实的事实（引用来源）、基于事实的分析（说明推理）、建议
（说明理由与成立条件）。材料缺失时先补读原文或补充研究；仍不足则明
确写出假设与验证方式，不把假设包装成结论。

**为什么。**复述资料没有增量；敢于形成判断并标明依据层级，才是专业
稿件与资料摘编的差别。

**不适用条件。**合规审计、法务陈述等以忠实转述为目的的材料，观点层
次让位于逐字准确。

**反例。**把资料复述当洞察；没有现成句子就不敢提出设计；把分析建议
写成已验证事实。

## 4. 选择方案

**可执行写法。**存在真实取舍时提出两到三个可行方案，比较范围、已有
条件、依赖、可验证程度与业务效果路径，说明推荐项的关键依据与成立条
件。被硬约束排除的选项可以说明排除理由，不把它包装成等价备选。材料
不足的成本/收益不伪造；没有真实取舍时不凑三个方案。

**为什么。**客户要的是"为什么推荐这个、什么条件下它不成立"，而不是
一排明显陪跑的选项。

**不适用条件。**用户已确认方向时沿用既有决定，只在该决定需要补充论
证时补写理由。

**反例。**先定推荐项再把其他选项写成明显不合理；用"方案一/二/三"
模板凑数；把未验证收益写成承诺。

## 5. 组织整稿

**可执行写法。**让后续内容建立在前面已说明的信息上：每个概念首次出
现即解释；证据放在它真正支持的论点附近；顺序和密度按任务与呈现条件
（现场讲解或独立阅读）决定。公司介绍、案例、架构由同一条主线组织，
不分别生成后拼接。封面、章节页不承担正文证据与密度要求；一页讲不完
的机制拆页，讲得清就不为凑页数注水。

**为什么。**Deck 是一次完整交流，不是页面集合；读者按线性理解，论证
断裂会被逐页放大。

**不适用条件。**附录、参考资料集允许非线性组织，但需标明用途。

**反例。**公司介绍、案例、架构三段拼接后互不引用；同一案例重复三遍；
先填占位页再裁剪论证。

## 6. 写成页面

**可执行写法。**每页先写结论，再组织支撑：标题表达该页需要受众接受
的判断（结构性目录页除外）；正文回答"这个机制怎样工作、为什么适合
当前场景、如何判断有效"；为页面选择最能说明问题的表达形式（表格、
流程图、对比），而不是默认三张能力卡片。引用跟随正文断言，标明来源
与适用条件。讲者备注写给现场讲的人，不写制作说明。内部推理、页面职
责、制作要求放在 `internal_only`，不出现在客户可见文字里。

**为什么。**页面是客户实际阅读的单元；"本页通过三个维度建立信任"是
作者备注，客户要读的是三个具体事实。

**不适用条件。**无。此方法对所有客户可见页面生效。

**反例。**标题写"三大优势"就算修复；图内标签出现"本模块""此页"等
制作语言；高密度补充文字只是把空泛话术换个说法塞满页面。

## 7. 实际编辑

**可执行写法。**审阅是改稿，不是出报告：读完整稿、来源与实际成品页
面，修正具体内容——补读已有资料、增加直接证据、缩小主张、改正计算、
解释机制、修正图示关系、删除非必需断言。修改按内容影响传播：文字偏
好通常影响单页；案例数字、系统边界或方案选择变化时，检查所有引用该
内容的页面与整稿结论。改前改后对比是否更好完成了本次任务；没有实质
改善时不制造返修轮次。

**为什么。**"建议增强说服力"式报告把创作负担退回给用户，违背一次
交付可用的目标。

**不适用条件。**实质业务决定缺失时（如预算、范围变更）请用户裁决，
其余自行修复。

**反例。**提交"建议增加说服力"的报告；扩大禁词表代替改稿；改了 A
页的数字却留着 B 页引用同一数字的旧结论。

## 示例：一次完整的成稿推演（合成材料）

材料（完全合成）：企业提供资料接入、引用问答、权限与门户集成；一个
历史项目完成了手册/工单接入和上线培训，没有效果数字。客户售后判断
依赖设备型号与版本，但当前门户不要求填写版本。120 条互斥分类记录中，
36 条信息齐全可按资料处理，54 条需先补问版本或批次，30 条信息齐全仍
需专家判断。门户支持加字段和展示查询结果，工单接口本期只读。

由材料形成的设计观点：优先把设备条件收集前移到服务点提交时，并为专
家准备完整问题上下文。不能推断 54 条都会被自动解决，也不能推断效率
提升比例；若现场根本无法获得设备条件，应改为设备识别/现场信息采集方
案——增加字段不一定有效。

三页对外正文示例：

**页面一：让产品知识进入一线售后工作流**

> 我们提供技术资料接入、引用问答与业务系统集成服务，把设备手册和维
> 修记录接入服务人员日常使用的工作入口。统一查询帮助定位资料；引用
> 位置帮助回到原文核对适用条件；企业身份与权限对接让应用沿用现有访
> 问体系。
>
> 在设备维修知识应用项目中，我们承担了手册与维修工单接入、权限对接、
> 引用问答界面及上线培训。这些交付经验可以用于资料、权限与服务入口
> 的协同建设。

**页面二：把设备条件收集前移，减少总部接单后的重复补问**

> 当前服务判断依赖型号、版本或批次。120 条记录中，54 条首次处理需要
> 补问版本或批次；36 条信息齐全可按现有资料处理；另有 30 条仍需专家
> 判断。
>
> 仅增加资料搜索入口，会保留提交后再补问的流程。建议在服务点提交问
> 题时提示补齐设备条件，让总部收到包含设备信息、问题现象和候选资料
> 的完整问题包。54 条补问记录支持优先改善这一环节，不代表这些问题
> 都能自动解决。

**页面三：在现有门户中连接条件补齐、引用问答与专家接力**

> 资料搜索增强可以改善查询，流程改动较少，但设备条件仍按原流程补充。
> 门户内的条件补齐与引用助手，能把补问前移，并按资料适用范围展示引
> 用；相应需要新增设备字段、适用范围映射和补问交互。
>
> 建议采用第二种方式：服务点提交设备与问题信息，系统提示补齐缺失条
> 件，检索并展示适用资料；需要进一步判断的问题附完整摘要转交专家。
> 工单接口按本期约定只读，摘要在现有流程中使用。

验证关注首次信息完整度、专家重复补问次数以及引用资料与设备版本的适
配性。已有资料与权限集成经验支持接入部分，设备条件映射与转交体验属
于本期新增设计。

注意这三页的关系：页面一交代能力与经验（首次交流需要建立信任），
页面二用客户数据引出设计观点，页面三给出方案选择与边界。若是已有客
户方案评审，公司介绍压缩为一句，直接从推荐选择、条件映射与实施内容
展开——不能只换标题，也不必把边界再单独扩成一页。

## 示例：返修前后（合成）

不合格的 finding：

> "P002 需要增强说服力。"

合格的返修：

> "P002 将接口写成'已确认可用'，但来源 S-SCOPE#E003 仅说明接口接入
> 方式需核对。该断言影响实施可行性。将其改为设计前提，并在试点阶段
> 保留接口核对；不得补造外部资料来证明客户私有接口。修改范围为 P002
> 与相关已授权实施描述，复审检查全文不再出现已确认表述。"

前者把创作负担退回用户；后者指明断言、依据、影响、修法与验证范围。

## 边界

- 公共方法不携带个人客户的私有事实；示例全部为合成或允许公开的材料。
- 方法不恢复时间指标：质量优先，不以耗时衡量产出价值。
- 方法不预设"所有 Deck 必须公司介绍开场 / 痛点诊断开场 / CTA 结尾"；
  这些都由第 1 条方法按任务推导。
