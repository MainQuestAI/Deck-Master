# 输入变化后的持续修改

## 先保存变化，再继续同一项目

新受众、新用途、正式决定替换或新增/替换来源，使用 inputs update。某页改字或颜色偏好使用已有 edit/feedback。不能把全局要求只塞进修某页的指令，也不能替换原始历史决定而不留版本。

工作单必须说明旧内容对应哪版输入，本次什么发生了变化，以及哪些决定仍有效。existing_decisions 是当前有效集合，不把互相矛盾的新旧规则不断追加。

## 看全稿关系，而不只搜索引用

阅读整体任务、新材料、变化说明和全稿概览，打开相关 Page 与原文。某来源没有被直接引用，不说明它对结论没有影响。反过来，补一份无关设备清单也不意味着要重画整份稿。

四种典型处理：

- 补充证据：校验现有断言，必要时更新正文/脚注；其余页保留。
- 正式范围变化：更新受影响的机制、架构、实施和总结，不只换一个词。
- 受众/用途变化：重新安排结构与解释量，可以调整较多页面，但保留仍适用内容与已认可设计。
- 只改局部表达：保持语义和关系，复用原始蓝图及未变页。

## 返回实际差异

compose 的 input_revision intent 返回 content_update。upsert_pages 只放真正变化或新增的完整 Page；remove_page_ids 放明确退出的页；page_order 是最终全稿顺序。保持已有页面和 atom 身份，不通过重命名全部 ID 假装全稿都是新内容。

没有实际影响时，用 unchanged_reason 解释本次材料与任务的关系，不能写“没有发现问题”充数。代码保存判断并更新正文依据，不自动产生质量通过记录。

`compose.v1` 任务同时在信封顶层提交更新后的完整 `content_plan`，它仍须覆盖最终所有页面；正文继续只用 `content_update` 提交差异。复用保留页面的 goal_id，以本次材料版本重新核对来源定位。即使正文无变化，也要记录这次输入的整合判断和未解决事实。不要用顶层 pages 把差异更新改成全稿替换。

## 示例：只读变为草稿写入

原要求：接口完全只读。新正式说明：允许保存草稿，员工正式提交，不能自动关闭工单。

应修改接口范围、流程与相关验证内容；不能把它写成已经具备的历史交付能力，不允许扩大为自动执行维修或关闭工单。公司介绍、未受影响案例可以保留。实际是否需要修改某页，取决于该页内容，不按章节名固定推导。

如果某条旧 finding 要求补的内容已被用户撤销：按新输入修改相关页后，由新一轮 content 审阅对当前页复查，并在说明中引用这次 input revision。页面没改、只是要求不再适用时，不要把它伪写成 fixed，应保持开放并如实告诉用户（v1.1 的已知限制）。几何错误、不可读文字和真实敏感信息不因为改用途就自动消失。

## 并发、恢复与等待

同一项目又收到更新时，旧工作单应被替代；不要用旧 produced_against 提交新输入内容。若其他执行者修改了全稿分析依赖的页面，重新读取当前版本，保留自己的工作作为可比较草稿，不强行覆盖。

必要业务决定尚未明确时提出具体问题，并持久化已知上下文。恢复会话后使用同一项目继续；没有 Host 的工作台只能记录反馈和显示等待，不能宣称后台正在思考或制作。
