# 内容到设计：保留关系，不按框架名称套版

设计依据当前作品和本次修改范围。下列规则只决定表达方式，不授权重写结论、删必要限定或制作未获授权的页面。

## 先识别关系
比较关系→共同标准的表格或分面；时序关系→步骤或时间线；因果/机制假设→明确箭头及条件；组成→分组与分母；教学辨别→关键差异可同时观察的案例对。正文块分组用于组织信息，版式由阅读任务决定。状态流在 layout 写清读者必须看出的节点、方向与分支。需要短标签时，从原文提取到 content.labels，保留原句和事实限定。

同一方法没有唯一版式。问题树可以只用一句综合判断和一张差异表表达；Toulmin不必画六个框；SCR不必占三个章节页；Pugh可以使用自然语言和数值，不必展示符号计分。

## 从构图句决定主视觉

先读 [page-writing](page-writing.md) 的页逻辑、按页职责写标题的规则和两类对照。阅读任务、标题、构图句及按结构组织的正文须先写好；交接缺任一项时先回到内容补写。Rust `deck` 将它们保存在 `purpose`、`content.title`、`layout` 和现有正文块中。构图句应给出本页关系、对象与方向或分支、分区职责、表是主视觉还是取材，以及拍扁会丢的关键事实。它要能具体到这一页；“闭环图”或“用三列卡片”不足以作决定。

已声明关系与主视觉须一致；生图前改稿顺序沿用 [page-writing 的关系约束](page-writing.md#构图句写出本页的空间逻辑)。

查阅页逐行核对就留表；机制或状态流页用表取材后，还要把正文按状态、条件、证据重组，不能只在大表前加一句画流程。块类型不决定画面类型。关系名称只是例子，不作图种枚举；房子图、金字塔不进默认菜单，层级支撑直接描述谁支撑谁。视觉系统归作品 style 和共享的 [视觉系统参考](design-system.md)，风格口号不能代替构图句。

禁止在生图时追加“扁平色块方便还原”或同类要求。正式输入若要改，先改作品中的正文或构图句，再准备任务；保留关系后按共享的 [还原策略](reconstruction.md) 重建可编辑页面。

## 三类不得丢失的语义
- 比较：各列的范围、单位、时间窗一致；正负符号必须与实际标准方向一致。
- 机制：观察事实、拟议设计和待验证箭头区分；图形位置不把相关变因果。
- 条件：影响本页结论的前提在读者能看到的位置；不能降为几乎不可读的脚注。

## 页面装不下怎么办
先识别重复与无贡献装饰，再提出拆页/分组/附录候选。需要修改正文、关键比较项或概念边界时回到正文改稿，不静默裁切。可用总览矩阵＋下一页必要细节；不执行“一律压成一页”的规则。

三种语义示例见 [semantic-layout-examples](../assets/design/semantic-layout-examples.md)。完整案例after稿是内容依据示范，不是排版尺寸标准。画布与字号取自实际任务和 [SVG 子集](svg-subset.md) 的换算说明。

## 主视觉与提交

先用一句写明这一页必须让读者看出的对象、方向和分支。类别名不能代替这句决定。比较和查阅可以继续以表为主视觉。

Host 读取 `deck run start image` 生成的 task.md，原文作为 ImageGen 的 prompt，附件按 attachments.json 传入。不要另写一份较短提示词覆盖。新的意见先改作品中的正文或 layout，再准备新的 run。代码当前不会拦截 Host 手写短提示词；原样提交是技能要求，遵守情况靠真实会话观察。提交是否与文件一致、原图是否成立，分开记录。没有实际阅图，不称视觉通过。可自动验证 task.md 继承输入及 export md 保留可读结构；这不能代替 T07 对原图与最终画面的视觉人判。

## 上屏边界与可编辑对象

上屏文字只取作品 content；todo、内部方法依据与制作说明不上屏。notes 放讲述提示，影响结论的业务条件仍留正文。必须可编辑的对象与有边界留图的范围按 [还原策略](reconstruction.md)，不能整页嵌图代替可编辑正文。
