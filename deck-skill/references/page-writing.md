# 从分析成果写成实际页面正文

问题树、论证卡和权衡表是写作材料，不是客户必须阅读的工作记录。完成的方法操作应转成自然、可用的正文。正文写入作品的 content；目的、布局、讲稿、待补和出处分别保存。

## 页逻辑写进现有字段

先确定这页让读者完成哪一个阅读任务，再挑承担回答的材料。标题按页职责写：判断页用完整判断句；查阅页明确查阅职责，例如“要求与响应对照”；说明页和教学页可用说明性、概念或问题标题，不强制结论标题或商业 CTA。判断页写不出判断时，检查是否混了多个问题，需要拆页，或实际承担其他页职责。无关结论删掉或后移，重复而不推进的页合并。“本页不讲什么”体现在删和后移中，不另落字段，也不写进会导出的目的或布局。

Rust `deck` 使用现有字段保存：

- `Page.purpose`：阅读任务，说明读者要看清、判断或查找什么；导出为“本页目的”。
- `Content.title`：按上述页职责写的标题。
- `Page.layout`：构图句，说明本页对象怎样在空间中形成关系；导出为“布局”。
- `content.body_blocks`：按这句结构组织的完整正文。关键事实和必要限定留在正文短句；`content.labels` 只提取“排队”“执行中”等必要短名，不承担整段解释。

目的和布局都是读者会读到的话，不放制作备忘、风格口号、工具指令或分区百分比。字段填过不等于内容成立；信息不足就保留真实边界，不让生图补造事实。

## 构图句：写出本页的空间逻辑

先说本页是什么关系，再说对象、方向或分支、分区各自承担什么、表是主视觉还是取材，最后保住拍扁后会丢的关键事实。查阅表、状态流、闭环、时间推进、架构分层、旅程交接、对照等都是关系例子，可以按实际内容写其他关系，不是封闭名单。

可借用这句帮助思考：

> 主图是[本页关系]：[对象与方向或分支]。[主区、旁列、底部各放什么]。[表是主视觉还是取材]。[拍扁会丢的关键事实]。

这是写作提示，不是程序校验模板。只用实际需要的分区，不为凑句式添侧栏或底栏。检查换一页还能不能照搬这句；能照搬往往说明缺少本页对象。“闭环图”“流程图”“中间是任务状态流”都太薄，“三列卡片展示三个要点”只说了排版。构图句应让人读出谁到谁、何时分开、哪里回流，以及哪些事实不能被并列摆放冲淡。

风格参照归作品的视觉系统，不代替关系。房子图、金字塔不进默认菜单；内容真是层级支撑时，直接写“底层三项条件共同支撑上层两个结果”。

## 两类对照：换关系与留表

以下均为合成示例，数字与要求不得移作当前项目事实。

**状态流页：表只作取材。** 原稿把校验、排队、执行、结果、容量与验收都塞进“模块／能力／说明”大表，配一句“中间任务状态流”。这会把状态与限制收成等权卡片，排队和执行的区别也消失。

改写为：

- `purpose`：看清任务从校验到结果的分支，以及并发目标适用的状态。
- `content.title`：排队与执行分开，才能核对并发目标。
- `layout`：主图是任务状态流：校验通过后，有空位进入执行，无空位进入排队，空位释放后排队任务进入执行；执行后分为成功或失败。主区沿状态方向展开，旁列放容量条件，底部放验收证据。原模块表仅作取材。50 指执行中并发目标，不是排队人数。
- 正文按关系重组：用“状态与分支”要点写校验、排队到执行、成功或失败；用“容量条件”短句说明并发目标；用“验收证据”要点写分别记录排队数、执行数和结果。必要短标签取“排队”“执行中”“成功”“失败”。不要在这句后继续拖着原来整张大表。

**查阅页：表就是主视觉。** 读者要按行找到要求、响应和展开位置，把它改成闭环或模块图会丢掉逐条核对能力。

- `purpose`：逐条核对要求、响应要点与展开位置。
- `content.title`：要求与响应对照。
- `layout`：主图就是查阅表：主区按“要求 → 响应要点 → 展开位置”逐行对照，底部说明响应状态口径；表是主视觉。每项要求与对应响应及位置保持同一行，拟议响应不表示已经交付。
正文保留查阅表：

| 要求 | 响应要点 | 展开位置 |
| --- | --- | --- |
| 异常记录 | 拟记录失败原因 | 异常处理章节 |
| 结果导出 | 拟支持按任务导出 | 导出说明章节 |

底部短句解释“拟议响应不表示已经交付”。按构图句留表就是成功。

表与关系图的选择来自阅读任务：查找规则、证据、报价、权限或逐条核对时留表；看状态分支、反馈、交接或阶段依赖时，把表当素材，正文也随关系重组。不按标题里有没有“封面”“流程”自动禁表。正文块是事实容器，`paragraph`、`bullets`、`table` 不自动等于画面中的卡片或表格。

## 写作的四个动作
先说本页回答哪一个问题；挑出直接承担回答的材料；把材料与回答间不可省略的理由写出来；最后补上会改变理解或使用的条件。顺序可因教学、研究和操作任务调整，不要求每页出现同名栏目。

| 页面任务 | 应写到的程度 | 不能停留的形式 |
|---|---|---|
| 判断 | 具体判断＋可比对象/范围＋证据为何支持 | “趋势良好、需要重视” |
| 机制 | 谁在何时用什么信息做什么，状态怎样改变 | AI→数据→平台三块连接 |
| 对比 | 同口径的真实差异、各自后果、改选条件 | 推荐项全优，其余全差 |
| 实施 | 交付物如何改变工作，依赖和验证如何安排 | 甘特图横线＋加强协同 |
| 研究 | 观察如何得到，解释能到哪里，不能到哪里 | 文献逐篇摘要拼接 |
| 教学 | 一个完整判断/操作示范，边界和新情境反馈 | 定义＋名词清单＋灵活运用 |

## 一段写实示范
不写：“通过知识治理与AI赋能提升效率。”
改为：“先在请求入口记录型号和版本，再限定检索资料的适用范围。工程师能直接核对引用章节；需要总部接手的问题同时带上设备条件和已查资料。现场能取得设备条件时，可在接单前补齐；暂时无法取得的条件标为待补并随摘要交接。”

这段的专业性来自过程与作用，而非“参与者/触发/价值”标签齐全。没有材料证明当前已有上述能力时，写成拟议设计，不写成已上线。该段解释工作机制，没有承诺节时比例，不必追加收益测量段；若进一步主张减少处理时间，则需给出依据或标明待验假设及测量口径。

## 表格、流程与注释也是正文
矩阵应能让读者知道每一列比较什么、每一行的后果是什么；流程箭头说明触发和交接；必要条件不能只放notes。引用或证据ID若对读者无帮助可留内部追溯，但真实来源不可删除。

## 交给设计

交接阅读任务、按上述页职责写的标题、构图句及按结构组织的完整正文。缺任一项时，Host 先补写并保存，不调用 `deck run start image`；草稿仍可保存和导出。必须改正文时仍回到内容范围。正式生图使用 task.md 原文，命令见 [commands.md](commands.md)。导出 `export md` 后实际阅读标题、“本页目的”、“布局”和正文，核对分支、限定、分组及查阅表对应关系。可读稿组织与 PPTX 画面还原分开判断。

## 各类输出边界
只要策划时交主张与框架，不用空白页假装正文完成；已有方向只补正文时沿用该方向；只改讲稿时保留正文与事实；局部修改不重写范围外页面。

## 成稿自查
把“此处展示、通过三个维度、建议补充”之类制作注释移出正式正文，真正写出需要展示的内容。删除只是换词重复的副标题、SO WHAT和总结句。保留独特证据、推理、例外或操作信息；不通过抽走内容换取好排版。
